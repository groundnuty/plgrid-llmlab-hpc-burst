# HBEP-4: Provider interface and profiles

## Summary

This HBEP defines how the framework works with providers: our access to one platform each (HBEP-3). Providers share one core interface, with capability flags that say which core operations a provider supports. What is true for everyone on a platform is data in its platform profile. What one provider adds (its account, grant, credentials reference, allowed partitions and labels) is its provider settings. Upstream bugs go to a known-issues register tied to versions, with a regression test and a workaround expressed as configuration. It is written for authors of provider plugins and of the lifecycle controller (HBEP-7).

For alpha it decides:
- the Slurm provider: the Slurm command-line tools over one multiplexed ssh connection per login node and credential, under crossplane-runtime's managed reconciler (spike S4, PR #32);
- its core operations, written as an interface;
- the Slurm dialect: the tag in `--job-name`, the queue listing then accounting, and the JSON of data_parser v0.0.40 and v0.0.42;
- the typed fields of the platform profile that alpha reads;
- the LLMLab managed provider as a read-only catalog.

## Motivation

Stage 1 (hit the limit), stage 2 (get resources), stage 3 (keep it running) and stage 7 (pay and give back), as defined in HBEP-2.

Problems this addresses, in general terms:
- **Submission rules differ per cluster and are learned by failure:** required options, job-name rules, compute nodes without home directories, schedulers that print local time.
- **Scheduling facts break naive designs:**
  - start estimates swing by hours and flip to unknown;
  - a freed slot goes to another user at once;
  - cancelling a parent starts its pending follow-on at once;
  - a dependency offset counts from the parent's start, not its end;
  - users cannot extend a job's time limit, and a running job's account cannot be changed;
  - a fast-start partition allows one job per user, pending jobs included.
- **A managed gateway has its own failure modes:**
  - it cuts replies that send no byte for a fixed time, and stalls periodically;
  - models go inactive without the listing showing it;
  - unknown, inactive and blocked models return the same error;
  - it rewrites requests;
  - keys expire mid-run.
- **Upstream bugs:** a router's default total deadline cut long streams without a log line; an engine's keep-alive was shorter than the router's connection reuse; a compile on an unseen shape ran past the engine's step limit and killed it. Each workaround lived in notes or one-off scripts, and nothing turned it off once the bug was fixed.
- **Usage was hard to count:** the center's accounting tool counted only finished jobs, billing formulas differ per cluster, and behaviour at grant exhaustion was unknown until it happened.

### Goals

- One core interface that every provider implements. Differences are flags and data, not branches on a provider's name.
- Every contingency as a profile parameter with thresholds, enabled by default and cheap when idle.
- For each upstream bug: a register entry tied to versions, pinned where HBEP-15 records each pin, one regression test, and a workaround as configuration.
- A new platform is added by writing its platform profile, plus plugin code only where data cannot express a difference. A new provider on a known platform is only provider settings.
- Expected performance in each platform profile, as the reference for qualification (HBEP-3, HBEP-7).

### Non-goals

- Lifecycle decisions: when to hedge, over-allocate, hand over, drain, restart or repurpose (HBEP-7). This HBEP exposes what those decisions need.
- What runs inside an Allocation, and how Instances start and restart (HBEP-7). This HBEP starts the job and stages the files it needs.
- How instances are reached (HBEP-6). The profile records the reachability facts HBEP-6 relies on.
- Which providers serve a model name. That is routing policy (HBEP-3, HBEP-5).
- Center priority pushes. The framework never assumes one.
- The static kind's interface, which comes later.

## Proposal

### User stories

- An operator adds Cyfronet Athena. They write its platform profile (time limits, submission options, billing formula, container runtime, expected performance), and reuse plugin code where the profile can express the difference. Then they add a provider for their grant there: provider settings with the account, a credentials reference, the allowed partitions and the labels.
- The operator gets a second grant on Helios. It is a second provider: new provider settings over the same platform profile.
- The lifecycle controller hedges `example-27b` across a provider on Helios and one on Athena. It reads each provider's start estimate as advisory, submits on both, keeps the first Allocation whose Instance serves and cancels the pending loser (HBEP-7). Hedging across providers at once comes after alpha.
- The controller qualifies a new Instance on Athena. Its benchmark falls well below the profile's expected performance for that node type, so the controller discards it (HBEP-7).
- LLMLab takes a model offline. Its listing does not show it, since the listing carries no activity flag (Managed provider in alpha), so in alpha the model shows only as LLMLab's 503 at serving. After alpha, the managed provider reports the model's state and returns a defined error instead of an ambiguous one.
- An engine upgrade fixes a bug. An HBEP-15 amendment raises the supported engine version, and the workaround is removed after it. The register entry keeps its fixed-in version, and its regression test keeps running (Known-issues register).
- An agent asks what an allocation has cost so far. The scheduler's billing for the allocation, in its partition's billing unit, times the allocation's actual running time gives the answer (HBEP-8, Provider accounting).
- The controller restarts while an `sbatch` is in flight on Helios. The Slurm provider finds the job by its tag, adopts it, and lifts its hold once. No second job runs.

### Notes, constraints and caveats

- **Alpha scope** (science-agent decision, 30 Oct 2026, within the alpha the owner set for HBEP-11):
  - one batch platform kind, Slurm, over ssh and the command line;
  - Helios and Athena as the alpha platforms, both with `holdRelease` true, measured by spike S1 (issue #18). Sano stays outside alpha. Its hold is not checked, so it would run fallback mode, and none of the per-partition preconditions is measured there: Apptainer on the compute nodes, a 56-character job name, a home directory that compute nodes can read (open questions 15 and 16) and the `sbatch` latency (Graduation criteria). Its required QOS no longer keeps it out, since a Provider can now name one (Provider settings; amended 2026-11-01); Since 11 Nov 2026 alpha graduates on Athena alone, by the owner's decision, and Helios's criteria run in beta when GH200 returns (Graduation criteria).
  - the LLMLab managed provider as a read-only catalog, with no start or restart;
  - a single user (HBEP-11).
- **Two layers.**
  - A platform profile holds what is true for everyone on a platform: hardware, architecture, limits, time zone, filesystems, requeue behaviour, expected performance, billing units and dial-home modes. Known issues are in the register, whose entries name the platforms they apply to (Known-issues register; amended 2026-11-16).
  - Provider settings add one provider's account, grant, credentials reference, allowed partitions and labels (organization, platform, partition, account; HBEP-3).
  - Every provider on a platform uses that platform's profile.
- **A provider is a plugin, a platform profile and provider settings.** Providers share a common core plus capability flags.
- **Two controllers.** Only a Provider's own controller calls its platform. The lifecycle controller (HBEP-7) creates and deletes Allocation objects and reads their status; it never calls a provider (Design details).
- **Cluster API.** The provider model follows Cluster API's idea of pluggable infrastructure providers behind common resources, applied to model serving.
- **Kinds** (HBEP-3) follow the platform: managed (a fixed catalog, no start or restart), batch (leases with unknown start and hard end, continuity through follow-ons) and static (later).
- **LLMLab will improve but keeps the same kinds of characteristics.** Its contingencies stay in its platform profile even when they rarely fire; thresholds keep them cheap.
- **Hedging is the framework's lever** (HBEP-3, HBEP-7). The core must therefore let the controller submit on several providers, read start estimates marked advisory, see promptly when an allocation starts, cancel a pending allocation, and read each allocation's hard end.
- **Agent primitives** (HBEP-10) require idempotent operations and reports of partial failure, so every core operation reports per-job results, and every one except submission is idempotent. For submission, the tag on the job supports recovery but does not enforce uniqueness. In hold mode every job is submitted held and only the recorded job's hold is ever lifted, so at most one job per Allocation runs (HBEP-7, open question 11).
- **Spike S5 (PR #19).** S5 recorded login-node facts for Helios, Athena and Sano as draft platform profiles in `profiles/`. Spike S1's step 0 (issue #18) added the first compute-node facts and the hold check to the Helios and Athena drafts, on its branch (commit 35babef). The entries below that cite S5 rest on its measurements and on the centers' documentation.
- **The job transport is decided:** the Slurm command-line tools over one multiplexed ssh connection per login node and credential. `squeue --json` and `sacct --json` work for a plain user on all three platforms (spike S5, PR #19). A REST job API stays a later option (open question 13).
- **The container runtime is a per-platform fact.** Apptainer is on the Helios and Sano login nodes. None of Apptainer, Singularity, enroot, Podman or Docker was found on Athena's login node, and other runtimes were not searched for. User namespaces are off on both Cyfronet login nodes (spike S5, PR #19). On the compute nodes, spike S1's probe 2 (issue #18) found Apptainer on both alpha partitions, with user namespaces off. Helios GH200 runs a SIF image; Athena A100 runs a sandbox directory but not a SIF. Each partition's `imageFormat` records which (open question 15).
- **Time.** Slurm prints local time (Europe/Warsaw) on the Cyfronet systems and UTC on Sano (spikes S5 and S7). The plugin reads epoch fields from the JSON and converts every time to UTC. No alpha code parses a text time.

### Risks and mitigations

- **A stale profile acts on old facts with confidence.** Centers change policies without notice. Mitigation: each draft fact records its method, source and date (S5's envelope), and the Slurm provider checks the one fact that every reply shows, the JSON version (Design details). Beta adds no probe: the other facts stay as recorded, with their dates, and the conformance run before a partition's beta rows measures again what it covers (open question 7).
- **Start estimates are trusted.** They are advisory. Decisions act on actual starts.
- **The framework's own polling trips login throttles.** Too many parallel logins have tripped a cluster's connection limit. Mitigation: one multiplexed connection per login node and credential, so two providers' credentials never share one; one queue listing per Provider per poll interval, shared by its Allocations; at most four commands at once on a connection. Spike S5 (PR #19) could not establish the login nodes' ssh limits, so a per-platform budget waits for them (open question 17).
- **Local time in scheduler output** gives wrong end times, worst across a daylight-saving change. Spike S5 (PR #19) measured it: Slurm's text output in a login session is in Europe/Warsaw local time, with no zone marker, on Helios and Athena, and in UTC on Sano. Mitigation: the plugin reads epoch times from the JSON and converts every time to UTC; it parses no text time. Tests cross a daylight-saving change.
- **A finished job vanishes from the queue listing.** Helios and Athena purge a finished job from `squeue` about 10 s after it ends (MinJobAge), and Sano after 300 s (spike S5, PR #19). A plugin that polls only `squeue` loses the final state, and a controller that reads the job as missing may submit it again. Mitigation: final state comes from accounting (`sacct`). A job missing from `squeue` is never read as completed or as never submitted; with no accounting record either, its state is unknown until `lostGrace` passes (Design details).
- **"Not listed" has two shapes.** Right after a job ends, Helios answers `squeue --json -j <id>` with an empty `jobs` list and exit 0; once the ID is purged, and on Athena at once, it exits 1 with "Invalid job id specified" (spike S7's capture, `spikes/s7/slurm-json-real.md`). Both mean "ask accounting". Any other non-zero exit is a failed read, never "not listed".
- **The scheduler requeues a job.** Requeue is on by default on all three platforms (`JobRequeue=1`; spike S5, PR #19), so Slurm may run a job's script again under the same job ID. Mitigation: submit with `--no-requeue`, record each platform's default in its profile, and report a requeue that still happens as Failed. HBEP-3 decides identity across executions (open question 13, from spike S4): a requeue fails that Instance, and its replacement is a new Allocation.
- **A job without GPUs on a GPU-only platform.** Athena is meant for GPU jobs only, and its documentation warns that workloads without GPUs can lead to account suspension (spike S5, PR #19). Mitigation: the plugin refuses a submission that requests no GPU on a partition whose profile entry names a GPU model, and refuses a partition that the profile does not list. Athena's profile lists only GPU partitions. Whether an idle GPU Allocation counts is HBEP-7's open question 13.
- **Cancelling in the wrong order starts a follow-on early.** Alpha submits no provider-side dependencies (HBEP-7, open question 3), so there is no dependent to cancel. A plugin that adds them must cancel dependents before their parent.
- **The hold lift has a check-then-act window.** Between reading a job and releasing it, another lifter, or a requeue, can change it. Mitigation: immediately before `scontrol release`, the leader re-reads the marker and the job under a per-job lock, and releases only a user-held job with restart count 0 that has not started and carries no marker (Core operations, `LiftHold`). Known risk: the lock holds within one process only, so a window remains after the re-read: a leader stalls after its re-read; another leader releases the job, and it starts; an administrator requeues it with a hold (the plugin submits `--no-requeue`, so only an administrator's action can requeue it); then the stalled leader resumes and releases that later hold. `scontrol release` names the job, not the hold, so nothing stops it. It needs a stall and a manual requeue with a hold in the same window, so it is rare, and it is accepted for alpha (science-agent decision, 31 Oct 2026, from PR #96's review). This is the one exception to "the hold is lifted exactly once" (HBEP-3, HBEP-7, HBEP-11). Its test is tracked in #93.
- **A per-user QOS limit is shared, and counts held jobs.** Slurm counts a user's pending and running jobs against a QOS's per-user submit limit, and a held job is a pending one (QOS limits). The owner's other projects use the same login, so they share the limit. Mitigation: the lifecycle controller plans within the typed limits, reserving a slot before each creation (HBEP-7, Provisioning), and a refusal for a full submit limit fails nothing: the Allocation waits with reason `SubmitLimitReached` and the attempt is retried with backoff (QOS limits).
- **A refusal that will never pass looks like a full slot.** Slurm ends every policy refusal with one line, for a full submit limit and for a job that breaches a limit on its own, such as a time above the QOS's wall limit; where a center enforces a grant as an association limit, a used-up grant may give it too (QOS limits). Mitigation: the plugin reads the reason name that Slurm prints on the line before. Only the submit-count reasons listed under QOS limits (per user, per account and the group limits) are `SubmitLimitReached`; any other is `SubmissionRejected` with that reason, retried with backoff and shown, never read as a full slot (Operational readiness 5). The plugin also refuses, before any call, a job above any typed per-job or per-user limit.
- **A QOS's own limit may not be the one that applies.** Slurm applies a partition QOS's limit before the job QOS's, unless the job's QOS has `OverPartQOS`, and uses the first that is set (QOS limits). Helios `plgrid-gpu-gh200`'s partition QOS is `plgrid`, which allows 2,000 submitted jobs per user, and `now` has no `OverPartQOS` (issue #94, comment 6557416899). So `now`'s submit limit of 1 does not bind there, while its cap of one GPU per user does, since `plgrid` sets none. Measured on 1 Nov 2026: a second held submission under `now` was accepted while the first was held ([issue #94, comment 6558113194](https://github.com/groundnuty/plgrid-llmlab-hpc-burst/issues/94#issuecomment-6558113194)). Mitigation: the profile types GH200's partition QOS, so the plan applies the same order as Slurm (Platform profile schema). An accepted submission is not a start: a second Allocation under `now` pends while the first runs, holding a place in the shared login's queue (HBEP-7, No-overlap mode).
- **A partly applied operation is reported as failed.** An interrupted multi-job cancel may already have cancelled some jobs. Results are reported per job, never as one status.
- **A submission is accepted but runs as something else,** for example with another partition, time limit or job name, or becomes unschedulable after an in-place change. Mitigation: the plugin reads every job back after it is established and compares it with what it submitted; a submitted job is never edited (Design details).
- **Plugins find their own jobs by scanning.** The newest matching job may belong to someone else. Decided in HBEP-3, from spike S4 (PR #32): every job carries its Allocation's tag in `--job-name`, and jobs are found only by tag.
- **A site rewrites the job name.** A `job_submit` plugin could shorten or change it, and a job then can never be found by tag. Mitigation: the read-back compares the name with the tag; a mismatch refuses the Allocation and cancels the job. A 56-character name is checked on each alpha partition before alpha (Graduation criteria).
- **A failed read looks like absence.** A transport error, a time-out or an unparseable reply says nothing about the job. Mitigation: only reads that succeeded count towards `lostGrace`; a failed read keeps the last known state and raises a condition.
- **A job stuck in `COMPLETING`.** The flag lasts until every node of the job has run its epilog and reported (Core operations, Phases), so a node that never finishes its cleanup keeps the job completing. Its Allocation then keeps its files, its finalizer and its slot (HBEP-7, Provisioning), and its deletion does not complete. Slurm itself sends the kill again to a job still completing after `KillWait` plus twice `MessageTimeout` (`_list_find_job_old`, cited under Phases), but nothing in the framework ends the wait. Accepted for alpha (science-agent ruling, 1 Nov 2026, for #198): the Allocation's `JobCompleting` condition (proposed) shows the state and since when, and an operator acts.
- **A Slurm upgrade changes the JSON.** A new data_parser version renames or moves fields. Mitigation: every reply's `meta.plugin.data_parser`, without its `data_parser/` prefix, must equal the profile's; otherwise the reply is not interpreted and the Provider gets a condition.
- **A workaround outlives its bug, or masks another fault,** for example a raised time-out hiding a hang. Mitigation: each register entry names the symptom it covers and the version range it applies to, and CI fails an entry for a pinned binary whose pins file has reached its fixed-in version while its workaround is still named. An engine entry is retired with an HBEP-15 amendment (open question 6; Known-issues register).
- **Contingencies cost when idle.** Probing a shared managed gateway adds load to it. Mitigation: each contingency's idle cost is stated in the profile, and the alpha managed provider reads the catalog at most once a minute.
- **Flags too coarse for real providers** push provider-specific code into the core. A new flag is an amendment to this HBEP.
- **Account data leaks into a public profile.** Accounts, grants and credentials references are provider settings, never platform-profile fields. Login node names and gateway addresses stay with the credentials (Provider settings).
- **An image build outgrows the RAM disk.** On Helios GH200 the build's tree lives in `$MEMFS`, which counts against the job's memory, and a cold build peaked at 55.39 GiB against one GPU's 122,375 MiB (Submission). An image whose unpacked size grows past one GPU's share fails the start `OUT_OF_MEMORY`, an `AllocationFailed` (Phases). Mitigation: a cold build happens only on a staging-cache miss, the agent reports each build's peak (HBEP-7), and the profile facts record it, so a growing image shows before it fails.
- **Expected performance goes out of date,** so qualification discards good Instances or keeps poor ones. The field records its source and date like any other (open question 7). Alpha holds no expected performance (HBEP-7, open question 12). In beta an entry is keyed on the deployment ID, so a new engine, image or checkpoint matches none; it gates for 90 days from its date; and HBEP-7 suspends an entry that two Allocations in a row fail (Platform profile schema, Expected performance).

### Open questions

1. **Core operations.** **Decided:** for a batch provider, the platform-profile reader, find by tag, observe one job, submit (held in hold mode), lift the hold, cancel, ensure a file, and remove an Allocation's files; for a managed provider, the profile reader and list the catalog (Design details, Core operations). In HBEP-6's host-dialed mode a batch provider also runs relays (9 Nov 2026): a long-lived duplex operation, outside the command interface (Transport). Source: spike S4 (PR #32) for submit, find by tag, lift the hold, cancel and observe; science-agent decision, 30 Oct 2026, for the file operations, which the allocation agent of HBEP-7 needs. **Not needed for alpha:** describe, follow-on, usage, remaining quota, and launching or stopping an Instance as a provider operation (HBEP-7 starts Instances through the allocation agent). **Proposed for beta** (HBEP-10, The release cost; amended 2026-11-15): estimate, a batch provider's read-only start estimate (Core operations, `Estimate`).
2. **Capability flags.** **Decided:** for alpha, the kind fixes the operation set (batch or managed), and the one flag is `holdRelease`. Source: spike S4 (PR #32) and HBEP-11. **Proposed for beta** (HBEP-10, The release cost; amended 2026-11-15): gives start estimates, the flag behind the `estimate` operation. The kind fixes it, as it fixes the operation set: a batch provider has the operation, and a managed provider has none. **Not needed for alpha:** the other candidates: can restart; has a hard end; supports follow-on dependencies; supports node pinning; a hard end that can move later (the controller re-reads it and never plans for it, HBEP-3); can change a running job's account; compute nodes can connect out; compute nodes are reachable in; reports model state; exposes revisions and limits; rewrites requests; requires streaming. Each is added by amendment when a plugin first needs it. **Decided for beta** (amended 2026-11-16): "rewrites requests" is a typed fact of a managed profile, `gateway.rewritesRequests`, not a flag, since no plugin branches on it (Platform profile schema, The remaining groups).
3. **Profile schema.** **Decided:** for alpha, the typed fields in Design details (Platform profile schema), plus an untyped `profile` block that keeps the drafts' `facts` with their envelope. Provider settings are decided (owner decision): account, grant, credentials reference, allowed partitions and labels; and an optional QOS (science-agent decision, 1 Nov 2026; Provider settings). The format of both is decided by HBEP-11: the PlatformProfile and Provider kinds. Source: HBEP-11's list of typed fields; spikes S4 (PR #32), S5 (PR #19) and S1 (issue #18) for the values; science-agent decision, 30 Oct 2026, for the fields the lifecycle controller reads. **Designed for beta** (science-agent design, 16 Nov 2026, with HBEP-7's open question 12): the form and source of expected performance, the typed list `expectedPerformance` (Platform profile schema, Expected performance). **Designed for beta** (science-agent design, 16 Nov 2026; amended 2026-11-16): the remaining field groups (hardware, environment, reachability, version pins, billing and exhaustion, managed-gateway behaviour, references to known issues). Four fields are typed, each for a named reader: `partitions[].billingUnit`, `partitions[].dialHomeModes`, and on a managed profile `gateway.overloadStatus` and `gateway.rewritesRequests`. Every other fact of those groups stays in the untyped block (Platform profile schema, The remaining groups). The LLMLab draft profile is still to come.
4. **Plugin granularity.** **Decided:** one plugin per scheduler type, here Slurm, with one platform profile per platform. The three drafts express every alpha difference between Helios and Athena as data: the JSON version, the GPU model, the GRES form and the time zone. Source: spike S5 (PR #19) and S7's capture; science-agent decision, 30 Oct 2026.
5. **Plugin boundary.** **Decided:** an in-process Go library inside each Provider's controller, a controller-runtime manager of its own (HBEP-11). There is one binary in alpha, so the core's version is the binary's. Source: spike S4 (PR #32), HBEP-11 (Controllers). **Not needed for alpha:** plugins in separate binaries that declare the core version they implement.
6. **Register format.** **Not needed for alpha:** alpha reads no register. The known workarounds for alpha are plain configuration in HBEP-5's front and the ModelDeployment's engine flags. The candidate entry fields stay: identifier, symptom, component and affected versions, fixed-in version, platform scope and stage (HBEP-2 dimensions), fix owner, detection check, workaround configuration, regression test, upstream link. Source: science-agent decision, 30 Oct 2026, within the alpha scope (Notes). **Decided for beta** (science-agent design, 16 Nov 2026; amended 2026-11-16): one file of entries, each with a symptom, a component and its version range, a scope of platforms and partitions, a workaround, one regression test and a source. A CI test reads it, and no controller does (Known-issues register). Of the candidate fields, fix owner, stage and detection check are dropped, since the regression test is the check.
7. **Profile provenance and probes.** **Decided:** for alpha, each fact in the untyped block keeps the drafts' envelope (value, method, source, date), and each typed value is copied from such a fact or is a framework default. The Slurm provider re-checks the JSON version on every reply. Source: spike S5 (PR #19); science-agent decision, 30 Oct 2026. In beta, each `expectedPerformance` entry carries its envelope in typed fields, since the lifecycle controller reads its date (Platform profile schema, Expected performance). **Decided for beta** (science-agent design, 16 Nov 2026; amended 2026-11-16): no new probe.
   - The JSON version is still checked on every reply.
   - The billing figure is the scheduler's own, read per Allocation in the accounting read the plugin already makes, so it needs no probe (HBEP-8, Provider accounting).
   - Every other fact stays as recorded, with its date. A typed value names its fact in a comment, as in alpha, and only `expectedPerformance` types its envelope.
   - The conformance harness, run on a partition before its beta rows, measures again what it covers: the held submit and release, the hard end, the 56-character name, the `sbatch` latency and the data_parser version. Its run is recorded as a fact with its date, as `facts.slurm.plgrid_now_conformance` is.
   - A stale limit already shows as a typed refusal (QOS limits), and a stale `imageFormat` as a failed start.

   A probe process comes after beta, if a stale fact causes a failure that no refusal shows. The spike this question named is not run.
8. **Public and private profiles.** **Decided:** accounts, grants and credentials references are provider settings, never platform-profile data, so they never ship in this repository. The Helios, Athena and Sano profiles ship here, since their drafts are already public (PR #19); the LLMLab profile ships with alpha. Login node names and gateway addresses are kept with the credentials, so no shipped profile holds one. Source: owner decision, 28 Oct 2026, for the provider settings; science-agent decision, 30 Oct 2026, for the rest. **Not needed for alpha:** how a private cluster's profile stays local. Alpha uses only the shipped profiles. A second Athena profile, `profiles/athena-now.yaml`, ships for short test deployments on `plgrid-now`: its minutes-long `routing.maxRequestDuration`, `drainMargin`, `handoverMargin` and `health.startTimeout` give a lead under that partition's 1 h limit, and it isn't for real serving (owner decision, 11 Nov 2026).
9. **Engine-wide data.** **Decided:** for alpha, HBEP-3 keeps the deployment-ID input table in code, with its scheme `v1`. Source: HBEP-3. **Not needed for alpha:** where engine-wide known issues and pins live beyond alpha. **Decided for beta** (amended 2026-11-16): an engine-wide known issue is an entry of the one register with no platform scope (Known-issues register), and pins live where HBEP-15 records them: the engine's in each ModelDeployment, a binary's in its pins file, and the site's software as profile facts.
10. **A managed allocation's hard end.** **Decided:** none for alpha (HBEP-3). A key about to expire, or a rejected key, sets a condition on the Provider (Managed provider in alpha); it is not a lease end. Source: HBEP-3, open question 10.
11. **Overrides.** **Decided:** for alpha, a ModelDeployment overrides two profile values, and may only shorten each. The lease length: an Allocation's time limit is the smallest of the partition's `maxTime`, the wall limit of the QOS it runs under (`maxWall`; QOS limits, amended 2026-11-01) and the ModelDeployment's `leaseLimit` (HBEP-7). A short lease is what makes a real handover testable in hours. The drain window: an Instance's window is `drainWindow`, or the ModelDeployment's `routing.maxRequestDuration` plus `drainMargin` when that is shorter (HBEP-5). A short lease needs a short window to fit, and the front and the lifecycle controller compute it from the same fields. Source: science-agent decision, 30 Oct 2026; HBEP-5, open question 12, for the drain window. **Not needed for alpha:** other overrides.
12. **The partition label.** **Decided:** for alpha, a Provider allows exactly one partition, so its `partition` label holds one value. Source: science-agent decision, 30 Oct 2026. **Decided for beta (owner, 17 Nov 2026, recorded on #679):** one Provider per partition. An account that allows several partitions gets one Provider for each, over the same platform profile, as a second grant does, so each Provider's `partition` label still holds one value and `ReadProfile`'s check is unchanged (Core operations). Before, how a provider that allows several partitions is labelled was open, blocking beta. **Its consequence in host-dialed mode** (revised by its Fable and Gemini Carbon reviews, PR #679): only one Provider per login host runs in that mode, and a second on a held host is refused with `LoginHostInUse` (HBEP-6, Dial-home modes, Capacity). ## Design details

### Two controllers

- **The Provider's controller** is the only component that calls a platform. Each Provider has its own controller-runtime manager, with its own leader `Lease`, `provider-<name>`, in the namespace `hpcburst-system`, which the launcher creates (HBEP-11). It writes under the field manager `hpcburst-provider` (Provider status), in beta an Operation's start estimate included (Core operations, `Estimate`).
- **For a Slurm Provider** that manager runs crossplane-runtime's managed reconciler over the Allocations whose `providerConfigRef` names the Provider. The management policies exclude Update, so a submitted job is never edited. Its external client maps onto the core operations as follows, and HBEP-7's open question 11 gives the full protocol:
  - **Connect:** the profile reader. A failure sets a condition on the Provider and makes no call.
  - **Observe:** find by tag; adopt a job when none is recorded; settle (cancel every held job with the tag except the recorded one, then lift the recorded job's hold once); read the recorded job back; report Lost after `lostGrace`; report a requeue as Failed.
  - **Create:** in ssh dial-home mode, check that the dial-home key files exist (Submission), and otherwise set the Provider condition `DialHomeKeyMissing` and submit nothing; ensure the agent's binary, frpc and the Allocation's files (Submission); claim an attempt by compare-and-swap, submit, record the job ID by compare-and-swap, then settle in the same reconcile.
  - **Delete:** cancel every live job with the tag. The finalizer stays while any job with the tag is live, a completing one included (Core operations, Phases), or an attempt is unresolved. Then write the Allocation's accounting record, `acct-<Allocation UID>`, waiting at most `lostGrace` for the read that gives the final elapsed time, and writing what is known after that, with unknown fields marked unknown (HBEP-8, Provider accounting). Then remove the Allocation's files.
  - **Update:** never.
  - crossplane-runtime's critical-annotation updater is replaced by one that re-applies only crossplane's own keys (spike S4; HBEP-11).
  - The reconciler runs with `managed.WithDeterministicExternalName(true)`, because the tag is a deterministic external name. Without it, a create interrupted before its outcome is recorded stops the reconciler before Observe, and the Allocation stays stuck until a person removes the annotation (S4: `spikes/s4/README.md`; `spikes/s4/cmd/provider-slurm/main.go`).
- **The lifecycle controller** (HBEP-7) creates Allocations with their submission parameters, deletes them, and reads their status. It never calls a provider.
- **The managed Provider's controller** runs the catalog loop under Managed provider in alpha.
- **Events** (beta; amended 2026-11-16; HBEP-8, Events, Allocation events, which names the reasons and their types). A batch Provider's controller raises its Allocation's transitions as typed events regarding the Allocation, through a recorder of `events.k8s.io` beside crossplane-runtime's: the job's submission or adoption, the lifted hold, the start, the hard end an hour away, the end, and each failed, lost, refused or requeued outcome. A planned end takes HBEP-8's beta type `ended`: an end at or after the hard end, while the Allocation's Instance drains, or by a deletion asked for, judged as the lifecycle controller judges an Instance's end. So the controller reads that Instance's phase from its cache, by `spec.allocationRef`, and a deletion that follows a failure raises no end event (HBEP-8, Events, Allocation events, Planned or not). Its other events stay these diagnostics, untyped, through crossplane-runtime's recorder, with their notes as they are. The typed events' notes name no job ID, since they become CloudEvents in HBEP-8's log, which may be exported; the job ID stays in the Allocation's annotation and status (HBEP-11, The Allocation's record). Its identity may create `events.k8s.io` Events, and read Instances, in the Allocations' namespaces.

### Core operations

The interface a provider plugin implements. Every time it returns is in UTC. Every operation reports per-job results. "Unknown" means the plugin cannot tell; it is never read as "none" or "failed".

For a batch provider (Slurm):
- **`ReadProfile(provider) → (profile, settings, error)`.** The platform-profile reader. It reads the Provider, its PlatformProfile and the credentials reference, and validates them:
  - the profile's kind matches the plugin;
  - the Provider allows exactly one partition, and the profile lists it;
  - the Provider's `qos`, and the partition's `qos`, when set, are listed in the profile's `qos` (QOS limits), so the plan knows every limit it names;
  - `jobName.maxLength` is at least 56, and the tag form matches `jobName.pattern` when one is set;
  - `jsonDataParser` is one the plugin knows;
  - `inflightWindow` is set and exceeds the `sbatch` time-out (60 s);
  - in beta, when the partition lists `dialHomeModes` and the launcher's dial-home mode is `ssh` or `host-dialed`, the list holds that mode (Platform profile schema, The remaining groups; amended 2026-11-16);
  - the credentials file, and for ssh the key file it names, are mode 600 and owned by the controller's user (HBEP-11).

  It fails with every invalid field named. Read-only.
- **`FindByTag(tag, since) → (jobs, error)`.** Every job of the calling user whose name is exactly the tag: from the queue listing, and from accounting for any job the listing does not show, starting at `since`. Jobs are sorted by job ID, never taken in output order. Read-only and idempotent. An error means unknown.
- **`Observe(jobID) → (job, found, error)`.** One job: from the queue listing, else from accounting. `found` is false only when both reads succeeded and neither shows the job. Read-only and idempotent.
- **`Submit(request) → (jobID, outcome, error)`.** One `sbatch`, held when `request.hold` is set, which hold mode always sets. The outcome is:
  - Accepted: `sbatch` printed a job ID;
  - Rejected: a definite refusal ("Batch job submission failed:" with a reason that is not transient), or a command that never started;
  - Unknown: a time-out, a signal, a transport error, unparseable output, or a transient reason. Slurm may still have registered the job.

  A Rejected outcome whose reason name is a full submit limit is a limit refusal: the Allocation waits with reason `SubmitLimitReached`, and nothing fails (QOS limits). Not idempotent. It runs only under a claimed attempt (HBEP-7, open question 11), and never retries by itself.
- **`LiftHold(jobID) → error`.** `scontrol release`. Its errors are: not held, an admin hold (reported, never retried), not found, and unknown. Within one process the reconciler calls it at most once per Allocation, guarded by the `hold-lifted` marker and the re-read below; across a leader handover a second call can still come (What remains). The operation itself does not guard.
  - **The re-read before the release** (science-agent ruling, 31 Oct 2026, for #76). Immediately before `scontrol release`, the leader re-reads the Allocation's marker from the API server and the job from Slurm, under a per-job lock in its process. It releases only a job that is held by its user (`JobHeldUser`), has a restart count of 0, has not started, and carries no lift marker. A leader that stalls before its re-read therefore cannot free a requeued job.
  - **What remains** is a known risk (Risks): a leader stalls after its re-read; another leader releases the job, and it starts; an administrator requeues it with a hold (the plugin submits `--no-requeue`, so only an administrator's action can requeue it); then the stalled leader resumes and releases that later hold. `scontrol release` names the job, not the hold, so nothing stops it. It needs a stall and a manual requeue with a hold in the same window, so it is rare, and it is accepted for alpha (science-agent decision, 31 Oct 2026, from PR #96's review). The test is tracked in #93.
- **`Cancel(jobIDs) → results`.** A result per job: cancelled, already ended, or error. Cancelling an ended job reports "already ended", so the operation is idempotent. How each is decided (erratum, 1 Nov 2026, for #199):
  - Cancel first reads each job fresh, from the queue listing, else accounting, never from a listing cached before the call;
  - a live job is cancelled with `scancel <id>` and reports cancelled;
  - an ended job, as the listing or accounting shows it, reports already ended, with no call;
  - a job neither shows reports an error that says not found, with no call, and a read that fails reports an error, with no call.

  The read decides because `scancel`'s exit cannot. The plugin runs `scancel <id>` with no options (`cancelLine` in `internal/slurm/dialect.go`), so `scancel` takes its default path (`src/scancel/scancel.c`, lines 340–341 in both versions, and `src/scancel/opt.c`, lines 125–148) and its default signal, SIGKILL (`scancel.c`, 24.11.5 lines 887–888, 23.11.7 lines 873–874). For a job that has ended (`ESLURM_ALREADY_DONE`) or that Slurm does not know (`ESLURM_INVALID_JOB_ID`), it then prints nothing and clears the error, so it exits 0 (`scancel.c`, [24.11.5, lines 928–941](https://github.com/SchedMD/slurm/blob/slurm-24-11-5-1/src/scancel/scancel.c#L928-L941); [23.11.7, lines 914–927](https://github.com/SchedMD/slurm/blob/slurm-23-11-7-1/src/scancel/scancel.c#L914-L927); `exit(rc)` at lines 124 and 123; accessed 2026-11-01). **A known limit:** a job that ends between the read and the `scancel` reports cancelled.
- **`EnsureFile(path, sha256, mode, content) → error`.** Places one file under the profile's `stagingDir`. It does nothing when a file there already has that SHA-256. Otherwise it writes the content through the ssh connection's standard input to a temporary name, sets the mode, and renames it into place. The content never appears on a command line. Idempotent.
- **`RemoveAllocationFiles(tag) → error`.** Removes the Allocation's directory under `stagingDir`. It takes only a tag and does not look at jobs, so its caller enforces the precondition: it is called only once no job with the tag is live, a completing one included (Phases; Two controllers, Delete). Idempotent.
- **`Estimate(request) → (start or unknown, readTime, error)`** (proposed for beta; HBEP-10, The release cost). Slurm's advisory start for an Allocation's job submitted now: one `sbatch --test-only` with the Allocation's submission parameters (Submission) and the Provider's settings. Slurm then returns an estimate of when the job would start, and submits no job (`sbatch.1`, as HBEP-10 cites it). It runs over the Provider's connection as one command, within Transport's bounds: the four-command budget and its time-outs. Read-only and idempotent: it claims no attempt, writes nothing on the Allocation and lifts no hold. An error, a time-out or an answer it cannot read is unknown, never a time.
  - **Who runs it.** Only the Provider's controller holds the credentials (HBEP-11, Risks), so it runs the estimate when an Operation's plan asks, and writes the answer and its time into the Operation's status under `hpcburst-provider` (HBEP-11, Controllers, Field managers). The plan does not wait for it: an estimate not filled in within HBEP-10's bound reads as unknown (HBEP-10, The release cost).
  - **Advisory.** The answer is shown beside the Provider's observed queue waits, and nothing plans on it (Risks: start estimates are trusted).
  - **Reading its time** (decided per platform by a probe; science-agent decision, 16 Nov 2026, from #661). `sbatch --test-only` answers in text, in the login shell's local zone with no zone marker, and this plugin parses no text time (Notes, Time; L-1.19). So `Estimate` runs it with `SLURM_TIME_FORMAT=%s`, which prints the start as epoch seconds, read with no zone.
    - **Athena, Slurm 23.11.7** (probe of 16 Nov 2026, #661): the epoch form gave the same instant, to the second, as the default form read by hand in the profile's `timeZone`, and the login node's clock agreed with `date -u`. Decided.
    - **Any other platform,** Helios included until its probe runs when GH200 returns: `Estimate` returns unknown, with that reason, until the same probe decides it there.
    - **Where the decision lives** (science-agent ruling on #661's plan, 17 Nov 2026): the PlatformProfile's `startEstimateTime` (proposed, below). It's set to `epoch-seconds` only for a platform whose probe has decided it, citing the probe as its fact. Absent means undecided, and `Estimate` returns unknown, naming that reason. A later platform's probe is recorded by setting it in that profile, in a PR citing the probe, with no amendment. No list of platform names lives in code.
    - **An answer that isn't a whole number of seconds** reads as unknown, never as a time or zero.

A job record holds:
- the job ID, the name, and the state as Slurm lists it (base state and flags);
- the phase;
- whether it is held, and whether the hold is a user or an admin hold;
- the state reason, the restart count, and whether it was requeued;
- the partition, the time limit and the GPU count;
- the submit time, start time, hard end and end time, in UTC;
- its source (queue or accounting) and the data_parser version of the reply.

Phases:
- `Held`: established, with its hold not yet lifted, or an admin hold, which also sets a condition.
- `Pending`, `Running`.
- `Ended`: COMPLETED, TIMEOUT (the lease end) or CANCELLED.
- `Failed`: FAILED, NODE_FAIL, OUT_OF_MEMORY, BOOT_FAIL, PREEMPTED or DEADLINE, or a requeue in any state (reason `Requeued`, kept once seen).
- `Lost`: absent from both sources for longer than `lostGrace`, counting only reads that succeeded. It returns to the real phase if the job reappears.
- **A completing job** (science-agent rulings, 1 Nov 2026, for #198, completed from PR #200's review). Slurm's source and pages are cited at Helios's 24.11.5 and Athena's 23.11.7, accessed 2026-11-01.
  - **Its phase follows the base state, at once,** so failure handling is not delayed. `["CANCELLED","COMPLETING"]`, `["TIMEOUT","COMPLETING"]` (the lease end) and `["COMPLETED","COMPLETING"]` are `Ended`; `["FAILED","COMPLETING"]` is `Failed`. The queue listing's `job_state` is a list, the base state plus flags, and a job is completing while its list carries `COMPLETING`, whatever the base state. The base state is usually terminal. A requeued job is `PENDING` with the flag while its nodes clean up (`_set_requeued_job_pending_completing` in `src/slurmctld/job_mgr.c`: [24.11.5, lines 2415–2424](https://github.com/SchedMD/slurm/blob/slurm-24-11-5-1/src/slurmctld/job_mgr.c#L2415-L2424); [23.11.7, lines 4111–4120](https://github.com/SchedMD/slurm/blob/slurm-23-11-7-1/src/slurmctld/job_mgr.c#L4111-L4120)). Such a job is `Failed` by the requeue rule above: its `restart_cnt` is above 0, a field of the queue listing in both data_parser versions (v0.0.40's job fields, `src/plugins/data_parser/v0.0.40/parsers.c`: [23.11.7, line 7377](https://github.com/SchedMD/slurm/blob/slurm-23-11-7-1/src/plugins/data_parser/v0.0.40/parsers.c#L7377)).
  - **It is live for four rules until the flag clears,** whatever its phase:
    - `RemoveAllocationFiles` is not called (Two controllers, Delete);
    - the Allocation's deletion finalizer stays (HBEP-7, open question 11, Deletion; HBEP-11);
    - HBEP-7's per-Provider slot count counts the Allocation (HBEP-7, Provisioning, Per-user limits);
    - the `acct-` record is written only after the flag has cleared, from the final state (HBEP-8, Provider accounting).

    This is stricter than Slurm, on purpose. Slurm frees the job's submit count and its per-user limits when it sets the flag: `job_completion_logger` calls `acct_policy_remove_job_submit` (`src/slurmctld/job_mgr.c`: [24.11.5, line 16583](https://github.com/SchedMD/slurm/blob/slurm-24-11-5-1/src/slurmctld/job_mgr.c#L16583); [23.11.7, line 17794](https://github.com/SchedMD/slurm/blob/slurm-23-11-7-1/src/slurmctld/job_mgr.c#L17794)), and `deallocate_nodes` calls `acct_policy_job_fini` (`src/slurmctld/node_scheduler.c`: [24.11.5, line 336](https://github.com/SchedMD/slurm/blob/slurm-24-11-5-1/src/slurmctld/node_scheduler.c#L336); [23.11.7, line 332](https://github.com/SchedMD/slurm/blob/slurm-23-11-7-1/src/slurmctld/node_scheduler.c#L332)). It frees each node once that node's epilog has completed (`make_node_idle`, below). The framework keeps one rule for when a job is live, at the cost of the seconds the flag lasts.
  - **The status.** `status.atProvider.jobCompleting` (proposed) is true while the recorded job carries the flag, and, on an Allocation being deleted, while any other job with its tag, such as a cancelled duplicate, still carries it, since the deletion finalizer waits for every tagged job (HBEP-7, open question 11, Deletion). The plugin writes it in the same status write as the phase, so the lifecycle controller never sees `Ended` without it. The Allocation's condition `JobCompleting` (proposed) is True while the flag lasts. Its message names the state and since when, and for another tagged job also which job blocks and why; the time is the listing's `end_time`, which the controller sets at termination.
  - **When the flag clears, observably.** A job is no longer completing once a successful queue listing shows it without the flag, or does not list it. In the second case the plugin reads it from accounting, which shows the base state alone. No other accounting read clears the flag, neither the read of allocated CPUs and GPUs once per execution nor `FindByTag`'s accounting half: in S7's poll `sacct` already said FAILED while the listing still showed `COMPLETING`. A failed read keeps the last evidence, the flag included. `Lost` is unaffected, since a completing job is always listed. Three facts make this hold:

### Transport

- **One OpenSSH master connection per login node and credential,** shared by every command of that Provider (`ControlMaster`, `ControlPersist`, and a `ControlPath` private to the Provider). `BatchMode` is on. The master carries no port forward and no other session, because tunnels on a shared master broke kill-by-PID (L-7.3).
- **Where the login node is, and as whom,** is in the ssh client configuration that the Provider's credentials reference names (Provider settings). It is never in the profile, the API or a log.
- **Commands are fixed argument templates.** Every value placed in one (tag, partition, account, QOS, time limit, path) is first checked against a safe pattern of letters, digits and `._:=,/-`. A value that fails is refused before any call. The remote command runs in the login node's non-interactive shell, as S5 measured it.
- **Paths are resolved once per connection.** After each new master connection, the plugin reads `HOME` on the login node with `printenv HOME`, and, when `stagingDir` starts with an environment variable, that variable with `printenv <VAR>`. Each result must be an absolute path that matches the safe pattern. An unset or empty variable, or a result that fails the check, sets the Provider condition `PathUnresolved`, and no call that needs the path is made. Commands, the bootstrap and `agent.json` hold only the resolved absolute paths, never a variable or `~`. The one exception is a partition's `tmpDir` variable, which exists only inside the job, so the bootstrap expands it there (Submission).
- **Time-outs:** 60 s for `sbatch`, 30 s for every other command. A time-out on `sbatch` is Unknown; on a read it is an error, so the state is unknown.
- **Concurrency:** at most four commands at once on one connection (a code default; open question 17).
- **Relays, in HBEP-6's host-dialed mode** (9 Nov 2026), aren't commands. In alpha the batch Provider's controller runs them; in beta the relay keeper does, on the controller's desired set (HBEP-6, The relay keeper), and the keeper owns the per-login-host count. They don't count against the four-command budget, and they have no 30 s time-out.
  - **The connection:** each relay is its own ssh process, never on the master. It uses the Provider's private `-F` configuration and hardening, plus `ControlMaster=no`, `ControlPath=none` and `-T`, because OpenSSH reuses a master even under `ControlMaster=no` unless `ControlPath` is `none`.
  - **The command:** `srun -u --overlap --jobid=<job> --ntasks=1 --chdir=<Allocation directory> <the job's agent binary> relay ...` (HBEP-6, Transport). The host-dialed conformance check accepts this form.
  - **Setup is bounded:** its preamble line must arrive within 30 s.
  - **Identity:** each relay is tracked by its PID and stopped by it.
  - **A job ended or not listed** ends the relay (HBEP-6, Dial-home modes).
  - **The check before each start** reads the Provider's one queue listing per poll interval, never a listing of its own. In beta the relay keeper starts a relay only under the controller's unexpired desired set, which carries that listing's age and its validity (HBEP-6, The relay keeper).
  - **Capacity:** in host-dialed mode a Provider has at most 2 Allocations, pending or running, a submit limit that the planner counts (`SubmitLimitReached`). Only one Provider per login host runs in this mode. The Provider's controller refuses a second, with `Ready` False and reason `LoginHostInUse` (HBEP-6).
- **Reconnects:** when the master fails, the plugin closes it and reconnects with exponential backoff from 1 s to 1 min. Calls in flight report transport errors.
- **Poll rate:** the queue listing is read once per poll interval for the whole Provider (`squeue --me --json`) and cached. Every Allocation's Observe reads that cache, after a forced refresh after any write. Accounting is read only for jobs the listing does not show, and once for each execution of a recorded job after it is first seen started, for its allocated CPUs and GPUs (HBEP-8, Provider accounting). The interval is 30 s, and 5 s while any of the Provider's attempts is unresolved or a job is held.

### The Slurm dialect

- **Submission:** `sbatch --parsable --job-name=<tag> --no-requeue [--hold] --partition=<p> --account=<a> [--qos=<qos>] --time=<limit> --nodes=1 --gres=gpu:<n> --cpus-per-task=<c> --mem=<m> [--constraint=<feature>] --output=<dir>/job.out --error=<dir>/job.err --wrap=<bootstrap>`.
  - `--parsable` prints `<jobid>[;<cluster>]`.
  - `--constraint=<feature>` is added when the partition sets `tmpDirFeature`, the node feature its `tmpDir` needs (science-agent ruling, 1 Nov 2026). Like every value in a command, the feature is checked against the safe pattern first (Transport).
  - **The QOS by GPU count** (proposed, beta; the science agent's design for Sano, #735, 18 Nov 2026). A partition may set `qosByGpus`, an ordered list of `{gpus, qos}`: the plugin adds `--qos=` the first entry's QOS whose `gpus` is at least the Allocation's GPU count, and refuses a count above the last entry before any call. Sano's `gpu` partition takes its QOS this way (`gpu1`, `gpu2`, `gpu4`, `gpu8` for up to 1, 2, 4 and 8 GPUs; #735's probe 3). A Provider whose partition sets `qosByGpus` doesn't set `qos` in its settings. `ReadProfile` refuses both together, since it reads the Provider and its profile; neither object's own validation can see the other. That's the QOS's one source: a profile edit of qosByGpus recounts live Allocations under the new map; Slurm still enforces each job's QOS at submission.
  - `--qos=<qos>` is added when the Provider's settings set `qos` (proposed; Provider settings). Like every value in a command, it is checked against the safe pattern first (Transport). `--qos` requests "a quality of service for the job", and users are limited to their association's QOS list where `AccountingStorageEnforce` includes `qos` (sbatch, `-q, --qos`: [24.11.5](https://slurm.schedmd.com/archive/slurm-24.11.5/sbatch.html), [23.11.7](https://slurm.schedmd.com/archive/slurm-23.11.7/sbatch.html)); Helios sets `AccountingStorageEnforce=associations,limits,qos` (`facts.slurm.other_config`). With no `qos`, no flag is sent, and the job gets "the QOS the association will use by default" (sacctmgr, `DefaultQOS`: [24.11.5](https://slurm.schedmd.com/archive/slurm-24.11.5/sacctmgr.html), [23.11.7](https://slurm.schedmd.com/archive/slurm-23.11.7/sacctmgr.html)): `normal` for the measured Helios association (issue #94, comment 6557416899).
  - GPUs are requested untyped, `--gres=gpu:<n>`, because Helios's GH200 GRES carries no type. Sano refused the typed form on 30 Oct 2026 (spike S5, PR #19), and accepted it on 18 Nov 2026 (#735's probe 3, `--test-only`); untyped works on both, so it stays.
  - The account comes from the Provider's settings. `<dir>` is the Allocation's directory under `stagingDir`.
- **The queue listing:** `squeue --me --json`, and `squeue --me --json --jobs=<id>` for one job.
  - Results are filtered by exact name or ID on our side, since `squeue --json` does not promise to apply every filter (S4), and sorted by job ID.
  - "Not listed" is an empty `jobs` list with exit 0, or exit 1 with "Invalid job id specified" (S7's capture). Any other failure is an error.
- **Accounting:** `sacct --json -X -D --name=<tag> -S now-<seconds> -E now`, and `sacct --json -X -D -j <id>` for one job.
  - `-S` is always given, as a relative time. Without it `sacct` starts at midnight, and the relative form avoids the login session's time zone (S4).
  - `-D` keeps earlier executions, which show a requeue.
  - `<seconds>` reaches back to the Allocation's creation plus one hour.
- **JSON fields,** per data_parser version. The v0.0.42 table is checked against S7's real captures on Helios. The v0.0.40 table follows Slurm's source, as S4's fake does; Athena's real v0.0.40 documents were not kept, so it is checked there before alpha (Graduation criteria).
  - **queue listing:** `job_id`, `name`, `job_state` (a list: base state plus flags), `state_reason`, `hold`, `priority`, `restart_cnt`, `partition`, `time_limit`, `tres_req_str`, and `submit_time`, `start_time` and `end_time` as `{set, infinite, number}` triples in epoch seconds;
  - **accounting:** `job_id`, `name`, `state.current` (a list) and `state.reason`, and `time.submission`, `time.start` and `time.end` as epoch integers; for accounting (HBEP-8), `time.elapsed` in seconds and `tres.allocated`, of which the entry of type `cpu` and the entry of type `gres` named `gpu`, and in beta the entry of type `billing` (amended 2026-11-16), from every record `-D` returns. `restart_cnt` exists only in v0.0.42; on v0.0.40 an earlier execution shows as a record with the `REQUEUED` state.
  - **Allocated time** (HBEP-8, Provider accounting). The Allocation's `status.atProvider.accounting` (proposed names) holds `allocatedCPUs` and `allocatedGPUs`, from the accounting read made once after the job is first seen started, in beta `allocatedBilling` from the same read (HBEP-8, Provider accounting, Billing), and `elapsedSeconds` and `readTime`. While the job runs, elapsed time runs from the scheduler's start time; once it has ended, it is the queue listing's `end_time` minus `start_time` when the final state came from there, else accounting's `time.elapsed`. A requeued job's hours are unknown (HBEP-8). A pending Allocation has none: unknown. The plugin makes one accounting read per execution, after it is first seen started, retried on failure, and no extra read at delete. After the tag lookup succeeds and shows no live job, a completing one counting as live (Core operations, Phases), a final read that persists in failing is bounded by `lostGrace`, like a missing one; a failed tag lookup keeps the finalizer (Delete). The numbers are allocated, not billed.
  - Each reply's `meta.plugin.data_parser`, after its `data_parser/` prefix is stripped, must equal the profile's `jsonDataParser`. Helios's real replies carry `data_parser/v0.0.42` (`spikes/s7/slurm-json-real.md`), which matches a profile value of `v0.0.42`. Otherwise the reply is not interpreted, the read is unknown, and the Provider gets the condition `DialectMismatch`.
- **Held:** `hold` true, or a set `priority` of 0, or a `state_reason` that starts with `JobHeld`. `JobHeldUser` is a user hold, which the job's user may lift. `JobHeldAdmin` is an admin hold.
- **Requeue:** `restart_cnt` above 0, or a `REQUEUED` record in accounting.
- **Times:** every epoch value is converted to UTC.
  - While a job is RUNNING, the queue listing's `end_time` is its projected end, start plus the time limit (S7's capture). That is the hard end, re-read on every observe, so a center's extension shows up without being planned for (HBEP-3).
  - For a pending job, `start_time` is an estimate, recorded as advisory and never planned on.
  - The profile's `timeZone` is used only to print diagnostics.
- **Read-back:** the job's settings (partition, time limit and GPU count) are compared with the request on the first observe after the job is established, and only then. Its name is compared with the tag on every observe (science-agent decision, 31 Oct 2026).
  - A name that differs refuses the Allocation, with phase `Refused` and reason `JobRenamed`, and cancels the job. Because the name is checked on every observe, a cancel that failed is retried.
  - A settings difference sets the condition `SubmittedAsOther`, with reason `ReadBackMismatch`, and the lifecycle controller replaces the Allocation (HBEP-7).
  - A later change of settings is not a mismatch. An administrator's extension of the time limit shows as a later hard end, re-read on every observe (Times), and is never flagged.

### Submission

- **The Allocation's submission parameters,** immutable (HBEP-11): `partition`, `timeLimit`, `gpus`, `cpusPerTask`, `memory`, `nodes` (1 in alpha) and `agentDigest`, the SHA-256 of the allocation agent's binary for the partition's `cpuArch` (HBEP-7). The lifecycle controller sets them; the plugin adds the account, the tag and the fixed options. S4's `account` and `wrap` are not parameters: the account comes from the Provider's settings, and the batch script is the fixed bootstrap.
- **GPU sizing.** In alpha the lifecycle controller sets `gpus` to the tensor-parallel size times the pipeline-parallel size, and refuses a `data-parallel-size` above 1 with `Degraded` reason `SpecUnsupported` on the ModelDeployment, because the framework runs its workers itself (HBEP-7). In beta, `gpus` is `spec.workersPerInstance` × TP × PP, on one node (HBEP-7, Several workers).
  - **The most GPUs an Allocation may ask for** is the smaller of `gpusPerNode`, the node's hardware, and the QOS's `maxGpusPerUser` when set (QOS limits; science-agent decision, 1 Nov 2026). Where the partition sets `qosByGpus`, the QOS depends on the count, so the bound is the smaller of `gpusPerNode` and the last entry's `gpus`. In every case, the effective `maxGpusPerJob` and `maxGpusPerUser` (Which limit applies, the partition QOS's before the job QOS's unless `OverPartQOS`) are then checked, and a count above either is refused, never capped, with `SpecUnsupported` when no allowed Provider fits. `gpusPerNode` stays the hardware fact: 8 on Athena's `plgrid-now`, whose nodes are `gpu:a100:8`, under a QOS that allows one GPU per user. A larger count is refused, never capped. The count is the engine's tensor-parallel size times its pipeline-parallel size, which fewer GPUs cannot run, and under `DenyOnLimit` Slurm would refuse it at submission anyway (QOS limits).
  - CPUs and memory still follow the GPUs: `gpus` times `cpusPerGpu` and `memPerGpu`.
  - **Never above one GPU's share** (beta; the science agent's decision, 16 Nov 2026; amended 2026-11-16). A partition's `cpusPerGpu` and `memPerGpu` never exceed its per-GPU share as the scheduler counts it, the inverse of its billing weights. Under the maximum rule the larger share sets the billing count (HBEP-8, Provider accounting, Billing), and with the documented rounding up an over-request bills a one-GPU job as two GPU-hours an hour. Helios GH200's shipped `memPerGpu`, 122,375 MiB, is within one GPU's share by the scheduler's own weights, 122,400 MiB, so it is not lowered. It is unverified against the center's documented share of 120 GB. GH200's first job's accounting `billing` count, equal to its GPUs, shows only that the recorded weights and the maximum rule still hold, not the center's rounding. Whether the documented share bills a one-GPU job as one GPU-hour an hour or two is settled only by the person-run comparison, which includes a GH200 window (HBEP-8, Provider accounting, Billing). Athena's 16 CPUs and 128,000 MiB are within its weights' share, 16 CPUs and 128 GiB.
  - When set, `maxCpusPerUser` and `maxMemPerUser` must be positive; admission refuses 0, which would size a job with no CPU or `--mem=0`, the whole node. An effective `maxSubmitPerUser` or `maxGpusPerUser` of 0 is valid and means the Provider cannot host the Instance: no Allocation is created, and the deployment's reason names the limit. The lifecycle controller caps each at the effective `maxCpusPerJob`, `maxMemPerJob`, `maxCpusPerUser` and `maxMemPerUser` (Which limit applies, so a partition QOS's caps count where no job QOS is set) when set, before it creates the Allocation, since they are an allotment in proportion, not what the engine needs (HBEP-7, Provisioning). Both alpha QOSes allow exactly one GPU's share: Helios `now` 72 CPUs and 122,400 MiB against GH200's 72 and 122,375 MiB, and Athena `plgrid-now` 16 CPUs and 125 GiB against A100's 16 and 128,000 MiB. So neither cap changes an alpha request.
- **Refused before any call:**
  - a partition that the Provider does not allow or the profile does not list;
  - no GPU on a partition whose `gpuModel` is not `none`;
  - more GPUs than the smaller of `gpusPerNode` and the QOS's `maxGpusPerUser`;
  - more CPUs or memory than the QOS's `maxCpusPerUser` or `maxMemPerUser`;
  - more GPUs, CPUs or memory in one job than the QOS's `maxGpusPerJob`, `maxCpusPerJob` or `maxMemPerJob` (proposed; Sano's caps are per job, `MaxTRES`: #735's probe 3);
  - a time limit above the smaller of `maxTime` and the QOS's `maxWall`;
  - an effective `maxSubmitPerUser` of 0, which no job can fit (QOS limits);
  - a memory request of 0, because Slurm reads `--mem=0` as the whole node (science-agent decision, 31 Oct 2026).
- **Files first.** Before claiming an attempt, the plugin ensures four files under `stagingDir`:
  - the agent's binary, at `agent/<digest>/hb-agent`, copied from the control-plane host's build of that digest;
  - frpc, the tunnel's client (HBEP-6), at `frpc/<digest>/frpc`, for the partition's `cpuArch`, copied from the control-plane host's copy, whose checksum `internal/launcher/frp-pins.txt` pins (HBEP-15);
  - the Allocation's credential, at `alloc/<tag>/credential`, mode 600;
  - the launcher's dial-home certificate, at `alloc/<tag>/dial-home.crt`. It is public; frpc verifies the front with it (HBEP-6, HBEP-11).

  The credential is the token the lifecycle controller generated for the Allocation (HBEP-7). It never appears in the batch script, on a command line or in a log (HBEP-6).

  A fifth file, `alloc/<tag>/agent.json`, mode 600, tells the agent where the control-plane host is, which dial-home mode it uses (direct, ssh or host-dialed; in host-dialed mode there's no `endpoint` and no `ssh`) and the pin of the agent endpoint's certificate, from the launcher's configuration (HBEP-11), and the resolved staging and dial-home directories (Transport). It also carries frpc's digest, in ssh mode the dial-home listener's loopback port next to the agent endpoint's (HBEP-6; field names are the code agent's), and the Hub's base URL from the launcher's configuration (HBEP-7, The allocation agent). The agent stages from that URL, and reads `HF_ENDPOINT` from its own environment only when the field is absent, since a job submitted over ssh does not inherit the control-plane host's environment. It names a private address, so it is never in the repository.
- **The dial-home key** for the ssh mode is not staged. The operator generates the restricted key and places the pinned host key on the platform once, in `~/.hpcburst/dial-home/`, mode 600 (HBEP-7). They live outside `stagingDir`, on storage that is not purged, because Helios purges scratch files older than 30 days (spike S5, PR #19). The plugin names that directory by the resolved home directory, never by `~` (Transport). Create checks that both files exist there before any submission, and sets `DialHomeKeyMissing` when they do not (Two controllers). Whether a compute node can use them shows at the first registration: a failure there sets `DialHomeUnreachable`, the lifecycle controller's condition (open question 16).
- **The bootstrap** is the `--wrap` command. When the partition sets `tmpDir`, it sets `TMPDIR` from it first (science-agent ruling, 1 Nov 2026). It checks the binary's SHA-256 against the digest, then runs it with the Allocation's directory as its only argument. Nothing else runs in the batch script.
  - **Expanded in the job.** A `tmpDir` such as `$MEMFS` names a job variable. On Helios such variables are unset on the login node (`facts.storage.node_local.job_variables_on_login_node`), so the plugin cannot resolve it there as it resolves `stagingDir` (Transport). The plugin checks the form when it reads the profile: the variable's name, and the rest of the path against the safe pattern. The bootstrap expands the variable inside the job. If it is unset or empty there, or the result is not an absolute path, the bootstrap exits with a non-zero code before the agent starts, and never falls back to the job's own `TMPDIR`. Slurm then records the job `FAILED`, the Allocation's phase is `Failed`, and its Instance ends with `AllocationFailed`; three such Allocations in a row raise `RestartLoop` and pause the class (HBEP-7, Reconcile loop step 5, and Health and restarts). An exit code of 0 would read as `COMPLETED`, an Allocation that ended early. The constraint is what makes the variable set.
  - **A node-local `tmpDir` needs its node feature** (science-agent ruling, 1 Nov 2026). Helios documents `$SCRATCH_LOCAL` as a per-node scratch volume for a job that requests `-C localfs`, lost when the job ends (`facts.storage.node_local.localfs`), and `$MEMFS` as a RAM disk for a job that requests `-C memfs`, whose contents count against the job's `--mem` (`facts.storage.node_local.memfs`). A feature that a node lists may still be refused at submission: on 1 Nov 2026 Helios refused `-C localfs` on every partition ("The feature 'localfs' is not supported"), although `sinfo` lists `memfs,localfs` on every node, and in a job without it `$SCRATCH_LOCAL` is unset. So a `tmpDirFeature` is set only after a submission with it has been accepted on that partition, never from `sinfo` alone. On Helios `plgrid-gpu-gh200` the job's directory is `$MEMFS` with `memfs`: a per-job tmpfs the size of the node's memory, with millions of inodes, freed when the job ends (measured 1 Nov 2026, #125). A cold image build peaked at 55.39 GiB in `$MEMFS` (the agent's `buildPeakTmpBytes`), about 6.7 times the 8.8 GB SIF it produced, and Slurm's MaxRSS for the job, 72.9 GB, agrees independently (second real GH200 run, 1 Nov 2026, issue #94). That fits in one GPU's `memPerGpu`, 122,375 MiB, because the build ends and its tree is removed before the engine loads its weights (HBEP-7, The allocation agent): the two never hold the RAM disk at once. So `memPerGpu` is unchanged, the memory request stays `gpus` times `memPerGpu` (Submission, GPU sizing), and no code adds a size. The agent removes the build's temporary tree once the image is in the staging cache, and reports the build's peak use of `tmpDir` (HBEP-7). The profile facts record the measured peak. No check runs before a build: on a RAM disk the job's memory, not the filesystem's free space, is the limit, so a build that exceeds it ends the job `OUT_OF_MEMORY`, an `AllocationFailed` (Phases). With no `tmpDir`, the job keeps its own `TMPDIR` and gets no constraint.

### QOS limits

Science-agent decisions of 1 Nov 2026, from the code agent's read-only measurement of Helios GH200 ([issue #94, comment 6557416899](https://github.com/groundnuty/plgrid-llmlab-hpc-burst/issues/94#issuecomment-6557416899)). The names `qos`, `maxWall`, `maxSubmitPerUser`, `maxGpusPerUser`, `maxCpusPerUser`, `maxMemPerUser` and `SubmitLimitReached` are proposed. Helios runs Slurm 24.11.5 and Athena 23.11.7 (`facts.slurm`), so each fact below cites both versions' pages, accessed 2026-11-01.

- **Which QOS.** A job runs under its Provider's `qos`; where its partition sets `qosByGpus`, under the QOS that list chooses for the Allocation's GPU count; or under the association's default when neither is set (The Slurm dialect). That is **the job's QOS** in the rest of this section, for the plan and at submission alike: the plan resolves it from the GPU count before it sizes the Allocation, so a `gpuN` QOS's 3-day `maxWall` bounds the time limit, not Sano's 7-day partition. Its partition may have a QOS of its own, which Slurm applies to every job on that partition. Athena's `plgrid-now` partition has the QOS `plgrid-now`; Helios `plgrid-gpu-gh200` has `plgrid` (`facts.partitions`). The profile types both (`partitions[].qos`).
- **Which limit applies.** For each limit, the plan takes the partition QOS's value if it sets one, unless the job's QOS has `OverPartQOS`; else the job's QOS's. With no job QOS known, only the partition QOS's typed limits apply, since the profile does not know the association's default QOS; Slurm still enforces the default's limits, and its refusals read by their reason names. With `OverPartQOS` on the job's QOS, the order is reversed. That is Slurm's order: the partition QOS comes before the job's QOS, reversible only by the QOS flag `OverPartQOS`, and "the point in this list where the limit is first defined will be used" (resource_limits, Hierarchy: [24.11.5](https://slurm.schedmd.com/archive/slurm-24.11.5/resource_limits.html), [23.11.7](https://slurm.schedmd.com/archive/slurm-23.11.7/resource_limits.html)). Slurm's source agrees: the partition QOS comes first unless the job's QOS carries `OverPartQOS` (`src/slurmctld/acct_policy.c`, [24.11.5, lines 5252–5265](https://github.com/SchedMD/slurm/blob/slurm-24-11-5-1/src/slurmctld/acct_policy.c#L5252-L5265)), and each limit is taken from the first QOS that sets it (lines 2055–2062). The profile records the flag as `qos[].overPartQos`; no QOS the alpha profiles type has it. A limit that neither sets is no limit, as far as the plan knows. On Helios `plgrid-gpu-gh200` under `now`, the limits that apply are `plgrid`'s 2,000 submitted jobs and `now`'s 12 h and one GPU's share; the measured second submission agrees (Risks).
- **Limits counted per QOS** (#745). Where one Provider's jobs run under several QOSes (`qosByGpus`), a QOS's per-user limits (`maxSubmitPerUser`, `maxGpusPerUser`, `maxCpusPerUser`, `maxMemPerUser`) count only the Allocations under that QOS, with each reserved slot, hedge member and extra charged to the QOS it would submit under. The partition QOS's limits and the host-dialed ceiling of two Allocations still count every Allocation on the Provider (HBEP-7, Per-user limits, reads these counts).
- **The time limit** is the smallest of the partition's `maxTime`, that QOS's `maxWall` and the ModelDeployment's `leaseLimit` (open question 11; HBEP-7). A wall limit never lifts the partition's: QOS and association limits on time "can't go over the limit imposed at Partition level" (the same pages, Hierarchy). On Helios `plgrid-gpu-gh200` under `now` the limit is 12 h, not the partition's 48 h.
- **The submit limit,** `maxSubmitPerUser`, is the QOS's `MaxSubmitJobsPerUser`: "Maximum number of jobs pending or running state at any time per user" (sacctmgr, SPECIFICATIONS FOR QOS: [24.11.5](https://slurm.schedmd.com/archive/slurm-24.11.5/sacctmgr.html), [23.11.7](https://slurm.schedmd.com/archive/slurm-23.11.7/sacctmgr.html)). A held job is a pending job. `--hold` submits a job "in a held state (priority of zero)" (sbatch: [24.11.5](https://slurm.schedmd.com/archive/slurm-24.11.5/sbatch.html), [23.11.7](https://slurm.schedmd.com/archive/slurm-23.11.7/sbatch.html)). squeue has no held state, only `PD PENDING`, and `JobHeldUser` is a reason: "The job is held by the user" (squeue: [24.11.5](https://slurm.schedmd.com/archive/slurm-24.11.5/squeue.html), [23.11.7](https://slurm.schedmd.com/archive/slurm-23.11.7/squeue.html)). So the held submit of hold mode takes a slot from `sbatch` on. Every job of the login counts, the owner's other projects' included. The lifecycle controller plans within the limit (HBEP-7, Provisioning).
- **The per-user caps,** `maxGpusPerUser`, `maxCpusPerUser` and `maxMemPerUser`, are the GPU, CPU and memory entries of the QOS's `MaxTRESPerUser`. They bound the sum over the user's running jobs. A job that fits alone but not beside the user's others pends, with a reason such as `QOSMaxGRESPerUser`: "The request exceeds the maximum number of a GRES each user is allowed to use for the requested QOS" (job_reason_codes, [24.11.5](https://slurm.schedmd.com/archive/slurm-24.11.5/job_reason_codes.html); in 23.11.7 the list is on [resource_limits](https://slurm.schedmd.com/archive/slurm-23.11.7/resource_limits.html)).
- **`DenyOnLimit`.** With this flag, "jobs using this QOS will be rejected at submission time if they do not conform to the QOS 'Max' limits as stand-alone jobs". A job that breaches them only beside other jobs is not rejected; it pends (qos, Other QOS Options: [24.11.5](https://slurm.schedmd.com/archive/slurm-24.11.5/qos.html), [23.11.7](https://slurm.schedmd.com/archive/slurm-23.11.7/qos.html)). A full submit limit refuses a submission with or without the flag, since it bounds the jobs a user "can have running and pending" (resource_limits, QOS-specific limits, `MaxSubmitJobsPerUser`, same pages). The pages do not say so outright; Slurm's source checks the submit limit at submission with no condition on the flag (`src/slurmctld/acct_policy.c`, [24.11.5, lines 2055–2075](https://github.com/SchedMD/slurm/blob/slurm-24-11-5-1/src/slurmctld/acct_policy.c#L2055-L2075); [23.11.7, lines 1877–1897](https://github.com/SchedMD/slurm/blob/slurm-23-11-7-1/src/slurmctld/acct_policy.c#L1877-L1897)), and takes it from the first QOS that sets it, as the Hierarchy says. `now` and `plgrid-now` both have `DenyOnLimit`.
- **A limit refusal.** Slurm's refusal is two lines on `sbatch`'s standard error, the reason name first. For a full submit limit under a QOS they are `sbatch: error: QOSMaxSubmitJobPerUserLimit`, then `sbatch: error: Batch job submission failed: Job violates accounting/QOS policy (job submit limit, user's size and/or time limits)`. The documentation prints neither line; Slurm's source gives both:
  - at submission, any failure of the accounting-policy check sets the one error `ESLURM_ACCOUNTING_POLICY`, and the reason's name as the error's message (`src/slurmctld/job_mgr.c`, [24.11.5, lines 7326–7339](https://github.com/SchedMD/slurm/blob/slurm-24-11-5-1/src/slurmctld/job_mgr.c#L7326-L7339), the name at line 7333; [23.11.7, lines 8820–8832](https://github.com/SchedMD/slurm/blob/slurm-23-11-7-1/src/slurmctld/job_mgr.c#L8820-L8832), the name at line 8826). So the second line is the same for a full slot and for a job that breaches a limit on its own;
  - the controller sends the message with the error (`src/slurmctld/proc_req.c`, [24.11.5, line 3666](https://github.com/SchedMD/slurm/blob/slurm-24-11-5-1/src/slurmctld/proc_req.c#L3666)), and the client prints it as an error before `sbatch`'s own line (`src/common/slurm_protocol_pack.c`, [24.11.5, lines 8143–8156](https://github.com/SchedMD/slurm/blob/slurm-24-11-5-1/src/common/slurm_protocol_pack.c#L8143-L8156); [23.11.7, lines 7496–7506](https://github.com/SchedMD/slurm/blob/slurm-23-11-7-1/src/common/slurm_protocol_pack.c#L7496-L7506));
  - the names are Slurm's job reason strings: `QOSMaxSubmitJobPerUserLimit` (`src/common/job_state_reason.c`, [24.11.5, line 246](https://github.com/SchedMD/slurm/blob/slurm-24-11-5-1/src/common/job_state_reason.c#L246); `src/common/slurm_protocol_defs.c`, [23.11.7, line 2360](https://github.com/SchedMD/slurm/blob/slurm-23-11-7-1/src/common/slurm_protocol_defs.c#L2360)), `AssocMaxSubmitJobLimit` (24.11.5 line 306; 23.11.7 line 2390) and `MaxSubmitJobsPerAccount` (24.11.5 line 720; 23.11.7 line 2605), each documented as a pending reason (job_reason_codes, [24.11.5](https://slurm.schedmd.com/archive/slurm-24.11.5/job_reason_codes.html); [23.11.7 resource_limits](https://slurm.schedmd.com/archive/slurm-23.11.7/resource_limits.html));
  - `sbatch` prints the second line after "Batch job submission failed:", from Slurm's error table (`src/sbatch/sbatch.c`, [24.11.5, line 305](https://github.com/SchedMD/slurm/blob/slurm-24-11-5-1/src/sbatch/sbatch.c#L305); `src/common/slurm_errno.c`, [24.11.5, lines 238–240](https://github.com/SchedMD/slurm/blob/slurm-24-11-5-1/src/common/slurm_errno.c#L238-L240), [23.11.7, lines 233–235](https://github.com/SchedMD/slurm/blob/slurm-23-11-7-1/src/common/slurm_errno.c#L233-L235)).

  No real refusal is captured yet: the measured second submission under `now` was accepted (Risks). The fake emits both lines. The plugin classifies a policy refusal by its reason name (science-agent decision, 1 Nov 2026, from PR #151's review):
  - `QOSMaxSubmitJobPerUserLimit`, `AssocMaxSubmitJobLimit`, `MaxSubmitJobsPerAccount`, and the group limits `QOSGrpSubmitJobsLimit` and `AssocGrpSubmitJobsLimit` mean a full slot (24.11.5 `job_state_reason.c` [210](https://github.com/SchedMD/slurm/blob/slurm-24-11-5-1/src/common/job_state_reason.c#L210) and [278](https://github.com/SchedMD/slurm/blob/slurm-24-11-5-1/src/common/job_state_reason.c#L278); 23.11.7 `slurm_protocol_defs.c` [2342](https://github.com/SchedMD/slurm/blob/slurm-23-11-7-1/src/common/slurm_protocol_defs.c#L2342) and [2376](https://github.com/SchedMD/slurm/blob/slurm-23-11-7-1/src/common/slurm_protocol_defs.c#L2376)). A group limit is shared by every user of the QOS or the grant's association, and it clears as their jobs end; its message says it is a group limit. The attempt is Rejected, like any definite refusal, and the next waits for the Rejected backoff (HBEP-7, open question 11). The Allocation stays in phase `Submitting`, with reason `SubmitLimitReached`, and its message carries the reason line;
  - any other policy reason, such as a stand-alone breach or a used-up grant, is an ordinary Rejected attempt: `SubmissionRejected` with that reason, retried with backoff (HBEP-7, Provisioning). The plugin refuses every typed stand-alone breach before any call (Submission), so such a refusal means a limit the profile does not type;
  - a refusal with no reason line, or one that is not a policy refusal, is Rejected as before, with the text Slurm gave;
  - nothing fails either way. No Instance ends, so a Rejected attempt never counts toward `RestartLoop` or a class stop (HBEP-7, Health and restarts). On `main` this already holds: the class's failure streak counts failed Instance ends only, and a Rejected attempt ends none. A test pins it (Test plan).
- **How a limit refusal fits S4's protocol** (HBEP-7, open question 11). It is a definite refusal: no job was registered, so nothing is recorded, adopted, settled or released. Whenever no job is recorded, Observe looks the tag up before anything else, the backoff check included. Take a reply that was lost under a one-job limit: the attempt was dropped after the in-flight window, its job then registered late, held, and took the one slot, so the next attempt was refused for the limit. The next Observe finds the late job by its tag and adopts it before any new claim, and settle lifts its hold once. Only the recorded job's hold is ever lifted, so at most one hold is lifted per Allocation, with HBEP-4's known risk as the one exception (Core operations, `LiftHold`). The Lost rule is unchanged: it applies to a recorded job, and a refusal records none.

Entries are unique by `deploymentID`, `capacityFlags` and the shape (proposal). A map can't key a list in the CRD, so admission refuses a second where a rule fits the budget, and otherwise `ReadProfile` does, naming the field (Core operations).
- **The source** (HBEP-7, open question 12: "a reference must not come from the Instances it judges"; proposal for the rest). A reference run, apart from serving. It is a ModelDeployment created for the measurement alone, with the serving spec, `workload` and capacity flags to be gated, under a model name no client sends, with `overAllocation` 0, ended once its Instance has warmed up. The model name is no ID input (HBEP-3, `served-model-name`), so the run has the gated ID. A spike that runs the agent's own warm-up on the same shapes is one too. Either way it measures by the gate's own method, so the two compare. With several runs on several nodes, the entry takes the slowest, so a fast node never sets a strict gate. A person writes the entry, with its envelope, into the shipped profile by PR, as for any profile change (Compatibility and upgrades). No value is copied from a serving deployment's Instances, and the controller never derives one from Instances it judges.
- **Ageing and refresh** (proposal). A new engine, image, checkpoint or ID-input flag is a new ID, which no entry matches, so the gate records only until a new reference run. An entry gates for 90 days from its `date`, then records only, since the profile records no driver or site change. A refresh removes the old entry first, so its reference run is judged against none.
- **With no entry,** the gate records only, as in alpha, and never fails an Instance (HBEP-7).
- **A known limit:** a fact outside the ID and the key, such as a node's driver or the site's configuration, can still move the figures. The age bound, and HBEP-7's suspension of an entry that two Allocations in a row fail, bound it.
- **What the spikes give.** One spike README records a figure by the gate's method. S94 measured 60.4 ms to first token and 2.44 ms per output token at 8 sessions, 1,024-token contexts and 128-token outputs, for Qwen2.5-1.5B-Instruct on one Helios GH200 GPU, with vLLM v0.32.0 at `max-num-seqs` 8 and `gpu-memory-utilization` 0.50 (`spikes/s94/README.md`, TTFT and TPOT; issue #94). As an entry with the default tolerance, its gate would fail above 4.88 ms per output token or 160.4 ms to first token. It isn't shipped. It is one run on one node, by the agent at 469acd5, before the checks' sampling rulings of 1 Nov 2026 (HBEP-7's amendment of that day), for a test spec, and the README calls it "not a capacity figure". No spike README holds an A100 figure: S2c has no live run yet, and S2b's GH200 figures come from four workers sharing one GPU. So the first entry waits for beta's first reference run on Athena (HBEP-7, Graduation criteria).

Their file systems (Lustre and NFS, and CephFS on Sano, L-12.5) and purge rules stay facts, since the agent stages again on any miss.

- **Reachability.** `partitions[].dialHomeModes`. HBEP-6 keeps the mode a launcher setting per host, and the profile says which of the two platform-dependent modes, `ssh` and `host-dialed`, each partition is measured to support. `direct` depends on the control-plane host's reachability, not the platform (HBEP-6, Notes; open question 8), so it is no profile fact. The relay facts HBEP-6 also relies on stay facts: the 40,000 `MaxStepCount` that bounds a relay's steps, recorded in both profiles, and the 4 relays per login host, a code default (Transport; open question 14).
- **Version pins.** No engine pin in the profile. HBEP-15 pins the engine per ModelDeployment by its digest, and "the framework pins no engine image of its own" (HBEP-15, Notes). The binaries the framework runs are pinned in their pins files, and the site's Slurm and Apptainer are facts the profile records as measured (HBEP-15, Where each origin is recorded). A register entry is matched against those (Known-issues register). The data_parser version stays the one typed version, checked on every reply.
- **Billing and exhaustion.** `partitions[].billingUnit`.
  - The cost is HBEP-8's (Provider accounting, Billing; the science agent's decision, 16 Nov 2026): the scheduler's own `billing` count for the job, which applies the partition's weights, times the elapsed hours, in this unit. It is the center's own count, which a factor in the profile would only drift from. The weights stay facts, since the scheduler applies them and no reader needs them.
  - At grant exhaustion nothing is typed. - **Managed-gateway behaviour.** `gateway.overloadStatus` and `gateway.rewritesRequests`, on a managed profile only. ### Provider settings

- The account, the grant, a credentials reference, the allowed partitions and the labels (owner decision, 28 Oct 2026).
- In alpha and beta a Provider allows exactly one partition; a second partition is a second Provider (open question 12; owner, 17 Nov 2026).
- The credentials reference names a mode-600 file owned by the controller's user (HBEP-11). For a Slurm provider it is an ssh client configuration naming the login node, the user and the key file, which must be mode 600 too. For a managed provider it holds the key, the gateway's base URL, and the key's expiry date when one is known, as strict JSON (science-agent decision, 31 Oct 2026; PR #71):
  - one object with exactly the members `key`, `baseURL` and an optional `expiry`; an unknown or misspelt member is an error;
  - `baseURL` is the gateway's OpenAI-style base URL, ending in `/v1`. It is https only, with http allowed on a loopback host;
  - `expiry` is an RFC 3339 time;
  - the managed Provider's controller and the front read it with one function, so they agree on every byte (HBEP-5). A file that fails these checks, or the mode and owner check, sets the Provider condition `CredentialsInvalid`, and no call is made (HBEP-11).
- The grant is recorded in alpha but not read, since billing comes after alpha. In beta the Provider's controller copies the grant and the account into each Allocation's accounting record, and the per-grant totals group by them (HBEP-8, Provider accounting, Billing; amended 2026-11-16).
- **An optional grant end,** `grantEnd` (proposed; HBEP-10, open question 12; amended 2026-11-15): when the Provider's grant ends, an RFC 3339 time. It is optional and additive, so a Provider without it is unchanged. Like the account and the grant, it is a provider setting, never in a shipped profile (open question 8). HBEP-10's audit retention reads it, as HBEP-10 (Audit) says; with no grant end recorded, `hpcburst audit prune` (stable) offers nothing for deletion. Nothing else reads it.
- **An optional QOS,** `qos` (proposed; science-agent decision, 1 Nov 2026). Which QOS a user may name is a property of the user's association, like the account, so it is a provider setting, not a profile field. When it is set, the plugin adds `--qos=<qos>` to `sbatch` (The Slurm dialect), and the profile must list it with its limits (QOS limits). With none, no flag is sent, and the association's default applies. Helios's alpha Provider sets `now`, which the framework may use freely (owner decision, 1 Nov 2026, [issue #145, comment 6557452958](https://github.com/groundnuty/plgrid-llmlab-hpc-burst/issues/145#issuecomment-6557452958)). Sano's partition `gpu` requires `--qos` (spike S5, PR #19), which this setting now allows. Sano stays outside alpha for the reasons in Notes.

### Provider status

- The age of the last successful queue read (`lastSuccessfulStatusRead`), the `Ready` condition (Operational readiness 1) and the other conditions.
- **`queueWaits`: the last 20 observed queue waits,** oldest dropped first. Each is one recorded job's wait from submission to start, taken from the scheduler's own recorded submission and start times (the queue listing's while the job is listed, its accounting record's `time.submission` and `time.start` after that), never from when the controller saw the change. Where the plugin needs the accounting record, it reads it once, after the job is first seen started; a failed read is retried on the next poll. A wait is recorded once per job: the Allocation's `status.atProvider.queueWaitRecorded` is set only after the Provider status write succeeds, so a failed write is retried at the next observe. Entries are keyed by job ID, so a repeated observe adds nothing. One exception: an Allocation that carries the queued-successor mark, the annotation `hpcburst.groundnuty.github.io/queued-successor` (proposed), adds no wait, because its pend is behind the per-user cap that the primary it replaces still holds, not the scheduler's queue (HBEP-7, Handover, No-overlap mode). Once its job has started, its `queueWaitRecorded` is set with no Provider status write, so its job still becomes final (`final` in `internal/providerctl/observe.go` requires `queueWaitRecorded` for a job that started). The lifecycle controller plans replacements from the waits (HBEP-7, open question 2). They live in status, not only in memory (HBEP-11), so a restarted controller plans from the same waits.
- For a managed Provider, `catalog` and `lastCatalogRead` (Managed provider in alpha).
- **Writers** (science-agent decision, 31 Oct 2026). The Provider's controller writes Provider status under the field manager `hpcburst-provider`, and keeps every condition it does not own. The lifecycle controller owns only the condition `DialHomeUnreachable` on a Provider, which it applies by server-side apply under its field manager, `hpcburst-lifecycle` (open question 16; HBEP-11). Neither removes the other's.

### Managed provider in alpha

- **A read-only catalog.** The managed Provider's controller lists the catalog (`GET /v1/models` with the provider's key) at most once a minute.
- **The catalog lives in the Provider's status** in alpha, as `catalog`, with `lastCatalogRead` the time of the last successful read: one entry per model the gateway has listed, with its name, any revision it reports, its managed deployment ID (HBEP-3, Deployment ID), and whether it is listed now. An entry that leaves the listing stays, marked unlisted, until the catalog's bound needs room (science-agent decision, 31 Oct 2026; PR #85):
  - **The bound** is 1,024 entries. When a read would exceed it, unlisted entries are pruned, the oldest last-listed time (the entry's `lastListedTime`) first, then by name. A listed entry is never pruned to make room.
  - **An entry that cannot be held,** such as an invalid name or one longer than the Provider status allows (253 characters for a name, 256 for a revision), is skipped, with an event naming it, raised when the entry is first skipped and then at most once an hour while it stays skipped, within HBEP-8's cap of 10 named skip events per Provider per hour, plus an hourly summary (HBEP-8, Repeating conditions). The rest is recorded, and the read still counts as successful.
  - **If listed entries alone exceed the bound,** which LLMLab is not expected to reach, the first 1,024 in name order are kept, and a `CatalogTruncated` event is raised when the cut starts and then at most once an hour until they fit. `Ready` stays True, because the read succeeded.
  - A ModelDeployment whose catalog name was pruned shows `CatalogEntryUnlisted`, as for any unlisted entry.
  - **Events** carry HBEP-8's type in `action`: `failing` for `FileRefused`, `NoCredentialsFile`, `KeyRejected`, `Expired` and `ReadsFailing`; `degraded` for `ExpiresWithinADay`, `CatalogEntrySkipped` and `CatalogTruncated`; `ready` when a condition clears (`FileRead`, `KeyAccepted`, `NotExpiring`, `CatalogRead`) (HBEP-8, Reasons in alpha).
- **Readiness.** A managed Provider's `Ready` follows the batch rule (Operational readiness 1): each successful catalog read writes `lastSuccessfulStatusRead`, and `Ready` goes False after 5 min without one, about five failed reads (science-agent decision, 31 Oct 2026; PR #85). In alpha it gates nothing: the front and a managed-source ModelDeployment still go by the last successful read and `CredentialsRejected` (HBEP-5, HBEP-7). A stale catalog is shown, not acted on; if the gateway itself is down, the front's own failed requests and pause handle it.
  - HBEP-3 models each catalog entry as an Allocation. Alpha keeps the entries in the Provider's status instead, because nothing in alpha starts, releases or repurposes them. Catalog entries as Allocation objects, through Crossplane's Observe-only import, come after alpha.
- **What LLMLab's catalog reports** (the real read of 31 Oct 2026, issue #69, [comment 6547016114](https://github.com/groundnuty/plgrid-llmlab-hpc-burst/issues/69#issuecomment-6547016114)):
  - 23 models;
  - no revision field, so a managed deployment ID never carries a revision for LLMLab (HBEP-3, Deployment ID);
  - no activity flag: `shutdown_date` is null on every entry, and nothing else in an entry names a state. An inactive model therefore shows only as LLMLab's 503 at serving, which the front passes to the client (HBEP-5).
- **The lifecycle controller never acts on a managed provider.** The front routes to the listed models of attached providers. Only a ModelDeployment with a managed source attaches a managed Provider, and a served one ignores it even when labels match (HBEP-5).
- **Keys.** From 24 h before the `expiry` in the credentials file, the Provider has the condition `CredentialsExpiring`: False with reason `NotExpiring` while the expiry is more than 24 h away or the file names none, True with `ExpiresWithinADay` within 24 h of it, and True with `Expired` after it. The file is read again on every pass, so rotating to a new key clears an earlier `Expired` at the next read (science-agent decision, 31 Oct 2026; PR #85). A rejected key (401 or 403) sets `CredentialsRejected`. A credentials file that fails its checks sets `CredentialsInvalid` (Provider settings). These are the key-expiry warnings of open question 10.
- **What a managed-source ModelDeployment shows** (HBEP-7, Reconcile loop, step 1). `Progressing` is false with reason `ManagedSource`. `Ready` follows the catalog entry, and is false with reason `CatalogEntryUnlisted`, `CredentialsRejected` or `ProviderNotOnPlatform`.
- **Not needed for alpha:** the model state that the listing does not show (LLMLab's has no activity flag), error mapping, revisions and limits, and the gateway-behaviour fields. HBEP-5 configures the front for the no-byte cut and the stalls. In beta two gateway facts are typed: the status LLMLab returns when its capacity binds, and whether it rewrites requests (Platform profile schema, The remaining groups).

### Known-issues register

The register holds upstream bugs tied to versions. Each entry has one regression test and a workaround expressed as configuration, which applies only within its version range and scope. Alpha reads no register (open question 6). Pins are where HBEP-15 records them: the engine's image digest in each ModelDeployment, a binary's sha256 in its pins file, and the site's Slurm and Apptainer as profile facts (HBEP-15, Where each origin is recorded).

**The format, for beta** (science-agent design, 16 Nov 2026; amended 2026-11-16; the file's name and the field names are proposed). One file, `register/known-issues.yaml`, holds a list of entries:

| Field | Type | Meaning |
|---|---|---|
| `id` | `KI-` and four digits; unique, never reused | the entry's name, which a workaround's comment cites |
| `symptom` | one line | what a client, a log or a test sees |
| `component`, `affected`, `fixedIn` | a name; a version range, `>=a,<b` or one version; a version, optional | the upstream part (`vllm`, `envoy`, `vllm-router`, `frp`, `apptainer`, `slurm` or `llmlab`), the versions it is seen in, and the first that fixes it, once known |
| `scope.platforms`, `scope.partitions` | PlatformProfile names; partition names; both optional, but `scope.partitions` only with `scope.platforms` | where the workaround applies. A partition is always named with its platform. With no platform it applies everywhere: an engine-wide issue (open question 9) |
| `workaround.where`, `workaround.what` | a file and field, or a package and setting; one line. Or `none`, once removed | the configuration that answers the bug |
| `test.package`, `test.name` | a Go package and a test function | its one regression test |
| `source` | a list of at least one upstream link, lesson ID or issue comment | where it was found |

**Who reads it.** No controller, in beta. Every beta workaround is a setting already in the code or a profile, applied on every version within its scope, and its comment names its entry. A controller would read an entry only to switch a workaround by version at run time on one platform, and no beta workaround needs that. A CI test reads the file (`internal/register`, proposed) and fails on:
- a field missing or unknown, or an `id` used twice;
- a platform that `profiles/` does not ship, a partition its typed list lacks, or a partition named with no platform;
- a `test.name` that is no `func <name>(t *testing.T)` in that package's test files. CI runs `go test ./...`, so the test itself runs there too;
- a version that does not parse;
- an entry for a binary pinned in a pins file, Envoy's or frp's, whose `fixedIn` the version in that file's first column has reached while its workaround is still named. Envoy's 1.40.2 reaches a `fixedIn` of 1.40.2. The PR that removes the workaround writes `none`, and keeps the entry and its test.

An engine entry never fails CI by version, since "the framework pins no engine image of its own" (HBEP-15, Notes). An engine workaround is retired only by an HBEP-15 amendment that raises the supported engine version (HBEP-15, Pinned versions).

An entry for site software is re-read by the PR that changes the profile fact it depends on.

**The entries beta starts with** are the workarounds already built for an upstream behaviour, each with its existing test:
- vLLM v0.32.0 keeps an idle connection for 5 s (L-2.5): the front drops its idle upstream connections after 4 s (HBEP-5, Time-outs and keep-alive), tested by `internal/front`'s `TestKeepAliveIdleTimeoutIsBelowTheEngines`. Behind a router, the worker's `VLLM_HTTP_TIMEOUT_KEEP_ALIVE=120` is a second entry, tested by `internal/agent`'s `TestAWorkerBehindTheRouterGetsTheKeepAlive`.
- Envoy 1.40.2's default route `timeout` of 15 s cuts a long stream, as vllm-router's default of 1,800 s did (L-4.1): the agent sets 10,800 s (HBEP-5, Time-outs and keep-alive), tested by `internal/agent`'s `TestEnvoyRouteTimeoutOutlivesTheDefault`. vllm-router's own default has no test yet; its entry comes with one if spike S2c picks that router.
- Apptainer 1.4.5 on Athena's A100 nodes cannot run a SIF (open question 15): `imageFormat: sandbox` on both Athena profiles' partitions, tested by `internal/lifecycle`'s `TestShippedAthenaNowHoldsPlgridNowOnlyAndSendsASandbox`.

### Test plan

- **S4's suite, ported to the plugin, against the fake Slurm.** It covers every scenario S4 ran, and the fake gains:
  - the real v0.0.40 and v0.0.42 shapes from S7's captures;
  - both "not listed" shapes, and Helios' three phases after a job ends (listed, empty list, then the error);
  - a reply whose data_parser differs from the profile's, and one with the `data_parser/v0.0.42` value of S7's real capture, which matches a `v0.0.42` profile;
  - a job name the fake shortens.
- **Batch fake behaviours:**
  - swinging estimates;
  - freed slots taken at once;
  - a requeue that reruns a job under the same job ID;
  - a finished job that leaves the queue listing seconds after it ends;
  - local-time text output across a daylight-saving change, which no code reads;
  - a one-job-per-user QOS: a second submission is refused with Slurm's two lines, `sbatch: error: QOSMaxSubmitJobPerUserLimit` and then the accounting-policy line; the Allocation stays `Submitting` with `SubmitLimitReached`, and the next attempt waits for backoff;
  - a per-user GPU cap: a second job that fits alone is accepted and pends until the first ends;
  - a GPU-only platform;
  - a login throttle (master failures, then reconnect).
- **Managed fake behaviours:** a no-byte cut, periodic stalls, models going inactive, ambiguous errors, key expiry and request rewriting. The alpha catalog loop is tested against listing changes and a rejected key.
- **Two providers on one fake platform,** with separate accounts: their Allocations, files and credentials never mix, and their ssh masters are separate.
- **A completing job, in both shapes.** Every case runs in each alpha cluster's shape (Core operations, Phases):
  - the Helios shape, v0.0.42: listed `[<base>,"COMPLETING"]`, then not listed (an empty list, exit 0), then read from accounting, which shows the base state alone. While the job is still listed with the flag, accounting already shows the terminal state, as in S7's poll, and that read clears nothing;
  - the Athena shape, v0.0.40: listed `[<base>,"COMPLETING"]`, then listed in its base state without the flag until `MinJobAge`, then not listed.

  The cases are `["CANCELLED","COMPLETING"]`, `["FAILED","COMPLETING"]`, `["TIMEOUT","COMPLETING"]` (the lease end, the most common real path) and `["COMPLETED","COMPLETING"]`. Each gives its base state's phase at once, with `jobCompleting` true in the same status write and `JobCompleting` True, whose time is the listing's `end_time`. A requeued job, `["PENDING","COMPLETING"]` with `restart_cnt` 1, gives `Failed` with reason `Requeued`. In every case and both shapes, all four protections hold while the flag lasts: the Allocation is counted in HBEP-7's slot count (HBEP-7, Test plan, a completing predecessor), and once deleted it keeps its files and its finalizer and has no `acct-` record. Once the flag clears, `jobCompleting` turns false, the files and the finalizer go, and exactly one `acct-` record is written. A failed listing while the flag lasts clears nothing, and the job is never `Lost`. The run-mode fake keeps the flag past its processes' exit, for its epilog. It frees the job's submit count and per-user GPU count when it sets the flag, as Slurm does (Phases), so a successor held back meanwhile is held back by the framework, not by the fake. A fixture that runs only one shape, or whose Helios shape drops a completing job from the listing at once, proves nothing for Helios; so does checking the four protections on the Athena shape alone.
- **Final state and GPU rules.** A job purged from the queue listing is reported from accounting as ended, never as missing. A submission without GPUs to a GPU partition, or to an unlisted partition, is refused before any call, and so is one with a memory request of 0.
- **The QOS flag.** A Provider with `qos: now` sends `--qos=now`. One with no `qos` sends no `--qos` at all, so Slurm uses the association's default QOS, whose limits the profile cannot know: only the partition QOS's typed limits apply then, and Slurm's own refusals still read by their reason names. To plan with a QOS's limits, a Provider names it in `qos`. With no `qos`, the fake's argv log holds neither the flag nor an empty value. A `qos` with a character outside the safe pattern is refused before any call. A `qos` that the profile does not list fails `ReadProfile`, with the field named.
- **The QOS list's bound.** A profile with 9 QOSes is refused by admission and one with 8 is accepted; two QOSes with the same name are refused.
- **The time limit is the smaller.** On a partition with `maxTime` 48 h under a QOS with `maxWall` 12 h, a 12 h request passes and a request of 12 h 1 min is refused before any call. With `maxWall` 72 h, 48 h passes and 48 h 1 min is refused. A partition QOS's `maxWall` of 1 h applies whatever the Provider's QOS sets, when that QOS has `overPartQos` false, which the fixture sets explicitly. The expected limits are worked out by hand.
- **A submit limit of 0.** Under a QOS whose effective `maxSubmitPerUser` is 0, every request is refused before any call.
- **The GPU bound.** Under a QOS with `maxGpusPerUser` 1, on a partition with `gpusPerNode` 8, a request for 2 GPUs is refused before any call, and one for 1 GPU passes. A request with more CPUs or memory than the QOS's caps is refused the same way. A fixture whose cap equals `gpusPerNode` proves nothing here, since the cap is never the smaller.
- **A limit refusal is no failure.** The fake's one-job QOS is full, held by another job of the user with another tag, as the owner's other projects would hold it. A submission is refused with both lines. The Allocation stays `Submitting` with `SubmitLimitReached`, and its message carries `QOSMaxSubmitJobPerUserLimit`. Its Instance does not end, and three such refusals in a row raise no `RestartLoop` and pause no class (HBEP-7). Once the other job ends, the next attempt after backoff is accepted. The same holds for `AssocMaxSubmitJobLimit`, `MaxSubmitJobsPerAccount`, `QOSGrpSubmitJobsLimit` and `AssocGrpSubmitJobsLimit`; for the two group limits, the message also says the limit is shared by every user of the QOS or the grant's association. A refusal whose reason line names another limit, such as `QOSMaxWallDurationPerJobLimit`, gives `SubmissionRejected` with that reason, retried with backoff, never `SubmitLimitReached`. A fixture that emits only the accounting-policy line proves nothing about the classification, since the real refusal carries the reason line first.
- **A lost reply under a one-job limit.** Attempt n's reply is lost, and the fake registers its job late, held, after the in-flight window, so attempt n is dropped. Attempt n+1 is refused for the limit, because that job holds the slot. The next Observe finds attempt n's job by its tag and adopts it before any new claim. Exactly one `scontrol release` reaches the fake's log, and no attempt n+2 is made. A fixture in which the late job never registers proves nothing here: n+1 would then be accepted, and the case the rule covers never arises.
- **Failed reads are not absence.** With the transport failing, an Allocation is never reported Lost, however long the failure lasts.
- **Read-back.** A job established with another time limit sets `SubmittedAsOther`; one whose name came back shortened is refused and cancelled. A time limit raised by the fake after the first observe moves the hard end and sets no condition. A job renamed after the first observe is refused at the next observe, and a cancel that fails is retried at the one after.
- **Time.** Hard ends parsed from epoch fields equal the expected UTC instants across a daylight-saving change.
- **Files.** `EnsureFile` places a file once, and a second call does nothing. The credential's content never reaches the fake's argv log.
- **The staging directory.** A `stagingDir` of `$SCRATCH` is resolved once per master connection to the fake's absolute path, and only that path appears in commands, the bootstrap and `agent.json`. An unset variable sets `PathUnresolved`, and no file call is made. An unset `HOME` sets `PathUnresolved`, and no `sbatch` runs.
- **The job's temporary directory.** With `tmpDir: $MEMFS` and `tmpDirFeature: memfs`, `sbatch` carries `--constraint=memfs`, and the bootstrap is the only place the variable appears. With no `tmpDirFeature`, no `--constraint` is sent. With no `tmpDir`, the bootstrap leaves the job's own `TMPDIR`.
- **The bootstrap under `/bin/sh`,** run from the submit line as `TestWrapFromTheSubmitLineRuns` runs it, with a stub in place of the agent. With the variable unset, empty, or set to a relative path, it exits non-zero before its `exec`, and the stub never runs. With it set to an absolute path, it execs the stub, which sees that path as its `TMPDIR`.
- **A failed bootstrap's outcome.** A fake job that ends `FAILED` gives the Allocation the phase `Failed`, and its Instance ends with `AllocationFailed`, never `AllocationEndedEarly` (HBEP-7, Reconcile loop step 5).
- **The dial-home key.** In ssh mode, with a key file missing from `~/.hpcburst/dial-home/`, Create sets `DialHomeKeyMissing` and no `sbatch` runs. A Provider status write keeps a `DialHomeUnreachable` condition that the lifecycle controller applied, unchanged.
- **Managed credentials.** A file with an unknown member, a `baseURL` over http to a host that is not loopback, or an `expiry` that is not RFC 3339 sets `CredentialsInvalid`, and no catalog read is made. `CredentialsExpiring` is set from 24 h before the expiry, and not a minute earlier; a rotation to a file with no `expiry` sets it False with `NotExpiring` at the next read. A catalog double that lists more than 1,024 names over time keeps every listed name and prunes the oldest unlisted first; one name that cannot be held is skipped with an event while the rest are recorded. A double that starts failing turns the managed Provider's `Ready` False after 5 min, while its ModelDeployments' `Ready` still follows the last successful read. A double that lists more than 1,024 names at once keeps the first 1,024 in name order, raises `CatalogTruncated` at its first read and not again within the hour, and leaves `Ready` True.
- **The hold lift's re-read** (tracked in #93). A job that the fake requeues, or starts, between the reconciler's first read and its re-read is not released: the re-read under the per-job lock sees a restart count above 0 or a start, and no `scontrol release` reaches the fake's log. A job whose marker another lifter wrote in that gap is not released either. The known risk's interleaving runs too, with a stall injected between the re-read and its release: leader A re-reads and stalls; leader B releases the job; it starts; the fake requeues it with a hold, as an administrator would; A resumes and releases that later hold. The test pins this as the accepted residual, so a change in either direction shows.
- **An interrupted create.** The controller is killed between the claim and the job-ID record: after restart the reconciler reaches Observe, because it runs with `WithDeterministicExternalName(true)`, and finds the job by tag.
- **Queue waits.** Each started job adds one wait, except a marked one (below), from the scheduler's recorded submit and start times (the queue listing's, or the accounting record's after the job has left it); a repeated observe adds none; a 21st wait drops the oldest; the waits survive a controller restart. A Provider status write that fails leaves `queueWaitRecorded` false, and the next observe adds the wait exactly once. A started job whose Allocation carries the queued-successor mark adds no wait and makes no Provider status write; its `queueWaitRecorded` is set, and once the job ends its observation is final, so the job is not read again. The marked case runs against the Provider's own controller (`internal/providerctl`), not only against the stand-in controller of the lifecycle controller's tests (`pkg/provider/fake`). A marked job that never starts proves nothing here, since it would record no wait anyway.
- **The estimate** (beta). Against the fake, `Estimate` runs one `sbatch --test-only`, and the fake's log shows no submit, cancel or hold release, and no attempt is claimed. A fake that fails, times out or gives an answer the plugin cannot read gives unknown, never a time or zero. With `SLURM_TIME_FORMAT=%s` the fake answers in epoch seconds, and the expected start is the fake's fixed answer, worked out by hand. On a platform whose probe hasn't decided the reading (Core operations, `Estimate`), every answer gives unknown, and so does an answer that isn't a whole number of seconds.
- **One regression test per register entry,** once the register exists. Once CI exists, an entry without a test fails it.
- **A profile is never verified against values derived from itself.** Writing a profile from a probe's output and then checking the probe against that profile proves nothing; expectations come from documentation or an independent measurement. Expected performance likewise never comes from the Instances that qualification judges. The fake's JSON is checked against S7's real captures, not against the parser it feeds.
- **Expected performance** (beta). A profile with one entry above the bound is refused and one at the bound accepted, and so is an entry with one capacity flag above its bound, or a value one character too long. Two entries with one `deploymentID`, `capacityFlags` and shape are refused, by admission or by `ReadProfile`, and two that differ only in `max-num-seqs` are accepted. An entry with no `method`, `source` or `date`, a `tolerancePercent` of 5 or 500, an `outputTokens` of 1, or a `deploymentID` of 11 characters is refused. The entries' values are hand-chosen, never a spike's measured figures, and a test that writes an entry from the Instances it then judges proves nothing (above). HBEP-7's Test plan judges the gate against them.
- **The remaining groups** (beta). Expectations are written by hand, never read from the profile under test:
  - **Dial-home modes.** Under a launcher in host-dialed mode, a Provider whose partition lists only `ssh` fails `ReadProfile` with `partitions[].dialHomeModes` named, and the fake's log holds no `sbatch`. With the list absent, or listing `host-dialed`, it reads. Under a launcher in direct mode, a partition that lists only `ssh` reads, since direct mode is not checked. A list that names a mode twice, or names `direct` or any other unknown mode, is refused by admission. A fixture whose list always holds the launcher's mode proves nothing.
  - **The billing unit.** `gpu-hour` and `cpu-hour` are accepted, and any other value is refused. With none, the record's unit is unknown. A profile changed after a record is written leaves that record's unit as it was.
  - **The gateway group.** A `gateway` group on a batch profile is refused. An `overloadStatus` of 399 or 600 is refused, and one of 429 is accepted.
- **The register's check** (beta), on fixture files written by hand. A duplicate `id`, a platform that `profiles/` does not ship, a partition its typed list lacks, a partition named with no platform, a `test.name` with no such function and a version that does not parse each fail it. An entry for `envoy` with `fixedIn: 1.40.2`, against the pins file's 1.40.2, fails while its workaround is named and passes with `none`; with `fixedIn: 1.41.0` it passes either way. An entry for `vllm` with `fixedIn: 0.32.0` passes with its workaround named, since no engine entry fails by version. A fixture written by the loader it checks proves nothing.
- **Conformance probes** against real providers stay cheap, read-only where possible, and rate-limited.

### Compatibility and upgrades

- The platform-profile schema, the provider-settings schema and the core interface are versioned with the kinds, at `v1alpha1` (HBEP-11). Unknown typed fields are refused; the untyped `profile` block takes any field.
- Version pins change by PR where HBEP-15 records them. A PR whose pins file reaches a binary entry's fixed-in version fails CI until it removes the workaround. An engine workaround goes with the HBEP-15 amendment that raises the supported engine version. Either way the entry's regression test stays (Known-issues register; amended 2026-11-16).
- The beta fields of The remaining groups are optional and additive: a profile without them reads as in alpha.
- A Slurm upgrade that changes the data_parser version stops interpretation and raises `DialectMismatch`. The fix is a profile change, plus a field table if the version is new.
- A plugin upgrade keeps every annotation of the Allocation's record (HBEP-11), so a newer plugin adopts what an older one submitted.
- Client compatibility with LLMLab is HBEP-5's concern.

### Security

- Provider credentials (cluster keys, gateway keys) are never in platform profiles, on command lines or in logs. Provider settings hold only a reference to them. For alpha, HBEP-11 keeps them in a mode-600 file on the control-plane host, or in a Secret in the team option.
- An Allocation's credential reaches the platform only through `EnsureFile`, over the ssh connection's standard input, into a mode-600 file.
- A plugin acts with the user's credentials and can spend their grant, so irreversible actions go through approvals (HBEP-10). In alpha the lifecycle controller takes no action outside the spec (HBEP-7, open question 8).
- Platform profiles hold no account names, grant names, host names or addresses. Accounts and grants are provider settings (open question 8).
- Values placed into commands are checked against a safe pattern first (Transport).
- In beta no typed Allocation event's note names a job ID (Two controllers, Events), since HBEP-8's durable log keeps them for the grant and may be exported. The untyped diagnostics stay in the cluster's own events, with their notes as they are.

## Operational readiness

1. **Working:** per provider, the age of the last successful queue read is the component signal, shown in the Provider's status, with a `Ready` condition. An Allocation submitted and seen Running is the end-to-end signal. A growing read age, `DialectMismatch`, or a submission never seen in the queue listing says it is not working.
2. **Restart:** a plugin re-reads its Allocations and their record annotations from the control plane, and finds their jobs by tag. It holds nothing in local files except the ssh master's socket, which it recreates.
3. **Silent failure:** a submission that succeeds but runs with other settings or another name; a failed read taken as absence; a reply in a changed JSON version. The read-back, the rule that only successful reads count towards `lostGrace`, and the data_parser check show the difference.
4. **Provider limits:** recorded per platform profile: time limits, MinJobAge, requeue defaults, per-user QOS limits (typed in `qos`; QOS limits), job-name rules, and the GPU-only rule. Login throttles are met with one master per login node and a cached queue listing.
5. **Capacity and exhaustion:** a full per-user or group submit limit makes `sbatch` refuse with a reason line, such as `QOSMaxSubmitJobPerUserLimit`, and then Slurm's accounting-policy line. The outcome is Rejected, the attempt waits for backoff, and the Allocation shows `SubmitLimitReached`, never a failure (QOS limits). Any other policy reason, a used-up grant enforced as an association limit included, shows as `SubmissionRejected` with that reason, also retried with backoff. It does not clear by itself, so the operator reads the reason in the message. Running jobs keep running to their hard ends. What each center does at grant exhaustion is not measured, and it stays a profile fact. Cyfronet documents one refusal for an inactive, exhausted or expired grant and for a missing account suffix, so the operator reads the cause from the grant, not from the reason (Platform profile schema, The remaining groups).
6. **Idle cost:** one ssh master per login node and credential, one queue listing per Provider per 30 s, and one catalog read per minute per managed Provider. No allocation is held while idle unless a retention policy keeps it (HBEP-7).
7. **Rollback:** disabling a provider stops new submissions. Its running allocations keep serving until their deployments hand over, because no instance is released before its replacement serves while its deployment keeps its desired capacity (HBEP-3). An instance whose replacement is late still drains before its lease end. Deleting an Allocation cancels every job with its tag. Profile changes revert by PR.

## Drawbacks

- Profiles need upkeep, and many facts are learned only by failure.
- The register is maintenance work that grows with every engine and router version.
- The command line over ssh is slower than a REST API, and each poll costs a login-node command.

## Alternatives

- **Per-site code with no shared core.** Rejected: every lifecycle rule would be written once per site.
- **One profile per provider, with account data inside.** Rejected: two grants on one platform would copy every platform fact, and account data would sit in files meant to be public.
- **Kubernetes-native offloading** (interLink and other virtual-kubelet offloading, Slinky / slurm-bridge). The evaluation (28 Oct 2026) found that they hide the lease's hard end and start estimate. Models run in provider jobs, not pods (HBEP-3, HBEP-11).
- **Contingencies off by default, enabled when needed.** Rejected: LLMLab keeps the same kinds of characteristics, so the contingencies stay on.
- **Workarounds as code patches.** Rejected: workarounds are configuration, so they can be switched off when the bug is fixed.
- **slurmrestd or FirecREST as the alpha transport.** Not chosen: no center advertises either, and JWT is off on all three platforms (S5). They stay optional transports (open question 13).
- **The tag in `--comment`.** Rejected (S4): accounting keeps the comment only where a site enables it, so the tag would vanish once the job leaves the queue listing.
- **Parsing text output with `SLURM_TIME_FORMAT`.** Not needed: the JSON gives epoch times on every platform, and parsing text needs the session's zone.
