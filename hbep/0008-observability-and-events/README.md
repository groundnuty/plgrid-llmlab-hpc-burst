# HBEP-8: Observability and events

## Summary

This HBEP decides what the framework measures and announces about the models it serves, and how a reader tells a missing reading from a zero. It covers:
- load and performance metrics that mean the same on every deployment;
- a typed event stream for the lifecycle of Allocations, Instances and ModelDeployments (HBEP-3);
- the liveness of every observer;
- per-request usage metering at the front;
- provider accounting read from the provider's own accounting.

It serves the user, the agents that operate deployments for them (HBEP-10), and the lifecycle controller (HBEP-7), which acts on the same signals.

In alpha:
- events are Kubernetes Events (`events.k8s.io/v1`), kept 7 days, with HBEP-8's type in `action`;
- metrics are Prometheus exposition from the front and the lifecycle controller, under `hpcburst_` names;
- usage records are the front's synced JSON Lines files;
- provider accounting is allocated GPU-hours and CPU-hours per Allocation, from the scheduler's accounting.

In beta (amended 2026-11-16):
- a durable log, NATS JetStream embedded in a process of its own beside the controllers, keeps every typed event for the grant, and a rolling copy of the latest usage records. The usage files stay the record;
- the Provider controller raises typed events on the Allocation itself;
- OpenTelemetry's generative-AI conventions are a mapping from the `hpcburst_` names, not new names;
- provider accounting adds the scheduler's own billing per Allocation, in its partition's unit, and totals per grant, all still "allocated, not billed".

HBEP-10's subscriptions read the log at stable.

## Motivation

This serves stage 4 of the user story in HBEP-2 (watch them). It also feeds stage 3 (keep instances running) and stage 7 (pay and give back).

A past project served models on several Slurm clusters behind its own fronts. Its signals existed somewhere but could not be read, compared or trusted:
- New instances served unannounced, and work parked behind a manual gate left GPUs idle for hours. Nothing said "ready" or "waiting".
- Watchers died silently with the session that started them, or kept their samples in temporary files that vanished. A summary later listed a dead watcher as live, so reports went unposted for hours.
- Empty samples were printed as 0, so busy routers looked idle. A rate check read renewable work claims as starts and always said OK. A window count returned zeros when it could not read its input.
- KV-cache utilisation was compared across deployments. Attention implementations differ per GPU type, so one percentage meant different loads. Streams with few chunks gave no per-token latency at all.
- Preemption counters reset when a server restarted, which invalidated before/after comparisons. A routing change was judged on an unchanged fingerprint alone, and it missed a several-fold throughput loss that prefix-cache hit rate and time to first token would have shown.
- A job ended by its time limit left its endpoint file behind, so the inventory kept a dead instance. Deliberate restarts were counted as crashes.
- Monitors read their list of targets once at start, so new deployments went uncounted for hours.
- Other tools parsed free-text state lines, and misread one kind of event as another.
- Tokens served and GPU-hours were rebuilt from logs afterwards. A center's usage report counted only finished jobs. A forecast counted pending jobs with an unknown start as starting now.

### Goals

- Metrics that compare across deployments, providers and GPU types: running and waiting requests per instance, time per output token, preemptions, prefix-cache hit rate, and time to first token.
- An event stream with the types started, ready, degraded, failing, ending soon and replaced, and in beta ended, for every Allocation, Instance and ModelDeployment.
- Liveness for every observer. A scraper, prober or watcher that stops is itself an event.
- An explicit "unknown" for every sample that could not be read, never a zero.
- Per-request usage metering at the front, attributed to the client key and to the deployment and instance that answered (HBEP-9).
- Provider accounting (grant hours by Allocation) from the provider's own accounting, with running and pending Allocations included.
- Observation that follows the inventory (HBEP-10) as it changes.

### Non-goals

- Choosing a metrics database or dashboard. The framework exposes metrics; storing them is the user's choice.
- Alerting policy: which threshold pages whom. Thresholds are platform-profile parameters (HBEP-4); routing alerts to people is the user's choice.
- Delivery guarantees to event subscribers. HBEP-10 owns subscriptions, cursors and acknowledgement. This HBEP owns what an event is and which types exist.
- Logging prompts or responses. Usage metering records counts and identities only.
- Engine metrics inside a managed provider. LLMLab exposes none, so the framework measures it from the front.

## Proposal

### User stories

- A researcher compares an instance on Helios with one on Athena by running and waiting requests, time per output token and time to first token, on one scale.
- An agent subscribes to "ending soon" and starts a handover before an Allocation's hard end, instead of polling job lists. Until HBEP-10's subscriptions come, at stable, it watches the Instance's events, and re-reads status when it resumes.
- An agent operating overnight receives a `failing` event for one provider's reads, reason `HeartbeatMissed`. It does not read the silence as health.
- At the end of a month, a researcher reads tokens served per model and per client key, and allocated GPU-hours per Allocation, from records kept while serving.
- Before changing a routing setting, an operator compares per-session throughput, prefix-cache hit rate and time to first token before and after. The comparison cannot silently straddle an instance restart.

### Notes, constraints and caveats

- **Three sources.** Engine metrics come from each Instance, through the agent's health reports (HBEP-7). Front metrics (time to first token, errors, cuts, usage) come from the front, for every provider including managed ones. Provider facts (queue state, start estimate, hard end, accounting) come from the provider plugin (HBEP-4).
- **KV-cache utilisation is recorded but not compared** across deployments. Load is compared by counts and times only.
- **Unknown is a value.** A sample is a value, "unknown" with a reason (unreachable, stale, not reported by this engine), or "not applicable". An aggregate says how many of its samples were unknown. A check that cannot read its input reports unknown, never pass.
- **Every series belongs to one Instance** (HBEP-9 attribution), and to one engine process of it. An engine restart starts a new series, so a rate never goes negative and a comparison across a restart is visible as one.
- **Six types, many reasons.** The types are `started`, `ready`, `degraded`, `failing`, `ending-soon` and `replaced`, spelled as the lifecycle controller emits them (PR #88). They apply to any subject: an Allocation, Instance or ModelDeployment, and also an observer or controller. Everything finer is a CamelCase reason code. A stopped observer is `failing` with reason `HeartbeatMissed`. A restart, a missed submission or a repeated crash (HBEP-7) are reasons under `failing`, `degraded` or `replaced`. A new type is an amendment to this HBEP; a new reason is not.
- **A seventh type in beta: `ended`** (amended 2026-11-16; the science agent's decision of that day). It is a job that ended at its planned end, or by its retention, never by a failure (Design details, Events, Allocation events, Planned or not). `replaced` would tell an agent that something took the job's place, which nothing may have. The Provider controller raises it for an Allocation (Design details, Events, Allocation events), and it joins the drift guard's types (`Actions`, `internal/reasondrift/docs.go`) with the code that raises it. A reader that does not know it treats it as "other" (Compatibility).
- **Events are typed.** Each has a type, a reason code, the resource's stable name, a time in UTC from the emitter's clock, and an optional message. Tools act on type and reason, never on the message.
- **Status is the truth, events are best-effort.** An event can be merged with an earlier one, delayed or dropped (Design details, What the recorder merges and drops). A reader that must not miss a change reads status. In beta the durable log keeps every typed event it acknowledges, but an emitter can still fail to reach it (Design details, The durable log, When it is down), so status stays the truth.
- **Planned and unplanned stops differ.** An event for a stop that someone asked for names the actor and the operation (HBEP-10). A stop without them is a failure. In alpha the actor is the emitting controller, in the event's `reportingController`. In beta, an event for a stop that an Operation asked for keeps its existing reason, carries the Operation in `related`, and names it in the note (HBEP-10, Proposed event reasons).
- **Usage records carry the request's own time,** not the time the record was written or copied.
- **Provider accounting** comes from the platform's own accounting, per provider, never from the framework's logs. In alpha it is allocated time only, labelled "allocated, not billed". Billing formulas differ per cluster (some charge the largest of a core, GPU or memory share). In beta the framework takes the scheduler's own billing, which applies each partition's weights, and the platform profile says what one unit counts (amended 2026-11-16; Design details, Provider accounting, Billing). A pending Allocation with an unknown start is unknown, never "starting now".
- **Contingencies stay on.** Every check here is on by default and cheap when idle, as for every contingency in this framework.

### Risks and mitigations

- **Observers die silently.** Every observer has a heartbeat: a time stamp it writes on each successful read, or a `Lease` it renews. A component that does not depend on it judges the heartbeat's age, marks the readings it fed unknown, and emits a `failing` event with reason `HeartbeatMissed` (Design details, Observers). Observers run under the control plane (HBEP-11), never in an agent's session.
- **Heartbeats alias against check ticks.** A batched heartbeat read against a fixed tick gave false "down" alerts. Each down interval spans several heartbeat periods, and the check reads the heartbeat's own time stamp, never a file's modification time.
- **Events taken as the only truth.** A subscriber that misses an event acts on stale state. Events are edges; resource status (HBEP-11) is the level truth, and a resuming subscriber re-reads status. client-go's recorder merges and drops events by design (Design details), so no tool depends on seeing every one.
- **A metric some engines cannot give.** With few chunks, the front cannot derive time per token. Engine-side timing is used where reported; otherwise the value is unknown.
- **Metering on the request path** adds latency, or loses records when the front crashes. A lost record must show as a gap in the usage record, or in a failure count, never as silence.
  - **Alpha** (HBEP-5): the front appends usage records to a local JSON Lines file. Each record is synced before the request is reported done to the sink's caller. Records that end together share one write and one sync, so they are batched only when they arrive faster than the disk syncs (Design details, Usage records).
  - **Counter:** each usage record carries a monotonic counter that the front persists apart from the log, in blocks, so a consumer can see a missing range after a crash.
  - **A crash leaves a gap that bounds the loss without counting it.** The gap holds the reserved counters that were never used and the records lost in the crash, and a reader cannot tell them apart. A clean stop leaves no gap of its own, but the counters of a batch that failed were assigned, so they still show as one, and so can a reservation whose persistence is uncertain (Design details, Usage records).
  - **Beta** (Design details, The durable log): the files stay the record, and the front copies each synced record from them to the durable log. Spike S8 (issue #25, PR #28) measured NATS JetStream with `sync_interval: always` at about 860 acknowledged publishes per second for one publisher, and 950 to 1,360 for 8 or 32, on its test disk (S8, Results 5). It lost no acknowledged write to 30 SIGKILLs, and did not test power loss or a kernel crash. So the log is a copy until a power-loss test proves it.
- **A full disk.** The usage files and the control plane's SQLite store share the host's disk. With SQLite, a full disk stops writes (HBEP-11, Operational readiness 5), so the `failing` event for the usage failure may not be stored either. The failure counter and the front's readiness are the reliable signals (Design details, Usage records). In beta the durable log shares the disk too. Its streams are capped, so it cannot take more than its caps, and `up` starts it only when the caps fit above a free-space floor (Design details, Retention).
- **Accounting sources lag or undercount,** as a report of finished jobs only does. The framework reads the scheduler's accounting, which counts running jobs. Where a center report and the scheduler's accounting differ, both are shown with the gap (beta).
- **Managed providers are opaque.** LLMLab's periodic stalls show only in the front's time to first token.
- **Series multiply with handovers.** Each handover adds a series per metric. Engine series carry only identity labels, and descriptive labels sit on one info series per Instance (Design details, Metrics). Retention and roll-up belong to whatever store the user picks.

### Open questions

"Science agent, 31 Oct 2026" marks a decision the science agent made that day for this HBEP to become implementable. "Proposed by this HBEP" marks the author's own choice, put to the review round. Questions decided in another HBEP name it.

1. **Metric names and units.**
   - **Decided for alpha:** our own names, prefixed `hpcburst_`, with units in the name, following Prometheus's naming conventions. vLLM's names are mapped to them in the agent and the controller (Design details, Metrics). Source: science agent, 31 Oct 2026.
   - **Decided for beta** (amended 2026-11-16): a mapping, not new names. Each `hpcburst_` metric and usage field with a counterpart in OpenTelemetry's generative-AI conventions is mapped to it, pinned to one commit, and the rest are named as having none (Design details, Metrics, OpenTelemetry). Every convention used is Development status, and this HBEP's names are read by tests and tools, so a rename would break them for names that may still change. The framework emits no spans in beta. Source: proposed by this amendment.
2. **How engine metrics leave the job.**
   - **Decided for alpha:** in the agent's health reports (HBEP-7, The allocation agent), never by a scrape through the tunnel. The tunnels carry only the front's routed requests and its passthrough: the token tunnel, and in beta the bulk tunnel (HBEP-6, The bulk path). Source: HBEP-6 and HBEP-7.
   - Spike S9 asked whether a scrape through the front and tunnel shows a gone Instance as down. Alpha has no such scrape, and the unknown rule answers the rest, so S9 is not needed for alpha.
3. **Where "degraded" and "failing" are defined.**
   - **Decided for alpha:** HBEP-7's malfunction signals, with thresholds in the platform profile's `health` group (HBEP-4, Platform profile schema). Source: HBEP-4 and HBEP-7.
4. **How "ending soon" is timed.**
   - **Decided for alpha:** once, an hour before a ready Instance's drain start, when no replacement is ready (HBEP-7, Events and conditions). Source: HBEP-7.
   - **Not needed for alpha:** a lead time from the profile, repeated at fixed steps.
5. **Usage counts.**
   - **Decided for alpha:** the engine's count when the response carries one; otherwise the counts are null and the front's count of streamed content events is recorded, marked `front_events`. Source: HBEP-5, Usage records.
6. **Retention of events, usage and metrics.**
   - **Decided for alpha:** events are kept 7 days: the launcher sets k3s's apiserver `event-ttl` to 168 h (Design details, Retention; HBEP-11). Source: science agent, 31 Oct 2026.
   - **Decided for alpha:** usage records are kept for the grant's life. Rotation keeps every file, and nothing in the framework deletes one. Source: science agent, 31 Oct 2026.
   - **Not needed for alpha:** retention of a metrics store, since the framework keeps none.
   - **Decided for beta** (amended 2026-11-16): events in the durable log are kept for the grant, compressed once cold, and deleted only after a person confirms, as the audit log is. Their stream is capped and refuses new events when full, rather than evicting. Usage records are kept for the grant's life in the files, which are the record; the log holds a rolling copy of the latest, whose oldest go at its cap. Kubernetes Events keep their 7 days (Design details, Retention). Source: the audit log's rule (owner, 14 Nov 2026; HBEP-10, open question 10), applied to events by this amendment; the caps and the rolling usage copy by the science agent's decisions of 16 Nov 2026.
7. **Whether each client key can read its own usage through the front.**
   - **Not needed for alpha:** the operator reads the usage files on the host. Source: science agent, 31 Oct 2026.
8. **The last level of liveness: an end-to-end probe from outside the front and control plane.**
   - **Not needed for alpha:** the alpha host's own checks (Operational readiness 1) and the client's view are the outer level. Source: science agent, 31 Oct 2026.
9. **Probes or live traffic for time to first token.**
   - **Decided for alpha:** live traffic only. Each usage record carries `firstTokenMs`, and the front exports their distribution. Alpha sends no probe requests for timing; HBEP-6's probe checks the path, not timing. Source: science agent, 31 Oct 2026.
10. **What an observer that restarts emits.**
    - **Decided for alpha:** one `degraded` event with reason `ObservationGap`, from the lifecycle controller and the front, and status is the truth. The Provider managers emit none in alpha, since their recorder writes no `action` (open question 14). Its message names the gap's start, the observer's last heartbeat before the restart. S8's gap marker covers events evicted from a log; an observer's missed transitions were never published, so it still needs its own gap event. Source: the lean of this HBEP, confirmed by the science agent, 31 Oct 2026.
    - **Decided for beta** (amended 2026-11-16): each Provider manager emits one too, regarding its `provider-<name>` `Lease`, since its Allocation events are typed (open question 14). The Reasons table's Emitter cell names it with that code. Source: proposed by this amendment.
11. **The event stream's store.**
    - **Decided for alpha:** Kubernetes Events (`events.k8s.io/v1`), best-effort, with status as the truth. Source: science agent, 31 Oct 2026.
    - **Decided for beta** (amended 2026-11-16): NATS JetStream, embedded in a process of its own that the launcher supervises, with one stream for typed events and one for usage records, delivered at least once with a dedupe id; the usage files stay the record (Design details, The durable log). Source: spike S8 (PR #28) for the settings and the delivery; proposed by this amendment for the process, the streams' subjects and ids, and the files as the record. HBEP-10's subscriptions and cursors over it come at stable (amended 2026-11-15; HBEP-10, Graduation criteria).
12. **How an unknown sample is shown in Prometheus.**
    - **Decided for alpha:** an absent series plus an explicit gauge, `hpcburst_instance_metrics_unknown`, with the reason (Design details, Unknown samples). Source: proposed by this HBEP, 31 Oct 2026, from the comparison there; the science agent asked for one form to be chosen with its reason.
13. **Whether the front serves while usage cannot be written.**
    - **Decided for alpha:** it keeps serving, and the failure is loud: counted, raised as a `failing` event and stated in its readiness. Source: the science agent's lean, 31 Oct 2026, taken here.
14. **Typed events for Allocations.**
    - **Decided for alpha:** an Allocation's lifecycle shows in its Instance's events, whose reasons name the Allocation's outcome (`AllocationFailed`, `AllocationLost`, `AllocationRefused`, `Requeued`, `SubmittedAsOther`, `RelayEndedForGood`, `AllocationEndedEarly`; HBEP-7). The Provider controller's own events (HBEP-4) keep crossplane-runtime's recorder, which writes no `action`; readers treat them as type "other" (Compatibility). Source: proposed by this HBEP, 31 Oct 2026.
    - **Decided for beta** (amended 2026-11-16): the Provider controller raises typed events on the Allocation itself, for its job's submission, lifted hold, start, nearing hard end, end and failures, through a recorder of `events.k8s.io` (Design details, Events, Allocation events). Their notes carry no job ID. HBEP-4's other diagnostics stay untyped, with their notes as they are. A planned end takes a new type, `ended` (Notes). Source: proposed by this amendment; `ended`, and the job-ID rule's scope, by the science agent's decisions of 16 Nov 2026. Each reason joins the Reasons table with its code.
15. **The billing formula.**
    - **Decided for alpha:** allocated time only.
    - **Decided for beta** (amended 2026-11-16): an Allocation's billed units are the scheduler's `billing` count for its job, from the accounting read the plugin already makes, times its elapsed hours, in its partition's `billingUnit` (HBEP-4, Platform profile schema, The remaining groups). Every figure stays labelled "allocated, not billed" until a center's report is compared (Design details, Provider accounting, Billing). Source: the science agent's decision, 16 Nov 2026: the count is the center's own, which a factor in the profile would only drift from; Slurm's `TRESBillingWeights` and three recorded billing counts (Design details, Provider accounting, Billing).
16. **A per-grant accounting ledger.**
    - **Decided for alpha:** one accounting record per ended Allocation, kept after the Allocation is deleted (Design details, Provider accounting). Source: proposed by this HBEP, 31 Oct 2026, since an Allocation's status goes with it.
    - **Decided for beta** (amended 2026-11-16): totals per grant and account, summed by `hpcburst accounting` (proposed) from the kept records and the live Allocations, each unit apart, with unknown members counted. The comparison with a center's report is a beta criterion, run by a person (Design details, Provider accounting, Billing; Graduation criteria). Source: proposed by this amendment; `grantEnd` from HBEP-10's amendment (HBEP-4, Provider settings).

## Design details

### Events

**Form.** Every event is an `events.k8s.io/v1` Event ([`events/v1/types.go`, lines 43–85](https://github.com/kubernetes/api/blob/v0.35.3/events/v1/types.go#L43-L85), accessed 2026-10-31):

| Field | Holds |
|---|---|
| `action` | HBEP-8's type: `started`, `ready`, `degraded`, `failing`, `ending-soon` or `replaced`, and in beta `ended` |
| `reason` | the CamelCase reason code alone |
| `type` | `Warning` for `degraded` and `failing`, `Normal` for the others |
| `regarding` | the resource the event is about |
| `related` | optional: a second resource, such as the Instance behind a deployment's event |
| `eventTime` | the emitter's clock; it serialises in UTC |
| `note` | the human message, at most 1,024 bytes |
| `reportingController` | the emitting component's field manager, such as `hpcburst-lifecycle`: the actor of a planned stop |

The API refuses a new event without `action` or `reason`, with either over 128 characters, or with a note over 1,024 ([`pkg/apis/core/validation/events.go`, lines 35–38 and 172–186](https://github.com/k3s-io/kubernetes/blob/v1.36.5-k3s1/pkg/apis/core/validation/events.go#L35-L38), in the Kubernetes that k3s v1.36.5+k3s1 builds, [`go.mod`, line 64](https://github.com/k3s-io/k3s/blob/v1.36.5%2Bk3s1/go.mod#L64); accessed 2026-10-31). So each emitter cuts its note to 1,024 bytes.

**Reasons in alpha.** Every reason below is emitted on `main`. Most are constants of the contracts (`api/v1alpha1`) or of the emitting package; `Ready`, `HandedOver` and `NoReplacementReady` are still literals at their emit sites until PR #246 makes them constants. #239's drift guard, in PR #246, is to check each row's type, reasons and Regarding kinds against the code's emit sites, both ways; it does not compare the Emitter column:

| Type | Reasons | Regarding | Emitter |
|---|---|---|---|
| `started` | `AgentRegistered` | Instance | lifecycle controller |
| `ready` | `Ready`; `ShapesFit` | Instance; ModelDeployment | lifecycle controller |
| `degraded` | `ReplacementLate`, `RestartLoop`, `IdentityUnresolved` | ModelDeployment | lifecycle controller |
| `degraded` | `VerificationFailed`, `CapacityDropped` | ModelDeployment, else the Instance once the ModelDeployment is gone | lifecycle controller |
| `degraded` | `CapacityDropped`, `CountsDrift` | ModelDeployment | front |
| `degraded` | `DrainWindowShort` | PlatformProfile | front |
| `degraded` | `PathProbeFailing` | Instance | front |
| `degraded` | `TunnelOrphaned` | the Allocation whose credential admitted the tunnel, else the `lifecycle` `Lease` | lifecycle controller |
| `degraded` | `ObservationGap` | the emitter's own `Lease` | the lifecycle controller and the front, at start |
| `failing` | `WorkerRestart`, `InstanceRestart`, `RouterRestart`, `CrashCorrelated`, `RestartLoop`, `RegistrationTimeout`, `StartTimeout`, `TunnelNotConnected`, `QualificationFailed`, `VerificationFailed`, `AllocationFailed`, `AllocationLost`, `AllocationRefused`, `Requeued`, `SubmittedAsOther`, `RelayEndedForGood`, `AllocationEndedEarly` | Instance | lifecycle controller |
| `failing` | `HeartbeatMissed` | the stale observer's resource (Observers) | the component that judges it |
| `failing` | `UsageWriteFailed` | the front's `Lease` | front |
| `replaced` | `HandedOver`, `HedgeLost` | Instance | lifecycle controller |
| `ending-soon` | `NoReplacementReady` | Instance | lifecycle controller |

- An event about a deployment caused by one Instance regards the ModelDeployment, with the Instance in `related`. `VerificationFailed`'s `degraded` event and `CapacityDropped`'s regard the Instance instead once the ModelDeployment is gone (`mdObject`, `internal/lifecycle/verify.go`), since nothing else is left to attach them to.
- The managed catalog controller's events take these types too. Their reasons are the condition reasons it writes: `failing` for `FileRefused` and `NoCredentialsFile` (`CredentialsInvalid`), `KeyRejected` (`CredentialsRejected`), `Expired` (`CredentialsExpiring`) and `ReadsFailing` (`Ready`); `degraded` for `ExpiresWithinADay`, `CatalogEntrySkipped` and `CatalogTruncated`; and `ready` for `FileRead`, `KeyAccepted`, `NotExpiring` and `CatalogRead` when a failing or degraded condition clears.
- The Provider controller's events are HBEP-4's diagnostics, untyped in alpha (open question 14). Among them is `RelayFailed`, a Warning regarding the Allocation (HBEP-6, Dial-home modes, host-dialed mode, What ends a relay): `onRelayFailed` raises it (`internal/providerctl/relayfailed.go`) when a relay ends for good other than by its job's end or, in alpha, by being superseded, after it marks the Allocation `RelayEndedForGood` and only while its copy leads. It carries no action, since it goes through crossplane-runtime's recorder as the others do. In beta the Allocation's transitions are typed instead (Allocation events), and `RelayFailed` stays a diagnostic.
- **Proposed with HBEP-10's Operations** (beta). They join the table only with the code that raises them, since the table is checked against the code: `PlanStale`, of type `degraded`, regarding the Operation, when an approved or confirmed plan turns stale at execution; and `OperationPartlyFailed`, of type `failing`, regarding the Operation, when one of its targets fails. A plan waiting for approval raises no event; its Operation's phase shows it (HBEP-10, Proposed event reasons).

**Allocation events (beta)** (open question 14; proposed by the amendment of 16 Nov 2026). The Provider controller raises typed events regarding the Allocation through a second recorder, `events.k8s.io`'s, from its manager, with `reportingController` `hpcburst-provider`. The raised-events counter (controller `provider-<name>`) and the log's publisher (The durable log) wrap it. One map from reason to type is the only place their types are set, as in the managed catalog controller (`internal/managed`). Each is raised in the pass that first computes the change, before the status write that records it, as HBEP-7 orders a restart's event before its generation write. A failed write makes the next pass raise it again, under the same id in the log (The durable log, Streams).

| Reason | Type | When | The note names |
|---|---|---|---|
| `JobSubmitted` | `started` | a submission's job is first recorded | the attempt, partition, QOS and time limit, and whether it is held |
| `JobAdopted` | `started` | a job found by its tag is first recorded instead | the source it was found in, the partition and the time limit |
| `HoldLifted` | `started` | the recorded job's hold is lifted, so it pends | the submit time |
| `JobStarted` | `ready` | the job runs | the start time, hard end, queue wait, and allocated GPUs and CPUs |
| `HardEndNear` | `ending-soon` | an hour before a running job's hard end, once per hard end | the hard end |
| `JobEnded` | `ended` | phase `Ended`, whatever its base state: at or after the hard end, while its Instance drains, or while the Allocation is being deleted for its retention, an Operation or a person | the base state, the end time, and the release cause when one is written |
| `AllocationEndedEarly` | `failing` | phase `Ended` before the hard end, with no Instance of it draining and no deletion asked for | the base state and the end time |
| `AllocationFailed` | `failing` | phase `Failed`, other than a requeue | the base state and the scheduler's state reason |
| `Requeued` | `failing` | a requeue is seen | the restart count and the base state |
| `SubmittedAsOther` | `failing` | the read-back differs from what was submitted | the fields that differ |
| `AllocationRefused` | `failing` | phase `Refused` | why |
| `JobLost` | `failing` | phase `Lost` | absent since when, and `lostGrace` |
| `JobReappeared` | `ready` | a `Lost` job shows again | the phase it shows, and since when it was absent |
| `AdminHold` | `degraded` | the job carries an admin hold, a repeating condition | the state reason |
| `JobCompleting` | `degraded` | the job has carried `COMPLETING` for 10 minutes, a repeating condition | the base state, and since when |

- **The reasons.** `JobSubmitted`, `JobAdopted`, `HoldLifted`, `JobLost`, `JobReappeared` and `SubmittedAsOther` are the Provider controller's untyped reasons on `main` (`providerControllerEvents`, `internal/reasondrift/exceptions.go`), raised typed instead. `AllocationEndedEarly`, `AllocationFailed`, `Requeued` and `AllocationRefused` are the lifecycle controller's Instance reasons, now regarding the Allocation too. `JobStarted`, `HardEndNear`, `JobEnded`, `AdminHold` and `JobCompleting` are new. All are proposed. Each joins the Reasons table, with the Allocation in its Regarding cell, only with the code that raises it, since #239's drift guard checks the table against the code.
- **Held and pending need no events of their own.** In hold mode a job is held from its submission, which `JobSubmitted` says, and pends from its lift, `HoldLifted`. In fallback mode it pends from its submission.
- **The types.** `JobEnded` takes beta's seventh type, `ended`: a job that ended at its planned end, or by its retention, never by a failure (Notes; the science agent's decision, 16 Nov 2026). `replaced` keeps its meaning, that something took the place of what ended (`HandedOver`, and HBEP-7's proposed `HedgeLost`). `JobReappeared` takes `ready`, as a cleared condition does (the managed catalog controller's `ready` events).
- **Planned or not,** as the lifecycle controller judges an Instance's end: a lease end is not a failure, and neither is a hard end that passes while the Instance drains (`internal/lifecycle/instances.go`, lines 118–124; HBEP-7, Test plan). So a job that ends at or after its hard end, or while its Instance drains, is `JobEnded`, whatever Slurm's state: `TIMEOUT`, `COMPLETED` or `CANCELLED`. The Provider controller reads that Instance's phase from its cache, by the Instance's `spec.allocationRef` (an index on that field; its identity may read Instances).
  - **A deletion asked for** by the Allocation's retention, by an Operation or by a person is `JobEnded` too. The lifecycle controller releases by deleting, under the retention policy (HBEP-7, Retention), and the finalizer cancels the job (HBEP-4, Two controllers). The release cause names which, when the lifecycle controller wrote one (HBEP-11, The Allocation's record). When it names an Operation, `JobEnded` carries it in `related` (HBEP-10, Proposed event reasons).
  - **A deletion that follows a failure raises no end event,** since its `failing` event has fired: the Allocation's phase is `Failed` (a requeue included), `Lost` or `Refused`, or it carries `SubmittedAsOther` or `RelayEndedForGood`, the failures HBEP-7 releases for (HBEP-7, Reconcile loop, step 5).
  - **`AllocationEndedEarly`** is only an end before the hard end, with no Instance of it draining and no deletion asked for: the job was ended from outside the framework, or its agent exited early (Notes, Planned and unplanned stops).
- **No job ID in a note.** These events become CloudEvents in a log that is kept for the grant and may be exported (Retention), so their notes name the job's facts: states, times in UTC, partition, QOS and counts. They never name the job ID, which stays in the Allocation's annotation and status (HBEP-11, The Allocation's record) and in its `acct-` record. The rule covers these events only (the science agent's decision, 16 Nov 2026). HBEP-4's untyped diagnostics keep their notes as they are: they stay in the cluster's own events, never in the log (The durable log, Streams).
- **Repeating conditions.** `AdminHold` and `JobCompleting` follow the hourly gate (Repeating conditions), and their end shows in status only. Ten minutes are far past a normal cleanup: S7 saw the flag for one 2 s poll (HBEP-4, Graduation criteria). So a job still completing then is HBEP-4's stuck case (HBEP-4, Risks).
- **`HardEndNear`** fires in the first pass at or after an hour before the hard end. Its in-memory gate is keyed by the hard end, so a hard end that moves later fires again before the new one, and a restart may fire it once more. It is the lease's own warning; `NoReplacementReady` stays the Instance's (open question 4).
- **After a restart.** The first pass compares the job with the stored status, so a change made while the controller was down is announced late, and steps in between are not replayed. Each Provider manager raises one `ObservationGap` regarding its `provider-<name>` `Lease` once it holds it (Gaps after a restart).
- **Counting.** These reasons' series in `hpcburst_events_raised_total` are created at 0 for each batch Provider, as the lifecycle controller's are (Raised events).
- **RBAC.** The Provider controller's identity may create `events.k8s.io` Events in the Allocations' namespaces.

**Repeating conditions.** An event for a condition that persists, such as `CatalogTruncated`, `CatalogEntrySkipped`, `UsageWriteFailed` or `HeartbeatMissed`, is emitted when the condition starts, and then at most once an hour while it lasts, never on every read. Merging cannot be relied on to bound such events (What the recorder merges and drops). The hourly gate is kept in memory, so a restart or a new leader emits it once more, which is "when it starts" for that process. For the managed catalog controller's Provider conditions, a condition that clears emits `ready` with the reason it writes (`FileRead`, `KeyAccepted`, `NotExpiring`, `CatalogRead`); the other repeating conditions show their end in status only. `CatalogEntrySkipped` is one condition per entry and skip category; at most 10 named skip events are emitted per Provider per hour, then one summary event per hour whose note names as many of the remaining entries as fit in its 1,024 bytes, ending with "…". The end of a skip or a truncation emits nothing, since neither sets a Provider condition (science-agent rulings, 31 Oct 2026, for #114).

**What the recorder merges and drops.** The lifecycle controller gets its recorder from controller-runtime, which builds client-go's `events.k8s.io` broadcaster ([`pkg/cluster/cluster.go`, lines 295–299](https://github.com/kubernetes-sigs/controller-runtime/blob/v0.23.1/pkg/cluster/cluster.go#L295-L299); [`pkg/internal/recorder/recorder.go`, lines 169–199](https://github.com/kubernetes-sigs/controller-runtime/blob/v0.23.1/pkg/internal/recorder/recorder.go#L169-L199); accessed 2026-10-31). The front builds the same broadcaster itself. In client-go v0.35.3 ([`tools/events/event_broadcaster.go`](https://github.com/kubernetes/client-go/blob/v0.35.3/tools/events/event_broadcaster.go), accessed 2026-10-31):
- **Merging.** Two events are isomorphic when type, `action`, `reason`, `reportingController`, `reportingInstance`, `regarding` and `related` are equal; the note is not part of the key (lines 58–66 and 297–310). `regarding` and `related` are full object references, `resourceVersion` included ([`tools/reference/ref.go`, lines 94–101](https://github.com/kubernetes/client-go/blob/v0.35.3/tools/reference/ref.go#L94-L101)), so an event about an object that was written in between is a new event, not part of a series. The controllers write status on most passes, so merging happens mainly for an event repeated on an unchanged object. A second isomorphic event within 6 minutes turns the first into a series with a count of 2. Later ones only raise the count in memory, and the note of every event after the first is lost (lines 170–206). The count reaches the API every 30 minutes, and once the series has been quiet for 6 minutes (lines 48–53, 126–161 and 392–394).
- **Dropping.** The queue holds 1,000 events, and a new event is dropped silently when it is full (line 115): the watch distributor's `select` has an empty `default` branch, and nothing is logged ([apimachinery `pkg/watch/mux.go`, lines 280–289](https://github.com/kubernetes/apimachinery/blob/v0.35.3/pkg/watch/mux.go#L280-L289)). An event the API refuses, a refused note or a full store's error included, is not retried. A transport error is retried up to 12 times, 10 s apart with jitter, and then dropped (lines 49, 208–228 and 250–282). An event whose object reference cannot be built is dropped before it is queued ([`tools/events/event_recorder.go`, lines 64–71](https://github.com/kubernetes/client-go/blob/v0.35.3/tools/events/event_recorder.go#L64-L71)).
- **Time.** `eventTime` is the recorder's wall clock at the call, not a controller's injected clock (`event_recorder.go`, line 65).
- **Namespace.** An event about a cluster-scoped object lands in `default` (`event_recorder.go`, lines 91–96).
- **The legacy recorder differs.** crossplane-runtime's recorder, which the Provider controller uses, writes through client-go's `tools/record` with no `action` ([`pkg/event/event.go`, lines 93–106](https://github.com/crossplane/crossplane-runtime/blob/v2.4.3/pkg/event/event.go#L93-L106)). That path also has a spam filter, 25 events per object and then one per 5 minutes, and it folds more than 10 similar events within 10 minutes into one "combined" event ([`tools/record/events_cache.go`, lines 36–48](https://github.com/kubernetes/client-go/blob/v0.35.3/tools/record/events_cache.go#L36-L48)). Accessed 2026-10-31.

So a test checks for at least one event of a type and reason on a resource, never for a count or for every note, in the Events the API holds. The raised-events counter (Metrics, Controller metrics) counts hand-overs exactly, and is where a count or an absence is checked. The message a test must see is checked on the condition. The order of a recorder call against a status write is checked on one shared sequence: the in-memory recorder and a client interceptor on status writes number their calls from one counter. The API cannot show that order.

- **When it fires.** `HeartbeatMissed` fires when the heartbeat goes stale, and then at most once an hour while it stays stale (Repeating conditions). A Provider's return shows in its effective readiness, an Instance's in `AgentUnreachable`.
- **A Provider never read** (science-agent ruling, 1 Nov 2026, for #111). A Provider with no `lastSuccessfulStatusRead` at all raises `HeartbeatMissed` once its `creationTimestamp` is older than `ProviderReadyStaleness`, through the same hourly gate. An observer that never starts has stopped.
- **An absent front `Lease`** (science-agent ruling, 1 Nov 2026, for #111), when the front was not started or not configured, raises no event. `hpcburst status` shows the front as absent only when the host has no front configured; a configured front with no `Lease`, one that never started or has stopped, is shown unhealthy (science-agent ruling, 1 Nov 2026, for #147; HBEP-11).
- **The lifecycle controller's `/readyz`** (science-agent ruling, 1 Nov 2026, for #111) fails until its caches have synced and it leads its `Lease`. Alpha runs one replica, so a controller that does not lead cannot act. A copy that does not lead, as during a hand-over, has its caches synced and is shown "not leading" by its two named checks, `caches` and `leading` (HBEP-11, Single-user host). `/healthz` stays liveness. `hpcburst status` reads `/readyz` for the controller's health.
- **`--leader-elect=false`,** a development and test mode of the lifecycle controller, holds no `Lease`, so it emits no `ObservationGap` (science-agent ruling, 1 Nov 2026, for #111). Its `/readyz` then needs only synced caches. The `lifecycle` `Lease` is then absent, and the front raises no `HeartbeatMissed` for it, as for an absent front `Lease`.
- **Events about cluster-scoped objects land in `default`.** Providers and PlatformProfiles are cluster-scoped (`api/v1alpha1/provider_types.go` and `platformprofile_types.go`, `kubebuilder:resource:scope=Cluster`), so their events are written in the `default` namespace (What the recorder merges and drops). Each emitter's RBAC allows creating events there.
- **A probe failure is not a prober failure.** `PathProbeFailing` (`degraded`) says a path is bad (HBEP-6). `HeartbeatMissed` (`failing`) says the prober stopped.
- **The front's `Lease`** gives front-level events a namespaced resource to regard, and gives the front a heartbeat. It follows Kubernetes' node heartbeats, where each kubelet renews its own `Lease` (Prior art). The front's recorder scheme registers `coordination.k8s.io/v1`, since client-go drops an event whose object reference it cannot build.

**Gaps after a restart.** At start, the lifecycle controller and the front each read their `Lease`'s previous `renewTime` before taking the `Lease`. Once they hold it, each emits one `degraded` event with reason `ObservationGap`, regarding it, whose message names that `renewTime`, the gap's start. The Provider managers emit none in alpha (open question 14); in beta each emits one regarding its `provider-<name>` `Lease` (Allocation events). A first start, with no previous `Lease`, emits none, and so does a lifecycle controller run with `--leader-elect=false`, which holds no `Lease` (Observers). Missed transitions are not replayed; status is the truth.

**Retention.** The launcher passes `--kube-apiserver-arg=event-ttl=168h` to k3s (HBEP-11, amendment of 31 Oct 2026). The facts behind it, all accessed 2026-10-31:
- kube-apiserver keeps events for `event-ttl`, 1 h by default ([`pkg/controlplane/apiserver/options/options.go`, lines 129 and 162–163](https://github.com/k3s-io/kubernetes/blob/v1.36.5-k3s1/pkg/controlplane/apiserver/options/options.go#L129)). The same TTL backs `events.k8s.io` ([`pkg/registry/events/rest/storage_events.go`, line 55](https://github.com/k3s-io/kubernetes/blob/v1.36.5-k3s1/pkg/registry/events/rest/storage_events.go#L55); [`pkg/controlplane/instance.go`, line 434](https://github.com/k3s-io/kubernetes/blob/v1.36.5-k3s1/pkg/controlplane/instance.go#L434)) and is set on every event's key ([`pkg/registry/core/event/storage/storage.go`, lines 42–44](https://github.com/k3s-io/kubernetes/blob/v1.36.5-k3s1/pkg/registry/core/event/storage/storage.go#L42-L44)).
- k3s passes `--kube-apiserver-arg` values to the apiserver ([`pkg/daemons/control/server.go`, line 277](https://github.com/k3s-io/k3s/blob/v1.36.5%2Bk3s1/pkg/daemons/control/server.go#L277); [`pkg/util/args.go`, line 27](https://github.com/k3s-io/k3s/blob/v1.36.5%2Bk3s1/pkg/util/args.go#L27)) and sets no `event-ttl` of its own: `server.go` has none. Its apiserver talks etcd3 to the datastore's endpoint (`server.go`, lines 340–345). SQLite, through kine, is the default datastore ([k3s datastore docs](https://docs.k3s.io/datastore)).
- kine v0.16.5, which k3s v1.36.5+k3s1 uses ([`go.mod`, line 111](https://github.com/k3s-io/k3s/blob/v1.36.5%2Bk3s1/go.mod#L111)), grants a lease whose ID is its TTL ([`pkg/server/lease.go`, lines 13–19](https://github.com/k3s-io/kine/blob/v0.16.5/pkg/server/lease.go#L13-L19)), and deletes each leased key once its lease has elapsed ([`pkg/ttl/ttl.go`, lines 1–8 and 143–150](https://github.com/k3s-io/kine/blob/v0.16.5/pkg/ttl/ttl.go#L1-L8)).
- **A restart restarts the clock.** kine computes each expiry as now plus the TTL when it first sees the key, and at its start it seeds every leased key that way (`ttl.go`, lines 103–117 and 168–180). So an event lives at least 7 days, and up to 7 days after the host's last restart.
- **Store growth** is small at alpha scale. Merging seldom applies (above), so each emission counts as one stored object, of at most about 2 kB with its 1,024-byte note. Assume 20 Instance lifecycles a day at about 6 events each, and 20 persisting conditions emitted once an hour (Repeating conditions): about 600 events a day, under 10 MB over 7 days. Even 5,000 a day is about 70 MB. These are estimates, not measurements.

**In the durable log (beta)** (open question 6; amended 2026-11-16). Per stream (The durable log):
- **Events are kept for the grant,** by the audit log's rule (owner, 14 Nov 2026; HBEP-10, open question 10). The stream has no `MaxAge` and no `MaxMsgs`, and nothing in the framework deletes an event. `hpcburst eventlog prune` (proposed; stable, with HBEP-10's `hpcburst audit prune`) purges the events older than the grant's end only after a person confirms at a terminal, and none while no grant end is recorded (HBEP-10, open question 12).
- **Usage is a rolling copy** (the science agent's decision, 16 Nov 2026). The files are the record and keep every record for the grant's life (open question 6), so `HB_USAGE` keeps only the latest records up to its cap, with `discard: old`: at the cap its oldest messages go to make room. The owner's never-evict rule binds the events only.
- **Compressed once cold.** Each stream sets `compression: s2`, nats-server's `StreamConfig.Compression`, whose values are `s2` and `none` ([`server/stream.go`, line 71](https://github.com/nats-io/nats-server/blob/v2.15.2/server/stream.go#L71); [`server/filestore.go`, lines 143–157](https://github.com/nats-io/nats-server/blob/v2.15.2/server/filestore.go#L143-L157)). The file store compresses a message block when it fills and the next starts: "We've now reached the end of this message block, if we want to compress blocks then now's the time to do it" (`filestore.go`, [lines 5271–5279](https://github.com/nats-io/nats-server/blob/v2.15.2/server/filestore.go#L5271-L5279)). It writes the compressed copy to a temporary file, syncs it and renames it over the block (lines 8123–8251). So only the block being written stays plain, as only the audit file being written does (HBEP-10, Audit). Accessed 2026-11-16. S8 did not run S2 under `sync_interval: always`; beta measures it (Test plan).
- **Events: capped, never evicted** (proposed). `HB_EVENTS` has a `MaxBytes` and `discard: new`, under which nats-server returns "maximum bytes exceeded" once the limit is reached ([`server/store.go`, lines 51–52](https://github.com/nats-io/nats-server/blob/v2.15.2/server/store.go#L51-L52), accessed 2026-11-16). A full stream refuses new events and keeps every old one. S8's `discard: old` would delete events silently. A full events stream counts its refusals as events not logged (The durable log, When it is down), and `hpcburst status` reports "degraded: event log full", naming the remedy: raise the events cap, a launcher setting applied at the log's next start, or, at stable, prune after a person confirms. Retention per event class is HBEP-10's, at stable, within this rule (HBEP-10, open question 8).
- **The caps** are a launcher setting, 2 GiB per stream by default (the science agent's decision, 16 Nov 2026, as sizing). They count logical bytes, each record's subject, headers and payload plus a fixed overhead, not the compressed blocks ([`server/filestore.go`, lines 5409–5411 and 10213–10215](https://github.com/nats-io/nats-server/blob/v2.15.2/server/filestore.go#L5409-L5411), accessed 2026-11-16), so compression saves disk but does not stretch a cap. At each start `eventlog` sets each existing stream's `MaxBytes` to the launcher's setting. A lower cap evicts nothing from `HB_EVENTS`, since nats-server enforces a lowered byte limit only under `discard: old` (`enforceBytesLimit`, [lines 6036–6039](https://github.com/nats-io/nats-server/blob/v2.15.2/server/filestore.go#L6036-L6039)); the stream refuses new events until it is under the cap. A lower cap on `HB_USAGE` drops its oldest records at once.
- **The caps must fit the disk** (the science agent's decision, 16 Nov 2026). The free-space floor is a launcher setting, by default 15 GB, the floor kept for builds on the alpha host. `up` starts the log only when the free space on its store's file system, less what the streams can still grow (the caps' sum less their bytes) and less what the upgrade's copy of the store can still add (the caps' sum less the size of the previous upgrade's copy, which the next one replaces; The durable log, Backup and restore), stays at or above the floor. With both caps at 2 GiB, an empty store and no copy, that is at least 23.59 GB free: 15 GB plus 8.59 GB, twice 4 GiB.
- **A log refused for space** (the science agent's decision, 16 Nov 2026). The control plane starts without it, loudly: `hpcburst status` reports "degraded: event log not started", naming the free space, the caps and the floor, with the exit code 0; and each emitter raises `EventsNotLogged`, as when the log is down (The durable log, When it is down). The launcher keeps the recorded `--event-log` choice and checks the space again at each health pass, and starts the log once it fits.
- **Kubernetes Events keep their 7 days.** The log, not the API store, is where an event outlives `event-ttl`.
- **Size.** Events: about 600 a day (above), of at most about 2 kB each, so about 1.2 MB a day and 0.45 GB a year before compression; a 2 GiB cap holds about 4.9 years. Usage: the files' sizing (Usage records, Sizing), about 85 MB a day at the planning rate, so the 2 GiB rolling copy holds about the latest 25 days, compressed or not, since the cap counts logical bytes. Compression only lowers the disk the store takes: gzip shrank the synthetic records about 8 times, and S2's ratio is measured in beta. These are estimates, not measurements.

### Metrics

**Exposition.** Both components serve Prometheus's text format on loopback, with no authentication and no credential in any label:
- the front at `GET /metrics` on its `/healthz` listener (the launcher's port base + 4);
- the lifecycle controller from controller-runtime's metrics server, bound on loopback at the port base + 12, a new offset of the launcher's block, proposed by this HBEP (`docs/development.md`, Runtime conventions). Its collectors register on controller-runtime's registry, so the controller's own work-queue metrics come with them.

The library is Prometheus client_golang, already in `go.mod` at v1.23.2 as an indirect dependency. Names follow Prometheus's conventions: one application prefix, base units in the name, `_total` on counters, and ratios from 0 to 1 named `_ratio` ([naming practices](https://prometheus.io/docs/practices/naming/); [source, lines 16–38 and 107–112](https://github.com/prometheus/docs/blob/bf977977d5f8d90923929577842d6d0c13bb5295/docs/practices/naming.md#L16-L38); accessed 2026-10-31).

**Engine gauges per Instance.** The lifecycle controller exports them at scrape time from each worker's latest health sample (HBEP-7, The allocation agent). A Prometheus collector builds the series from the samples it holds, so a series exists only while its value is known. Each field aggregates the engine's series across its `engine` labels: counters and counts are summed, and KV-cache usage, a fraction, takes the maximum. A value that is NaN or infinite, or missing from any one contributor, makes that field's aggregate unknown, never a partial total; for the HTTP status counts that is the whole map. **Unknown samples.** Three ways to show an unknown sample in Prometheus were compared:
- **NaN.** The text format allows it ([exposition formats, line 96](https://github.com/prometheus/docs/blob/bf977977d5f8d90923929577842d6d0c13bb5295/docs/instrumenting/exposition_formats.md#L96)). But PromQL arithmetic follows IEEE 754, so one NaN turns a `sum` or `avg` over a deployment into NaN, while `min` and `max` skip it silently ([operators](https://prometheus.io/docs/prometheus/latest/querying/operators/); [source, lines 41–44 and 488–491](https://github.com/prometheus/prometheus/blob/ef78ff64267724c8ecd1a1283cad49b365a8b67f/docs/querying/operators.md#L41-L44)). It either poisons the aggregate or hides the gap. Rejected.
- **A stale marker.** Prometheus writes it itself when a series it scraped before is missing from a scrape; no exporter can write one ([staleness](https://prometheus.io/docs/prometheus/latest/querying/basics/#staleness); [source, lines 565–593](https://github.com/prometheus/prometheus/blob/ef78ff64267724c8ecd1a1283cad49b365a8b67f/docs/querying/basics.md#L565-L593)). From the exporter's side it is the absent series, and it carries no reason.
- **An absent series plus an explicit gauge.** Chosen. Aggregates skip the missing value without being poisoned, and the gauge says that a value is missing and why.

All accessed 2026-10-31. So:
- an engine series is absent while its value is unknown: while the agent is unreachable, while `Health.MetricsFresh` is false (HBEP-7, Only fresh gauges act), or while the engine does not report that metric;
- `hpcburst_instance_metrics_unknown{instance_uid, worker, metric, reason} 1` stands in for each absent one, with `metric` the `hpcburst_` name and `reason` one of `agent_unreachable`, `stale` or `not_reported`;
- the share of unknown samples is then a query: the count of `hpcburst_instance_metrics_unknown` series over the count of engine metrics expected per worker.
- **A collector whose read fails** exposes none of its series and sets `hpcburst_collector_success{collector} 0`, which is 1 after a successful read, following node_exporter's `node_scrape_collector_success`. So `/metrics` answers even then, and "none" is told from "could not read". In alpha two collectors read at scrape time. `accounting` reads the Allocation list. `instances` reads the Instance inventory from the informer cache (below), and the engine values from the reports held in memory. Its inventory read is the Instance list and the cache reads of each Instance's Allocation, Provider and PlatformProfile; any error other than not-found fails it, and `instances` then exposes no Instance series and sets `hpcburst_collector_success{collector="instances"} 0`. A reader takes the share of unknown samples only while that gauge is 1: 0 is a failed read, and the gauge absent on every copy means no copy serves (below). A missing or stale report shows per worker as below (science-agent rulings, 1 Nov 2026, for #111 and from PR #142's review; the `instances` collector's success gauge, 6 Nov 2026, for #249);
- an Instance with no report yet, new or after the controller restarted (reports are held in memory, HBEP-7), has, for each worker of its desired state (in alpha one, `worker-0`; in beta the Instance's `launch.workers` of them, HBEP-7, Several workers), every engine metric as `hpcburst_instance_metrics_unknown` with reason `stale`, unless `agent_unreachable` applies; `not_reported` is kept for a metric the engine does not export (science-agent ruling, 1 Nov 2026, for #111). An Instance still pending, with no agent yet, is one of them. The leader builds this inventory from its informer cache, which HBEP-11 starts before the election, not from its reconciles. So after a leadership change the new leader lists every live Instance at once, each unknown until its first report to that leader, and a share-of-unknown query reads them as unknown rather than 0 over 0. A copy exports these series, the accounting series and every collector's `hpcburst_collector_success` only while it serves: `/readyz`'s `leading` passes (it holds the `lifecycle` `Lease`, or runs with `--leader-elect=false`) and its `caches` passes. Otherwise it exports no `hpcburst_` series; controller-runtime's own series stay, and `leader_election_master_status{name="lifecycle"}` tells a standby (0) from a broken copy. So one copy exports at a time, except during the overlap of one hand-over, which a `Lease` does not fence (HBEP-11). Prometheus's staleness can also show a short duplicate or gap across a hand-over, depending on scrape order (science-agent rulings, 2 and 6 Nov 2026, for #249);

**Which Instances have series** (science-agent ruling, 1 Nov 2026, for #111). The names are this HBEP's:

- each worker in the Instance's latest report has, for each engine metric, either that metric's series or `hpcburst_instance_metrics_unknown` with its reason. The reason is `stale` while the worker has no fresh read, for example while it starts, unless `agent_unreachable` applies;

**Raised events** (science-agent ruling, 8 Nov 2026, for #256). A test that lists Events cannot prove an event was not raised, because client-go's event recorder delivers asynchronously. So each controller counts the events it hands to its recorder.
- **The counter:** `hpcburst_events_raised_total{controller, reason, action, type}`, with the help text "events handed to the event recorder, not events delivered: the recorder may aggregate or drop them".
  - `controller` is `lifecycle`, `provider-<Provider name>` (a batch or a managed Provider; each runs its own manager) or `front`.
  - `action` is HBEP-8's type (Events), or `none` for an event with no action.
  - `type` is `Normal` or `Warning`.
  - `reason`'s values come from each controller's own source, all constants, so the labels stay bounded:
    - `lifecycle` and `front`: the Reasons table;
    - a managed Provider: the managed catalog controller's reasons (Events);
    - a batch Provider: its own reasons, which the drift guard lists as code-only, plus crossplane-runtime's managed reconciler reasons.
- **Counting:**
  - The count rises in the same call that hands the event over, before the recorder's queue, so it is final once the emitting code has returned. The help text covers the events a recorder then drops.
  - The count is taken by a wrapper where each recorder is built, so no emit site can raise an event uncounted. Each copy of a manager has one counter, never a package-level one.
  - **Series are created at 0** for every reason, action and type that `lifecycle`, `front` and a managed Provider can raise, so an event never raised shows a real 0 (Unknown samples, on counts of the framework's own events). A batch Provider's untyped series appear at its first event.
- **Export:**
  - The controller process's counts are on the lifecycle controller's `/metrics`, the Provider managers' included, since they bind no metrics port. Only the serving copy exports them, like the other `hpcburst_` series (Unknown samples); every controller that raises events in that process runs only on the copy that leads `lifecycle`.
  - The front's counts are on the front's own `/metrics`, which also gains the process collector's `process_start_time_seconds`.
  - **The relay keeper (beta, HBEP-6)** exports no metrics of its own and binds no port. The serving copy of the lifecycle controller reads the keeper's relay states and ends over its socket, and exports them through its serving collector, so a non-serving copy still exports no `hpcburst_` series:
    - `hpcburst_relays{provider, channel, state}`, a gauge of relays by state (`up`, `retrying`, `final`); a relay waiting for its pair of slots counts as `retrying`;
    - `hpcburst_relay_restarts_total{provider, channel}`, a counter of relay starts after the first;
    - `hpcburst_relay_sets_refused_total{provider, reason}`, a counter of desired sets and acknowledgements the keeper refused (`epoch`, `login_host`);
    - `hpcburst_relay_keeper_epoch`, a gauge of the keeper's `E`, so that a reset of the keeper's counters shows;
    - `hpcburst_collector_success{collector="relays"}`, in keeper mode only, so that a failed read of the keeper shows as 0 and not as no relays.

    A final end re-reported after a restart raises no second `RelayFailed`: the event is raised once, when the mark is newly written.
- **Proving that an event was not raised** takes all four of these. Otherwise the result is inconclusive, never a pass:
  1. **The first read comes before the change** that could raise the event.
  2. **Both reads come from the same process while it serves:** `process_start_time_seconds` is unchanged, and on the lifecycle controller every `hpcburst_collector_success` series is present (two, or three in beta's keeper mode). A restart or a hand-over between the reads makes the check inconclusive.
  3. **Between the reads, a pass of the emitting loop, for the same subject, observed the change and finished emitting,** and that pass started after the time the event would have been due (for example, `tunnelOrphanGrace` for `TunnelOrphaned`). The barrier per loop:
     - **the lifecycle reconciler:** a later `status.lastReconcileTime` write of the same ModelDeployment. It runs several workers, serialized per key only, so a pass of another ModelDeployment proves nothing;
     - **the tunnel-state reader:** a condition write of a later pass;
     - **a managed Provider's catalog controller:** the next pass's write;
     - **the front's `Lease` keeper:** the next beat's `renewTime`;
     - **the observer, the gap emitter and the front's request path:** none on `main` (Code that differs). For these, absence is proven by a test hook that signals after the emitter's recorder call, or by a test that calls the emitting function itself and reads the counter after it returns.
  4. **Other sources of the same series are quiet:** for example, `HeartbeatMissed` from the observer shares `lifecycle`'s series with the reconciler's.

### Usage records

**The store in alpha** is the front's sink on the control-plane host, with HBEP-5's fields (HBEP-5, Usage records). It is also the attribution log (HBEP-9).

**Durability.**
- `Write` returns only after the batch that holds its record has been written and synced, and returns that batch's error. So each record is synced before the request is reported done to the sink's caller. Records that end together share one write and one sync.
- The sink keeps writing after a failure, and each later batch reports its own result. An error is never sticky.
- When a new file is created, its directory is synced too, so the file survives a crash.
- **Gaps.** A clean stop syncs the next unused counter after the last one assigned (HBEP-5, Counter), so it leaves no gap of its own. The counters of a batch that failed were assigned, so they still show as a gap.

**Failures are never silent.** A failed write or sync of a batch, a full disk included, or a failed counter-block reservation:
- adds the records it lost to `hpcburst_usage_write_failures_total`. A failed reservation drops its record before it has a counter. When the new block end never reached the disk, it leaves no gap, and the failure counter is its only trace. When its persistence is uncertain, as when the directory sync after the rename fails, the new end may survive, and a restart then skips that block: a gap;
- raises a `failing` event, reason `UsageWriteFailed`, regarding the front's `Lease`, at the first failure after a success, and then at most once an hour while failures last (Repeating conditions);
- is stated in the front's readiness: `/healthz` carries `usage` with `state` (`ok` or `failing`), `lostRecords`, `since` and the last error, and `hpcburst status` reports the front as "degraded: usage writes failing" while it says `failing`: the exit code stays 0, the overall health stays `healthy`, and only the front's line says degraded. It is not a readiness failure (science-agent rulings, 31 Oct 2026, for #112). Until the front holds its `Lease`, a failure is counted, logged and shown in `/healthz`, and the `UsageWriteFailed` event follows once the `Lease` is held; it never falls back to regarding a ModelDeployment, which a usage failure is not about.

**The front keeps serving** while usage cannot be written (open question 13). `/healthz` keeps answering 200 for it, so a usage failure never makes anything restart the front. A failed write leaves the log at its last whole line, as PR #95 does.

**Rotation keeps every file.**
- Records go to `usage-<YYYY-MM-DD>.jsonl` in `usageDir` (a name proposed by this HBEP), named by the UTC day of the write. The first record after midnight UTC opens the next day's file. A closed file is never written again, except by the repair below.
- Nothing in the framework deletes a file, and the only rewrite is the repair at open: it cuts a partial last line off the newest file, whatever its day, and touches no other. Files are kept for the grant's life. The counter runs across files, so readers order records by it.
- A legacy `usage.jsonl`, written before rotation, is the newest file while no daily file exists, so the repair applies to it; after that it is never written again.

**Sizing.**
- A record is about 0.7 to 0.9 kB: 725 bytes on average for 20,000 synthetic records with realistic name lengths, and 853 bytes for one with long names (measured 31 Oct 2026 on synthetic data). gzip shrinks the synthetic records about 8 times.
- No source gives alpha's request rate. The planning figure is an assumption, 100,000 requests a day, for one user (HBEP-11, open question 8):

| Requests per day | Per day | Per 30 days | Per 365 days |
|---|---|---|---|
| 10,000 | 8.5 MB | 0.26 GB | 3.1 GB |
| 100,000 (planning) | 85 MB | 2.6 GB | 31 GB |
| 1,000,000 | 850 MB | 26 GB | 310 GB |

- The alpha host's home file system is 98 GB. It had 37 GB free at 20:35 UTC on 31 Oct 2026, at 61% used, after reaching 99% earlier the same day (L-12.2).
- At the planning rate a year of records fits in that space. At ten times the rate it fills in about six weeks. `hpcburst_usage_dir_free_bytes` shows the trend.
- **Not needed for alpha:** compressing closed files, or moving them off the host. In beta the durable log's copy is compressed (Retention, In the durable log), and the files stay plain, as the record, until the log becomes the record (The durable log).

### The durable log (beta)

Decided for beta (open question 11; amended 2026-11-16). Each part is marked by its source: spike S8 (issue #25, PR #28), an existing rule, or proposed by this amendment. Status stays the truth, and the usage files stay the record.

**Where it runs** (proposed).
- **One process,** `hpcburst-controller eventlog`, a subcommand of the controller binary, as the relay keeper is (HBEP-11, Single-user host). It embeds nats-server's `server` package, as S8's `jsnode` did, so its version is pinned in `go.mod`: nats-server v2.15.2, S8's, with nats.go v1.55.0 for the clients. v2.15.3 (11 Nov 2026) is untested here.
- **The launcher starts it** with `hpcburst up --event-log` (proposed), before the controllers and the front, records the choice in its state and keeps it across `upgrade`, as it does the bulk path. It records the process by process ID plus start time, judges its liveness through a pidfd, restarts it when it exits, and stops it last (HBEP-11, Single-user host). Without `--event-log` no log runs, and nothing publishes. It refuses to start the log when the caps would not fit the disk (Retention, In the durable log).
- **Opt-in in beta** (the science agent's decision, 16 Nov 2026). The log is not a contingency, so the rule that contingencies stay on (Notes) does not apply to it. Whether it is on by default is decided at stable, once it is proven.
- **Loopback only:** clients at the port base + 16, and nats-server's monitoring at base + 17, whose `GET /healthz` is the health check. On a single server that check makes "sure the streams were recovered" ([`server/monitor.go`, lines 3577 and 3743](https://github.com/nats-io/nats-server/blob/v2.15.2/server/monitor.go#L3743), accessed 2026-11-16), so the launcher asks without `js-enabled-only`, which checks only that JetStream is on. The block grows to base..base+17, and +13 to +15 stay the bulk path's, used or not.
- **Its store** is `<state>/eventlog/`, mode 700, on the host's disk.
- **It checks what it parsed** (S8, Finding 8: a misspelt setting looks like the default until power fails). At start it reads back the options nats-server parsed, `SyncAlways` among them ([`server/opts.go`, lines 2715–2718](https://github.com/nats-io/nats-server/blob/v2.15.2/server/opts.go#L2715-L2718), accessed 2026-11-16), and each stream's configuration. It creates a stream that is absent, and sets an existing stream's `MaxBytes` to the launcher's cap (Retention, In the durable log). It serves only when `sync_interval` is `always` and both streams then have this HBEP's settings. Otherwise it exits naming every difference, and `hpcburst status` reports the log unhealthy.

**Settings** (S8, Short answer): one file-backed replica, limits retention, `sync_interval: always`, a two-minute duplicate window with the event's id as `Nats-Msg-Id`, and direct get on. `HB_EVENTS` differs from S8 in `discard: new`; `HB_USAGE` keeps S8's `discard: old`, as a rolling copy (Retention, In the durable log).

**Streams** (proposed, with S8's subject per resource):

| Stream | Subjects | One message | Its `Nats-Msg-Id` | Writers |
|---|---|---|---|---|
| `HB_EVENTS` | `hb.ev.<kind>.<uid>`: the regarding object's kind in lower case, and its UID | one typed event, a CloudEvent 1.0.2 in structured JSON | the event's id | each controller and the front, for the events they raise |
| `HB_USAGE` | `hb.usage` | up to 256 usage records, as the files' lines, byte for byte | `usage-<first counter>-<last counter>` | the front |

- **Subjects by UID, not name.** A Kubernetes name may "contain only lowercase alphanumeric characters, '-' or '.'" ([Object Names and IDs](https://github.com/kubernetes/website/blob/8a342c522c21f05564881573fcca7d5910a2ebb5/content/en/docs/concepts/overview/working-with-objects/names.md), accessed 2026-11-16), and S8's layer refuses `.` in a subject. A reused name would also join an old object's history (HBEP-10, open question 11). A UID has neither problem.
- **The envelope** (HBEP-10, Notes; S8): `specversion` `1.0`; `id`; `source` `/hpcburst/<controller>`, with the raised-events counter's `controller` value; `type` `io.hpcburst.event.v1`; `subject` `<kind>/<namespace>/<name>`, or `<kind>/<name>` for a cluster-scoped object; `time`, the event's `eventTime`; and `data` with the Kubernetes Event's fields: `action`, `reason`, `type`, `regarding` and `related` with their UIDs, `note` and `reportingController`. Both copies come from one recorder call, so they agree.
- **The event's id.** An Allocation event that marks a transition (Events, Allocation events) has the id `<Allocation UID>/<reason>/<fact>`, where the fact is the status value that marks the transition. So a transition raised again after a failed status write keeps its id, and a second transition with the same reason gets its own:
  - the attempt's number for `JobSubmitted` and `JobAdopted`;
  - the restart count for `HoldLifted`, `JobStarted` and `Requeued`;
  - the end time for `JobEnded`, `AllocationEndedEarly` and `AllocationFailed`;
  - `absentSince` for `JobLost` and `JobReappeared`, and the hard end for `HardEndNear`;
  - the start of the condition that shows it for `SubmittedAsOther`, its own condition, and `AllocationRefused`, the `Ready` condition turned False.

  Every other event gets a fresh UUID per recorder call, kept across its publish retries: a repeating condition's events among them (`AdminHold`, `JobCompleting`, `EventsNotLogged`, `HeartbeatMissed` and their like), since each emission is an event of its own. The id never holds a job ID.
- **Only typed events.** An event without HBEP-8's type, crossplane-runtime's own and HBEP-4's diagnostics, stays in the cluster's own events alone, since its note may name a job ID (Allocation events, No job ID in a note).
- **Usage in batches** (S8, What this means for the HBEPs). Under `always` one node acknowledges about 1,000 publishes a second on S8's disk, so the front batches records when they arrive faster than a few hundred a second. At the planning rate, about 1.2 records a second (Usage records, Sizing), a message holds one. 256 records of 0.9 kB stay under nats-server's default maximum payload of 1 MiB ([`server/const.go`, line 94](https://github.com/nats-io/nats-server/blob/v2.15.2/server/const.go#L94), accessed 2026-11-16).

**Who writes** (proposed).
- **Events:** a publisher in the wrapper where each `events.k8s.io` recorder is built, beside the raised-events counter (`internal/eventcount`), so no emit site raises a typed event that skips the log. The wrapper hands the event to the Kubernetes recorder as before, and to a queue of 1,000 per process, from which a goroutine publishes and retries. The emit site never waits for the log.
- **Usage:** the front's forwarder takes only what the sink has synced: from the sink after each sync, and from the files after a restart or an outage. So the log never holds a record the files lack, and serving never waits for the log.
- **The token.** The launcher writes the log's configuration, mode 600, with a token, and the same token to `<state>/eventlog/token`, mode 600, which the controllers and the front read. The log refuses a client without it.

**Delivery** (S8, Design of the layer, Publish; Findings 4 and 6): at least once, de-duplicated by `Nats-Msg-Id` within the two-minute window. S8 dropped an acknowledgement after the store, and the retry stored one copy. A retry after the window stores a second copy, so a reader de-duplicates by the event's id, and usage by its counter (HBEP-10, Notes). Exactly once is not claimed; S8 did not measure it.
- **The usage forwarder resumes from the log** (proposed). At start, and after any failed or unacknowledged publish, it reads the stream's last message by direct get, and publishes from the next counter in the files. A retry therefore never duplicates a batch the stream already holds. The files are the record, so this also re-publishes a tail that a power loss took from the log. That is the lost-tail case HBEP-10 leaves undetectable for events (HBEP-10, Notes); usage cannot lose to it.

**When it is down** (proposed).
- **Usage loses nothing.** The files keep every record, as in alpha, and `Write` never depends on the log. The forwarder waits and catches up. `hpcburst_usage_unlogged_records`, a gauge, is the last synced counter minus the last counter the log acknowledged. `/healthz`'s `usage` block gains `log`, `connected` or `down`, and `loggedCounter`. `hpcburst status` reports the front as "degraded: usage log behind" while the log is down or the gauge has stayed above 0 for 5 minutes, with the exit code 0, as for a failing sink.
- **Events can miss the log, never silently.** Kubernetes Events go on as in alpha. An event the queue cannot hold, or whose retries run out, is counted in `hpcburst_events_unlogged_total{controller}`. At the first loss after a success, and then at most once an hour while losses last (Repeating conditions), the emitter raises `degraded`, reason `EventsNotLogged` (proposed), regarding its own `Lease` (`lifecycle`, `front` or `provider-<name>`), with the count and since when in its note. It raises one more with its first publish after the log returns, so the log itself shows the span it lacks. `EventsNotLogged` joins the Reasons table with its code.
- **A crash** loses the events still queued in that process; its next start's `ObservationGap` names the gap (Gaps after a restart).
- **Nothing waits on the log.** A failed publish never fails a reconcile or a request.

**Backup and restore** (proposed; HBEP-11, Single-user host).
- Before each upgrade, once the log has stopped last, the launcher replaces the previous upgrade's copy of `<state>/eventlog/`, beside its copy of the SQLite file: it removes the old copy, then copies the store. A failed copy stops the upgrade before anything changes, and the live store is untouched. The floor binds here too: the launcher refuses the upgrade when the free space, plus the old copy it frees, less the store's size, would fall below the floor, naming the sizes (Retention, In the durable log). Copies never pile up.
- `restore` puts both back. The log then ends at the backup's last message, and the events raised since are lost from it, as they are from the restored API store. Usage loses nothing: the forwarder re-publishes from the files every record after the restored stream's last counter. For HBEP-10's cursors (stable), a restore is rewritten history (S8, Finding 7), and the subscriber re-reads status.

**Readers** (owner, 15 Nov 2026, for the audit log; HBEP-10, open question 10): whoever may read the launcher's state directory, where the store and the token live. That is the person, and agents that share the person's Unix user. Every client needs the token, and the listener is on loopback.

**The files stay the record** (proposed; accepted by the science agent, 16 Nov 2026). S8 did not test power loss or a kernel crash, the only cases where `sync_interval: always` differs from the default (S8, Unknown), while the files have their sync-before-done and counter-gap rules (Usage records). So in beta the log is a copy, and HBEP-5's beta criterion "usage records go to HBEP-8's log" is met by the forwarder. Making the log the record, and then compressing or dropping the files, is a later amendment. It needs a power-loss test of the log first (S8 names dm-flakey or a write-dropping FUSE passthrough), and a month in which the log and the files agree.

### Provider accounting

Alpha counts **allocated** time, from the scheduler's accounting: elapsed time times the GPUs or CPUs the scheduler allocated. Every number is labelled "allocated, not billed". Beta adds the scheduler's own billing, and totals per grant (Billing, below), under the same label.

- **What HBEP-4's plugin reads.** One accounting read per execution, after it is first seen started, retried on failure, and none at delete (HBEP-4, The Slurm dialect, Accounting). Its fields:
  - `tres.allocated`: the entry of type `cpu`, and the entry of type `gres` named `gpu`, from that read;
  - for the final state: `start_time` and `end_time` when the queue listing gives it, else accounting's `time.elapsed`, in seconds;
  - every record `-D` returns for the job, one per execution, to see whether it was requeued.
  - S7 captured `time.elapsed` and the `cpu` entry of `tres.allocated` from a real CPU job (`spikes/s7/slurm-json-real.md`). The `gres`/`gpu` entry's shape is the fake Slurm's (`internal/slurm/fakeslurm`), and is verified on the first GPU job (Graduation criteria).
  - The same list carries a `billing` entry, the site's own weight. It is not read in alpha; beta reads it (Billing, below).
- **Where the numbers live.**
  - **A live Allocation's status:** `status.atProvider.accounting` (proposed names) holds `allocatedCPUs`, `allocatedGPUs`, `elapsedSeconds` and `readTime`. While the job runs, elapsed time runs from the scheduler's start time to `readTime`; once it has ended, it is the queue listing's `end_time` minus `start_time` when the final state came from the queue listing, and otherwise accounting's `time.elapsed`, for its one execution. **A requeued job's hours are unknown:** a job with more than one execution, a `restart_cnt` above 0, or `Requeued` already seen in status. The plugin submits `--no-requeue`, but a site setting such as Slurm's `ForceRequeueOnFail` can still requeue a job after a launch failure; any detected requeue already fails the Allocation (HBEP-4), so per-execution sums are not needed in alpha (science-agent ruling, 31 Oct 2026, for #113). On data_parser v0.0.40, which has no `restart_cnt`, a reply that shows only the last execution reveals a requeue only through `Requeued` already in status. The status's accounting is written only when the allocated counts change, or at most once a minute, not on every poll. GPU-hours are `allocatedGPUs × elapsedSeconds / 3600`, and CPU-hours likewise.
  - **A pending Allocation** has no `accounting`: its hours are unknown, never 0.
  - **The kept record.** When the Allocation's last job has ended and no longer carries `COMPLETING` (HBEP-4, Core operations, Phases), and before its finalizer is removed (HBEP-4: the finalizer stays while any job with the tag is live, a completing one included), the Provider controller writes one record that outlives the Allocation: a `ControllerRevision` named `acct-<Allocation UID>` in the Allocation's namespace, with no owner reference (HBEP-11, Records outlive deletion). Its data holds the Provider, the partition, the tag, the job IDs, `allocatedCPUs`, `allocatedGPUs`, `elapsedSeconds`, the start and end times, and `basis: allocated`. It is created once, if absent, and never rewritten. The record step makes no extra read at delete: it uses the deleting pass's reads. Once the tag lookup has succeeded and shows no live job, the finalizer waits for the recorded job's final accounting read for at most `lostGrace` (HBEP-4), whether that read is missing or keeps failing, then writes the record with what is known, each missing field marked unknown. A failed tag lookup or `Observe` keeps the finalizer, since a failed read is unknown, never absence, and a tagged job may still be live (HBEP-4, Delete). So the record never blocks deletion indefinitely, and needs no scheduler call at delete; a job stuck in `COMPLETING` does block it, a known risk of HBEP-4 (Risks). A `Lost` job is recorded with its elapsed time unknown.
  - **Metrics:** the lifecycle controller exports `hpcburst_allocation_allocated_gpu_seconds{provider, namespace, allocation}` and `hpcburst_allocation_allocated_cpu_seconds{provider, namespace, allocation}` (gauges, with the help text "allocated, not billed") for live Allocations, absent while unknown. Seconds are Prometheus's base unit; people read hours.
- A researcher's month is the kept records plus the live Allocations, read from the API (open question 16).

**Billing (beta)** (amended 2026-11-16; the science agent's design, for open questions 15 and 16; the new names are proposed).
- **The formula.** An Allocation's billed units are `allocatedBilling` × `elapsedSeconds` ÷ 3,600, in its partition's `billingUnit`, `gpu-hour` or `cpu-hour` (HBEP-4, Platform profile schema, The remaining groups). `allocatedBilling` is the `billing` entry of `tres.allocated`, from the same accounting read as `allocatedCPUs` and `allocatedGPUs` (HBEP-4, The Slurm dialect), so it costs no call. It is unknown when the entry is missing, when the job was requeued, and while the Allocation is pending, as its hours are.
- **Why the scheduler's own count,** rather than a formula in the profile (the science agent's decision, 16 Nov 2026): it is the center's own count, and a factor in the profile would only drift from it. Slurm computes it from the partition's `TRESBillingWeights`: "By default the billing of TRES is calculated as the sum of all TRES types multiplied by their corresponding billing weight", and "If PriorityFlags=MAX_TRES is configured, the billable TRES is calculated as the MAX of individual TRESs on a node" (slurm.conf, `TRESBillingWeights`: [24.11.5](https://slurm.schedmd.com/archive/slurm-24.11.5/slurm.conf.html), [23.11.7](https://slurm.schedmd.com/archive/slurm-23.11.7/slurm.conf.html); accessed 2026-11-16). The three billing counts recorded on Cyfronet fit the maximum, worked by hand from the recorded weights:
  - Helios `plgrid`, weights `cpu=1,mem=0.0005M`: S7's CPU job, with 4 CPUs and 6,144 MB, gives 4 and 3.07, so 4 by the maximum and 7.07 by the sum. Its record says 4 (`spikes/s7/slurm-json-real.md`).
  - Helios GH200, weights `cpu=0.01388,mem=0.00000816993M,GRES/gpu=1`: a node, with 288 CPUs, 489,500 MB and 4 GPUs, gives 4.00, 4.00 and 4, so 4 by the maximum and about 12 by the sum. Its configured billing is 4 (`facts.other.gh200_node_tres`).
  - Athena, weights `cpu=0.0625, mem=0.0078125G, GRES/gpu=1`: the conformance job, with 1 GPU, 4 CPUs and 32,768 MB, gives 1, 0.25 and 0.25, so 1 by the maximum and 1.5 by the sum. Its record says 1 (`facts.slurm.plgrid_now_conformance`). The count is a whole number, so this point fits a sum only if Slurm drops the fraction.

  Neither profile records `PriorityFlags`; it is a fact for both to add, from `scontrol show config`. Cyfronet documents the same maximum for its GPU partitions, "max(GPUs, ceil(CPUs / CPUs-per-GPU), ceil(memory / memory-per-GPU)) times the duration" (`facts.other.billing`, from the center's [billing page](https://docs.hpc.cyfronet.pl/environment/batch-system/billing/), recorded 2026-10-30), and L-13.2 gives it for Athena. The page was not read again on 16 Nov 2026, when its certificate did not verify; a web search of it that day returned its shares as a summary, not its text: 16 CPUs and 128,000 MB per A100, and 72 CPUs and 120,000 MB per GH200. So the framework re-implements no center's formula, and the weights stay profile facts.
- **What it gives for the framework's own sizing.** CPUs and memory follow the GPUs (HBEP-4, Submission, GPU sizing), so a one-GPU request bills as one unit. On Athena: 16 × 0.0625 = 1, 125 GiB × 0.0078125 = 0.98, and 1 GPU. On Helios GH200: 72 × 0.01388 = 0.999, 122,375 MiB × 0.00000816993 = 0.9998, and 1 GPU. So the cost is the allocated GPU-hours times 1, a GPU's weight on both, and `allocatedBilling` shows when a job departs from that.
- **Where the documented rule may differ.** It rounds each share up, and gives GH200's memory share as 120 GB in the fact and 120,000 MB in the search's summary, where the scheduler's weight sets it at 122,400 MiB. Read as 120,000 MB in Slurm's unit of 2^20 bytes, or as 120 × 10^9 bytes, it bills a one-GPU job of `memPerGpu`'s 122,375 MiB as two GPU-hours an hour; read as 120 GiB, as one. The scheduler counts one. So the framework never requests more memory, or more CPUs, per GPU than the partition's per-GPU share as the scheduler counts it, since under the maximum an over-request sets the count, and rounded up it doubles a one-GPU job's GPU-hours (HBEP-4, Submission, GPU sizing; the science agent's decision, 16 Nov 2026). GH200's shipped `memPerGpu`, 122,375 MiB, is within one GPU's share by the scheduler's own weights, so it is not lowered, and it is unverified against the documented 120 GB. GH200's first job's accounting `billing` count, equal to its GPUs, shows that the recorded weights and the maximum rule still hold; it cannot show the center's rounding. Whether the documented share bills a one-GPU job as one GPU-hour an hour or two is settled only by the person-run comparison, which includes a GH200 window (below).
- **The status and the record.** `status.atProvider.accounting.allocatedBilling`, an integer, sits beside `allocatedGPUs`. The `acct-` record gains `allocatedBilling`, the partition's `billingUnit` when the record is written, and the Provider's `grant` and `account`; each missing one is in `unknown`. A record written before these fields existed is never rewritten (The kept record), so its billed units are unknown.
  - **Grant and account names in records** (the science agent's decision, 16 Nov 2026). The Provider's spec already holds them (owner decision, 28 Oct 2026; HBEP-4, Provider settings). They stay in the cluster's own records, readable by the identities that read the namespace's records (Security), and in `hpcburst accounting`'s output on the host, and no record goes to the durable log. They stay out of every public artefact, such as an issue, a PR, a CI log or a published document. That rests on the owner's Provider-settings decision of 28 Oct 2026 (HBEP-4, open question 8), and on the science agent's extension of the owner's rule of 10 Nov 2026.
- **Totals per grant** (open question 16).
  - `hpcburst accounting` (proposed) lists the kept records and the live Allocations, groups them by grant and account, and sums the billed units of each unit apart, never GPU-hours with CPU-hours. A grant's account is its name with a resource suffix (`facts.submission.account_naming`, Athena), so the grouping keeps each resource's hours apart.
  - A total with unknown members shows their count beside the sum of the known ones, never the sum alone (Notes: an aggregate says how many of its samples were unknown). A pending Allocation is one of them.
  - When the Provider sets `grantEnd`, the time left to it is shown beside the total (HBEP-4, Provider settings). A grant has one name for its life, and a new grant is a new Provider (HBEP-4, User stories), so the grouping needs no window.
  - It reads the API only, and adds no series.
- **The comparison with a center's report** (the science agent's decision, 16 Nov 2026). It is a person-run step, since it needs the owner's access to the center's report (its tools, `facts.submission.grant_helper_tools`), and it is run once beta's totals exist. The person sets the report for a window of ended jobs against the same window's total. The window ends before the read, since the center's report counts only finished jobs (L-13.1). The comparison includes a GH200 window once GH200 returns, which settles whether the documented 120 GB share bills a one-GPU job as one GPU-hour an hour or two (Where the documented rule may differ). Publicly, only its verdict is recorded: agreed within a stated tolerance, or not, and why, with no figure, grant, account or job ID. The owner is the person to ask when beta reaches it; the owner hasn't decided it. Until the two agree, every figure stays "allocated, not billed".

### Test plan

Tests use the fake Slurm of spike S4, the engine double behind a real agent (`internal/agent/enginedouble`), and a real k3s for the event tests. Each event test checks for at least one event of the named type and reason on the named resource, since the recorder merges isomorphic events (Events). Messages are checked on conditions.

- **Event form.** Every event the lifecycle controller and the front emit has `action` set to one of the six types, `reason` set to the code alone, `type` Warning exactly for `degraded` and `failing`, and a note of at most 1,024 bytes. A note built from a long engine message is cut, and the event is stored.
- **Merging.** Emit the same event twice within a minute on an unchanged object: the API shows one event with a series count of 2. Emit it again after a write to the object: a second event appears. A test that asks for "at least one" passes in both.
- **Repeating conditions.** A condition that persists for three hours (a truncated catalog, a failing usage disk, a stale heartbeat), read every minute, gives at most four events, not one per read.
- **Retention.** On the launcher's k3s, an event created under a short `event-ttl` (a test setting) disappears after it, and the default launch passes `event-ttl=168h`. After a k3s restart, an event created before it is still present.
- **Stop an observer:** stop the Provider controller, then an agent's reports. The stopped controller's stored `Ready` may stay True; `ProviderReady` turns false by age. At least one `failing` event, reason `HeartbeatMissed`, appears regarding the Provider or the Instance within its staleness rule plus one reconcile. The readings it fed show unknown: the Provider is skipped, and the Instance's engine series are absent with `hpcburst_instance_metrics_unknown` set.
- **Batched heartbeats** against a fixed check tick, each within the staleness rule: no `HeartbeatMissed`.
- **Observers that never start.** A Provider created with no read at all raises at least one `HeartbeatMissed` once its `creationTimestamp` is older than `ProviderReadyStaleness`, and not before. With no front `Lease` in the namespace, no event regards the front. `hpcburst status` shows the front as absent when no front is configured, and unhealthy when one is configured but has no `Lease`. A lifecycle controller run with `--leader-elect=false` creates no `Lease`, emits no `ObservationGap`, and the front raises no `HeartbeatMissed` for the absent `lifecycle` `Lease`.
- **Readiness.** The lifecycle controller's `/readyz` fails while a second copy holds the `lifecycle` `Lease`, and while its caches have not synced; its `/healthz` answers in both. `hpcburst status` reports the controller by its `/readyz`.
- **Series scope.** An Instance in `starting` has its info series, and each engine metric of `worker-0` is `hpcburst_instance_metrics_unknown` with `reason="stale"`, before its first report and until the first fresh read. Once the Instance ends, none of its series is exposed.
- **A failed Allocation list.** `/metrics` answers 200 with `hpcburst_collector_success{collector="accounting"} 0` and no accounting series; after the next successful list, 1 and the series again.
- **A failed Instance inventory read.** `/metrics` answers 200 with `hpcburst_collector_success{collector="instances"} 0` and no Instance series; after the next successful read, 1 and the series again.
- **A standby.** Two managers with leader election on one API server, each read on its own `/metrics`. The standby's has no `hpcburst_` series, while the serving copy's has the Instance and accounting series and both success gauges. After the serving copy stops, the other gains both gauges at 1, and every live Instance shows as unknown with reason `stale` until it reports. A leading copy whose caches have not synced exports no `hpcburst_` series. A fixture with one replica, or one that injects the serving predicate into a collector, proves nothing here.
- **Raised events.**
  - **Counting:** for each reason a test raises, `hpcburst_events_raised_total` rises by one, with its `controller`, `action` and `type`, in the same call that hands the event over, including an event raised through crossplane's `WithAnnotations`. A suppressed `CreatedExternalResource` is not counted.
  - **Series at 0:** a reason never raised reads 0 on a serving copy.
  - **The drift guard** fails on any recorder built without the counting wrapper.
  - **Absence:** an absence check meets the four conditions (Metrics, Controller metrics). With a restart or a hand-over between its reads, it is inconclusive.
  - **None of these proves anything here:**
    - a single read showing 0;
    - a first read taken after the change;
    - a count kept in the test's own client;
    - a barrier that shows only that the emitting read completed, or a pass of another subject or made before the event was due.
- **A restart of the lifecycle controller.** Until the agent's next report, each engine metric of `worker-0` is `hpcburst_instance_metrics_unknown` with reason `stale`.
- **An engine's metrics endpoint times out or returns nothing:** the series are absent and `hpcburst_instance_metrics_unknown` names the reason, never a 0.
- **An engine double that omits the prefix-cache counter lines:** those series are absent with reason `not_reported`, and the other series are present. A real vLLM v0.32.0 with prefix caching off still exports both counters, at 0, since it registers them unconditionally (`loggers.py`, lines 660–677): its series are present, and the hit rate is 0 over 0, with no value.
- **Restart an engine at each rung:** a new series starts under the new generation labels, and no counter series decreases.
- **End a job at its time limit:** the drain-start event fires, `replaced` with reason `HandedOver` when a replacement serves, or `degraded` with reason `CapacityDropped` when none does, with a note citing the hard end. The Instance leaves the inventory, and no endpoint stays listed. No new reason is involved.
- **Drain an instance on purpose, then crash another:** the drain's event names the lifecycle controller in `reportingController` and the operation in its reason (`HandedOver`); the crash is `failing`.
- **Add a deployment while observers run:** it is observed without restarting them.
- **Restart the lifecycle controller and the front:** each emits one `ObservationGap` naming its previous `renewTime`. A first start emits none.
- **Usage durability.** A `Write` returns only after its record is synced. Kill the front between records: the counter shows a gap no larger than one block, and no record that `Write` acknowledged is missing.
- **Usage failure.** A disk that refuses writes (a log file that fails, as PR #95's tests use): the front keeps serving, `hpcburst_usage_write_failures_total` rises by the records lost, `/healthz` says `failing` with status 200, and at least one `UsageWriteFailed` event appears. When the disk recovers, the next records are written, `Write` returns nil for them, and `/healthz` says `ok`. A reservation that fails before its rename adds to the failure counter and leaves no gap. One whose directory sync fails after the rename, followed by a restart, leaves a gap of at most one block. After a failed batch and a clean stop, the next start shows only the failed batch's counters as a gap.
- **Rotation.** Records across a UTC midnight go to two files, with the counter continuous across them; the closed file is never touched again. A front stopped with a partial last line in the previous day's file repairs that file, and only that one, at its next start; a legacy `usage.jsonl` with no daily file beside it is repaired the same way.
- **Front metrics.** Each request adds one to `hpcburst_front_requests_total` with its code; a cut adds to `hpcburst_front_cuts_total` with its `cut_by`; a stream without content events adds no time-to-first-token observation.
- **Accounting.** A pending Allocation has no `accounting`, and no gauge is exported for it. A running one's elapsed time follows the scheduler's start time. A requeued job's hours are unknown, on v0.0.40 and v0.0.42 alike, also when the reply shows only the last execution, and its record lists them as unknown. A running job polled ten times within a minute gets one status write. With the tag lookup succeeding and only the final accounting read failing, the record is written after `lostGrace` with unknowns, and the finalizer goes; with the lookup itself failing, the finalizer stays. Deleting an ended Allocation leaves `acct-<UID>` with its hours. An Allocation deleted while its job carries `COMPLETING` has no `acct-<UID>` until the flag clears, then exactly one, in HBEP-4's Helios shape (the job not listed, then read from accounting) and in its Athena shape (listed without the flag); a fixture whose jobs never carry the flag proves nothing here. A job whose final state came from the queue listing has the elapsed time `end_time − start_time`. When the final read does not come within `lostGrace`, the record is written with its elapsed time unknown, and the Allocation goes.
- **A long reply with few chunks:** time per output token is the engine's value or absent, never 0.

### Compatibility and upgrades

- **Versions.** The vocabulary of types and reasons, the metric names and the usage fields are versioned with the API, `v1alpha1`. Within it, reasons, metrics and usage fields may be added; renaming or removing one waits for a new API version.
- **Readers** treat an unknown reason as its type's generic case, and an event with no type (an empty `action`, as the Provider controller's in alpha, and its diagnostics' in beta) or an unknown type as "other", and keep working.
- **Usage files.** A file written before rotation, `usage.jsonl`, is the newest file while no daily file exists (Usage records, Rotation), and then stays as it is; the counter file continues. A record gains fields only by addition, so an earlier reader skips the new ones.
- **The event TTL** applies to events created after the flag is set. Events created before keep the TTL they were stored with.
- **The durable log (beta).** The CloudEvent's `type` carries its version, `io.hpcburst.event.v1`, and its `data` gains fields only by addition. A reader of the log treats an unknown reason or type as readers of Events do. An earlier binary neither writes nor reads the log, and the store stays; `up` without `--event-log` runs as alpha. The Provider controller's typed events keep their reasons, so a reader that matched them as untyped still finds them. A reader written for six types treats `ended` as "other" (Readers, above), and so loses nothing but its type.
- LLMLab exposes no metrics, so there is no client contract to keep for them. Usage reporting inside responses follows HBEP-5.

### Security

- Usage records hold a client key's ID, never the key, and counts, never prompts or responses. The files are mode 600 in a directory of mode 700, read by the operator on the host. A client key reading its own usage is not needed for alpha.
- Events and metrics never carry credentials, keys or prompts. Metrics are served on loopback only, with no client key ID in any label.
- Provider job IDs are Instance metadata (HBEP-3), and appear in accounting records, visible only to identities that can read the namespace's records (HBEP-11). In beta so do the Provider's grant and account names (Provider accounting, Billing).
- Events are readable by the identities that HBEP-11's RBAC lets list events in the namespace.
- **No note of a typed Allocation event names a job ID** (beta; Events, Allocation events), since the log that keeps them may be exported. HBEP-4's untyped diagnostics keep their notes, and stay in the cluster's own events.
- **The durable log** (beta) listens on loopback and refuses a client without its token. Its configuration and token are mode 600 and its store mode 700, under the launcher's state directory, so its readers are the audit log's (The durable log, Readers).

## Operational readiness

1. **Working:** every observer's heartbeat is within its rule: each Provider's `lastSuccessfulStatusRead`, each Instance's last report, the front's probe ages, and the `front` and `lifecycle` `Lease`s. Both `/metrics` endpoints answer, and the serving lifecycle copy's has `hpcburst_collector_success` for `accounting` and for `instances`, each at 1. If no copy has them, no copy serves, which is not working. End to end, a request through the front appears in the usage file with its deployment and Instance, and in `hpcburst_front_requests_total`. A `HeartbeatMissed` event, an endpoint that does not answer, or a request missing from usage says it is not working. In beta, with `--event-log`, the log's `/healthz` answers, the front's `usage.log` says `connected`, `hpcburst_usage_unlogged_records` returns to 0, and `hpcburst_events_unlogged_total` stays flat; an `EventsNotLogged` event says it is not working.
2. **Restart:** an observer re-reads the inventory and resumes, and the lifecycle controller and the front emit one `ObservationGap` each. Engine counters start new series under new generation labels. The usage counter resumes at the persisted block end. A crash, a failed batch or a reservation of uncertain persistence leaves a gap; a clean stop does not. Events in the store survive a k3s restart, with their TTL restarted. In beta the log restarts from its store, the forwarder resumes after the stream's last counter, and each Provider manager emits one `ObservationGap` too.
3. **Silent failure:**
   - a collector that cannot read: `hpcburst_collector_success` 0, with none of its series;
   - an observer that runs but reads nothing: its readings turn unknown, and the share of unknown samples is a query on `hpcburst_instance_metrics_unknown`. A display that draws an absent series as zero would hide this, so displays draw it distinctly;
   - a recorder that drops events: through a full queue, silently, or through a refused note or a store error, which it logs. The conditions still change, since status is the truth;
   - a usage write that fails: the failure counter and `/healthz`;
   - in beta, an emitter that cannot reach the log: `hpcburst_events_unlogged_total` and `EventsNotLogged`; a forwarder behind: `hpcburst_usage_unlogged_records`; and a log started with a setting it did not parse as given: it refuses to serve (The durable log, Where it runs).
4. **Provider limits:** accounting adds one `sacct -j` read per execution, after the job is first seen started (HBEP-4, Poll rate); its other fields come from existing reads, which are paced per platform profile (HBEP-4).
5. **Capacity:**
   - a full KV cache: waiting requests and preemptions rise, and those are the signals;
   - a full disk: usage writes fail loudly, and the SQLite store stops writes, so events may not be stored (Risks; HBEP-11, Operational readiness 5; L-17.2). Sizing is in Usage records;
   - the event store holds an estimated 10 MB or less over 7 days at alpha scale (Retention);
   - in beta, the log's streams are capped, 2 GiB each by default: a full events stream refuses new events, and the usage copy drops its oldest records. `up` starts the log only when the caps and the upgrade's copy fit above the free-space floor (Retention, In the durable log).
6. **Idle cost:** no new process in alpha; beta's `--event-log` adds one, whose memory beta measures. Two loopback `/metrics` endpoints, built only when scraped; one `Lease` renewal every 10 s; heartbeat checks inside existing reconciles; one sync per batch of finished requests. Nothing runs on providers.
7. **Rollback:** an earlier binary ignores the new status fields and emits fewer events; the usage files and accounting records stay. Removing the launcher's flag returns new events to 1 h. Serving does not depend on any metric or event. In beta, `up` without `--event-log` stops nothing that serves, and the log's store stays.

## Drawbacks

- Every reader must handle three outcomes, not two.
- Per-instance series and per-request records add storage that a single-user setup must carry.
- Alpha's events can be merged or dropped, so an agent that wants every transition must re-read status until HBEP-10's subscriptions exist, at stable.
- Until the log is the record, beta stores usage twice, in the files and in the log, and runs one more process.

## Alternatives

- **Each engine's own dashboard per site.** The metrics exist, but without common names and labels they cannot be compared, and they cover neither the front nor the provider.
- **Free-text logs as the event source.** Cheap to write, but tools that parse them misread one event as another.
- **Rebuilding usage from logs afterwards.** Possible, but slow, and only as complete as the logs.
- **KV-cache utilisation as the load measure.** Simple, but it does not compare across attention implementations.
- **JetStream as alpha's event and usage log.** S8 supports it, but it adds a process, and subscriptions and cursors that HBEP-10 has not designed. Kept for beta.
- **A watcher that copies Kubernetes Events into the log.** One writer, but the log would inherit the recorder's merges, drops and full queue (Events), so it would be no more complete than the API store.
- **The log as the usage record in beta.** One store, but S8 did not test power loss, so the files stay the record (The durable log).
- **A pinned nats-server binary beside frps.** One more binary to pin and check; embedding pins the version in `go.mod`, as S8 ran it.
- **Evicting events by age or size** (`discard: old`, S8's setting). It deletes events silently, against the owner's retention rule (Retention, In the durable log). The usage copy evicts, since the files are the record.
- **OpenTelemetry's names as the framework's own.** Every convention used is Development status, and this HBEP's names are read by tests and tools (Metrics, OpenTelemetry).
- **Untyped Allocation events for beta too.** No change, but readers would keep treating the Allocation's lifecycle as type "other" and read it from the Instance's events, which a kept Allocation with no Instance lacks.
- **NaN for an unknown sample.** One value per series and no extra gauge, but it poisons or hides aggregates (Design details, Unknown samples).
- **Scraping engines through the tunnel.** It would show the engine's own series, but HBEP-6's tunnel carries only routed requests, and a gone Instance would read as a stale series.
