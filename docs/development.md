# Development

The framework is one Go module at the repository root, `github.com/groundnuty/plgrid-llmlab-hpc-burst`. The minimum Go version is 1.26.0.

Code under `spikes/` and `third_party/forked/*` is not part of this module.
- **Spikes:** each Go spike has its own `go.mod`. S7 is Python and shell, with no Go packages.
- **Forked packages:** each one has its own `go.mod`. A build tag alone is not enough, because `go mod tidy` considers every build tag. Check with `go mod tidy -diff`; it must show nothing.

## Controllers and the agent

### Process layout

- **One controller binary** in alpha, `cmd/hpcburst-controller` (#61 owns its `main`). `hpcburst up` starts and supervises it, and restarts it when it exits (#61, in `internal/launcher`).
- **Inside it, one controller-runtime manager per Provider** (HBEP-4, Two controllers; HBEP-11, Controllers).
  - Each runs crossplane-runtime's managed reconciler over the Allocations naming its Provider.
  - Each has its own leader `Lease`, `v1alpha1.ProviderLeaseName(<provider>)`, which is `provider-<name>` (`@hpc-burst-science-agent`, 31 Oct 2026).
  - A supervisor starts a manager when a Provider appears and stops it when the Provider goes, so one Provider's failure does not stop the others (#59 owns it, and `main` calls it).
- **The lifecycle controller** is one more manager in the same binary (#61), with the `Lease` `v1alpha1.LeaseLifecycle`.
- **Every `Lease` lives in `v1alpha1.ControllerNamespace`, `hpcburst-system`.** The launcher creates that namespace before it starts the controller binary; #61, which owns the supervision in `internal/launcher`, adds it.
- **The agent API** runs inside the lifecycle controller's process:
  - #60's HTTP server handles TLS, the routes, authentication and the long poll;
  - it calls the lifecycle controller through `agentapi.Backend`, which #61 implements.
- **Host-dialed mode's relays** (HBEP-6, Dial-home modes; #298) run under each batch Provider's controller, in the same binary. When `hpcburst up` recorded `--front-mode host-dialed`, `providerctl.Setup` adds the relay owner, `hostdial.Owner`, to the Provider's manager as a leader-only runnable (`relayRunnable`). It keeps two `ssh` children for each running Allocation, stops them by PID when the job ends, the Allocation is deleted or the manager stops (before the manager releases its `Lease`), and starts the relays of every running Allocation again when a controller takes the lead. The children die with the controller process: each starts on a thread that stays locked, with `Pdeathsig` `SIGKILL`. A restart of the controller therefore cuts the streams on them, which a restart does not do in `direct` and `ssh` modes (owner's decision, 9 Nov 2026, "Accept cuts for alpha"; a relay keeper is beta). A relay carries a fence (E, N), with E the `provider-<name>` `Lease`'s `leaseTransitions` when the controller took the lead, so after an unfenced hand-over between two copies the agent refuses the older copy's relay as `superseded`, for good. A host-dialed Provider has at most 2 Allocations (`lifecycle.HostDialedMaxAllocations`), and the cap of 4 relays per login node is one process-wide `hostdial.SharedSlots`, shared by the Providers that use the same login node; only one host-dialed Provider runs per login host.
- **The allocation agent** is a separate static binary, `cmd/hb-agent` (#60), built for `aarch64` and `x86_64`, that runs inside the job.

### Single writer of the API

- **Only the contracts owner edits `api/` and `config/crd/`.** A builder who needs a field, a condition type or a reason asks for it and gets a small PR. Builders never regenerate or hand-edit the CRDs.
- **Each field of each object has one writer.** Every write carries a resourceVersion precondition: an Update, or a patch with an optimistic lock. A conflict means re-read, never overwrite (HBEP-7, open question 11). The one server-side apply is the lifecycle controller's `DialHomeUnreachable` (below).
- **Field managers.** Every write names its controller's field manager, so `managedFields` shows who wrote what: `v1alpha1.FieldManagerLifecycle` (`hpcburst-lifecycle`) for the lifecycle controller and its `Backend`, and `v1alpha1.FieldManagerProvider` (`hpcburst-provider`) for every Provider's controller.

It is written by `lifecycle.WriteTunnelConnected` (a status Update that carries the resourceVersion, like the reconciler's own writes), called from `cmd/hpcburst-controller`'s tunnel-state. The gate is on an Instance's first entry to `ready` only (`status.readyTime` is nil): one that has never been ready becomes `ready` only with the condition True, and one that is not ready at `health.startTimeout` while it is not True ends with `status.endReason` `TunnelNotConnected` (`v1alpha1.ReasonTunnelNotConnected`), otherwise `StartTimeout` (HBEP-7, Instance start). After a restart of either rung, an Instance that has been ready returns to `ready` once its checks pass, whatever the condition; with the tunnel down it is ready and not eligible at the front, which routes on its own probe, and nothing restarts, ends or releases on the tunnel's account (`@hpc-burst-science-agent`, 1 Nov 2026). ### Runtime conventions

- **The host layout.** `agentapi.Host{StateDir, PortBase}` names every path and port that several components share on the control-plane host. The launcher owns the state directory and its loopback port block, and passes both to the controller binary and the front (#61 and #64 fill a `Host` from them):
  - `Host.CredentialsDir()`, `<state>/credentials`, mode 700: the controller's credentials directory;
  - `Host.AgentBuildsDir()`, `<state>/agent-builds`: the builds the Provider's controller stages on a platform. For each cpuArch (`aarch64`, `x86_64`, the profile's strings) it holds the agent build `agentapi.AgentBuildName(cpuArch)`, `hb-agent-<cpuArch>`, which `hack/build-agents.sh <state>/agent-builds` builds (see Agent builds below; its SHA-256 is the agentDigest the lifecycle controller sets), and the frpc build `agentapi.FrpcBuildName(cpuArch)`, `frpc-<cpuArch>`, which `hack/fetch-frp.sh --agent-builds <state>/agent-builds` places: it fetches the pinned release's tarball for each architecture of `internal/launcher/frp-pins.txt`, checks the tarball's and then frpc's sha256 against the pins, and installs frpc under the cpuArch name (`@hpc-burst-science-agent`, 1 Nov 2026: the name `frpc-<cpuArch>`);
  - `Host.AgentCertFile()` and `Host.AgentKeyFile()`, `<state>/agent-endpoint/tls.crt` and `tls.key` (key mode 600): the agent endpoint's certificate, which the launcher creates. #60's server and, in direct mode, the front's dial-home listener present it;
  - `Host.AgentEndpointPort()`, the port base plus 3, bound on loopback by #60's server (the launcher only checks that it is free); `Host.AgentEndpointAddr()` is the front's passthrough target.
  - `Host.DialHomePort()`, the port base plus 7, is the front's default dial-home listener in ssh and host-dialed dial-home modes (`Host.DialHomeAddr()`, on loopback; `@hpc-burst-science-agent`, 31 Oct 2026). In ssh mode each platform's restricted VM key permits `-L` forwards to exactly the agent endpoint's port and this one, so **a launcher started with another port base needs new keys**; host-dialed mode has no key, and its serving relay dials this port on loopback (`Host.RelayChannelPorts()`: `control` to base+3, `serving` to base+7), so `/agent/v1/` on this listener answers 404 there, since the agent reaches the agent endpoint through its control relay. In direct mode the dial-home listener's address stays required and explicit (compute nodes must reach it), and this default does not apply.
  - The frp server's four loopback ports (HBEP-6, Loopback ports), from the base: `Host.FrpsPluginPort()` base+8 (`FrpsPluginPortOffset`), the server plugin's plain HTTP endpoint at `FrpsPluginPath`, which the lifecycle controller binds; `Host.FrpsBindPort()` base+9, frps's bind port, where the front's dial-home listener passes frpc's websocket; `Host.FrpsTCPMuxPort()` base+10, the tcpmux `CONNECT` port the front dials; `Host.FrpsWebPort()` base+11, the web server whose API lists the proxies. Each has an `...Addr()` helper, `127.0.0.1:<port>`. The launcher starts frps, which binds base+9 to base+11.
  - `Host.ControllerMetricsPort()`, base+12 (`ControllerMetricsPortOffset`), the lifecycle controller's `/metrics` on loopback (`Host.ControllerMetricsAddr()`, issue #111). It is the block's last port: the block is 13 ports, base to base+12, and `PortsFromBase` accepts a base only when base+12 is at most 65535.
  - `Host.FrpsWebPasswordFile()`, `<state>/frps/web-password`, mode 600 (the directory 700): the password of frps's web server (`FrpsWebUser`, `hpcburst`). It has a key file's form (64 lowercase hex characters, no newline): the launcher writes it with `agentapi.NewKey` and `agentapi.WriteKeyFile` and puts the same password in frps's configuration; the lifecycle controller reads it with `agentapi.ReadKeyFile` to list the proxies.
  - The whole block at the default base 29220: base API, +1 HTTPS, +2 controller manager, +3 agent endpoint, +4 front `/healthz`, +5 load balancer (reserved, never bound; `internal/launcher/ports.go`), +6 lifecycle controller `/healthz`, +7 dial-home listener (ssh and host-dialed modes), +8 frps plugin, +9 frps bind, +10 frps tcpmux, +11 frps web server, +12 lifecycle controller `/metrics` (`Host.ControllerMetricsAddr()`; HBEP-8, Metrics: controller-runtime's metrics server, on loopback, with the engine gauges per Instance). Of these, +4 and +6 are assigned to #64 and #61, +8 to +11 to the tunnel items of #90, and +12 to #111. k3s binds base, +1 and +2, and the launcher requires the whole block, base to base+12, to be free before `up`: +4 and +7 belong to the front (#64), +3, +6, +8 and +12 to the controller (#60's server, #61, #90, #111), and +9 to +11 to frps.
- **Key files.** Both kinds of key file in the credentials directory have one form: 64 lowercase hex characters (256 random bits), no newline, mode 600, owned by the controller's user. They are written with `agentapi.WriteKeyFile` (temporary file, fsync, rename) and read with `agentapi.ReadKeyFile`, which refuses any other form, a file with any permission bit for its group or others or one its owner cannot read (so modes 600 and 400 pass, and 640 or 200 do not), a file owned by another user, a symlink and anything that is not a regular file.
  - `agentapi.AllocationCredentialPath(dir, <Allocation UID>)` holds each Allocation's credential. The lifecycle controller writes it as soon as the create returns the UID. Until the file exists, the provider's Create waits and requeues: it neither submits nor marks the attempt Rejected. The provider reads the file to stage it (`alloc/<tag>/credential`), and the agent API reads it to authenticate.
  - `agentapi.InstanceKeyPath(dir, <Instance UID>)` holds each Instance's key. The agent generates it with `agentapi.NewKey` and sends it in `InstanceReport.Key` until `KeyStored`; the lifecycle controller checks it (`agentapi.CheckKey`) and writes it; the front reads it and sends `Authorization: Bearer <key>` to the Instance.
- **A managed Provider's credentials file** is `provider.ManagedCredentials`: one JSON object with exactly `key`, `baseURL` and an optional `expiry` (RFC 3339), member names exact, mode 600 (HBEP-4, Provider settings). `baseURL` is the gateway's OpenAI-style base URL with its version segment, for example `https://gateway.example/v1`; a request for the front's `/v1/<rest>` goes to `baseURL/<rest>` (`URLFor`), and the catalog is `baseURL/models` (`CatalogURL`). https only, or http on loopback. #69 and #64 both read it with `provider.ReadManagedCredentials`; `Expiring` says when `CredentialsExpiring` applies (a day before the expiry). The key is printable ASCII of 16 to 4096 bytes (`MinManagedKeyBytes`, `MaxManagedKeyBytes`); a shorter one is refused as `CredentialsInvalid`, and the error gives its length only. `@hpc-burst-science-agent`, 31 Oct 2026.
- **Dial-home settings in `agent.json`.** `Mode` and `Endpoint` are the front the launcher recorded (`hpcburst up --front-mode --front-addr`); in host-dialed mode `Endpoint` is empty and `SSH` is absent, because nothing in the job dials the host (`AgentConfig.Validate` refuses either to be set), and `Allocation` (JSON key `allocation`) is the Allocation's UID, which the agent's greeting on its relay socket names and each relay checks against its `--allocation`; it is set in host-dialed mode only, and `Validate` refuses a missing one there and any one in the other modes; in ssh mode `SSH.User` is the user who runs the controller, `SSH.AgentPort` is `Host.AgentEndpointPort()` and `SSH.DialHomePort` is `Host.DialHomePort()`, an explicit value that must differ from `AgentPort`; `CertSPKISHA256` is `agentapi.PinOf` of the certificate at `Host.AgentCertFile()`.
  - **The ssh endpoint's port** is 22 by default, and `AgentConfig.Validate` accepts any valid port, because the owner routes the clusters through a port forward on the gateway at its own port (`@hpc-burst-science-agent`, 31 Oct 2026).
  - **frpc runs in every mode** (HBEP-6, Dial-home modes), so `agent.json` requires `FrpcDigest` in every mode, as 64 lowercase hex characters, and `SSH.DialHomePort` in ssh mode; `AgentConfig.Validate` enforces it, and `AgentConfig.FrpcPath()` is `<stagingDir>/frpc/<digest>/frpc` (`agentapi.StagedFrpcPath` relative to `stagingDir`). The provider stages frpc there before it claims an attempt (`providerctl` `files()`, mode 700, in HBEP-4's order: the agent's binary, frpc, the credential, the certificate, then `agent.json`): `providerctl.FrontSettings.FrpcDigests` gives the digest per `cpuArch`, and the bytes staged are those of `<agent-builds>/frpc-<cpuArch>` (`agentapi.FrpcBuildName`), which must have that digest. A missing file, or one with another digest, is refused before any call to the platform, with the cpuArch and both digests in the Allocation's reason; the agent checks the staged file against the digest again before it runs it.
  - **The dial-home certificate** is staged in each Allocation's directory as `alloc/<tag>/dial-home.crt` (`agentapi.StagedDialHomeCertPath`), mode 644 because it is public, before the claim. It is the PEM of `Host.AgentCertFile()` as the controller read it (`providerctl.FrontSettings.CertPEM`, kept by `frontSettings` from the same read as the pin), and `FrontSettings.CheckCertificate` refuses, before any call to the platform, any certificate the agent would refuse: it runs `agentapi.VerifyDialHomeCert`, the very function the agent runs before it starts frpc (exactly one PEM certificate with nothing before, between or after it and no PEM headers; the pin is `FrontSettings.CertPin`, the one `agent.json` carries; it names `agentapi.DialHomeServerName`; it is valid now). A missing certificate is refused too. Its subject alternative name and frpc's `transport.tls.serverName` are both `agentapi.DialHomeServerName`, `dial-home.hpcburst.invalid`; the launcher issues the certificate with that name (see The launcher, the agent endpoint's certificate).
- **Host-dialed mode's relay contract** (`pkg/agentapi/relay.go`, `internal/hostdial/`, `internal/slurm/sshrun/relay.go`, `internal/providerctl/relays.go`, `internal/lifecycle/hostdialed.go`, `cmd/hb-agent`; HBEP-6, Dial-home modes, host-dialed mode). The controller, the agent and the relay step read the same names, so they agree by construction.
  - **Channels.** `agentapi.RelayControl` (`control`) ends at the agent endpoint, base+3; `agentapi.RelayServing` (`serving`) ends at the dial-home listener, base+7. Each has its own relay, so control and the token tunnel never share a connection.
  - **The relay line** is `agentapi.RelayLine(jobID, agentPath, args)`, with `args` an `agentapi.RelayArgs` (`Channel`, `Dir`, `Allocation`, `Epoch`, `Seq`; `Validate` refuses any word that would need quoting): `srun -u --overlap --jobid=<job> --ntasks=1 <staged hb-agent> relay <channel> --dir <Allocation directory> --allocation <UID> --epoch <E> --seq <N>`. The step is the agent binary itself (`hb-agent relay <channel>`, `cmd/hb-agent`, read by `agentapi.ParseRelayArgs`). Its exit codes are 0 when its session ended, 1 when it could not start, 2 on a usage error, 4 for "agent not ready" (`hostdial.ExitNotReady`) and 5 for "superseded" (`hostdial.ExitSuperseded`). `-u` is required: without it `srun` held output that ended without a newline until the stream closed (probe of 9 Nov 2026). The controller runs the line over `ssh` through `sshrun.Relay`, on a connection of its own (`ControlMaster=no`, `ControlPath=none`, never the transport's shared master), with `-T`, `BatchMode=yes`, `ServerAliveInterval=10`, `ServerAliveCountMax=3` and a private `-F` file, and with no `SSH_AUTH_SOCK`.
  - **The rendezvous.** The agent (`hostdial.StartJob`) makes one Unix socket, for both channels, in a directory with a random name, `hb-relay-<random>`, mode 700, under the job's `$TMPDIR` (science-agent ruling on #301: the site scopes it per job and removes it at the job's end, on Helios the bootstrap points it at `$MEMFS`, and the probe found an `--overlap` step's `$TMPDIR` the same as its batch step's), and under `/dev/shm` only when the `$TMPDIR` path would pass a socket's 107 bytes (`agentapi.MaxRelaySocketPath`), which it logs. An unset or unusable `$TMPDIR` fails by name (`hostdial.ErrNoSocketDir`), with no fallback. In tests, a killed agent's directory goes with the fake job's `TMPDIR`, and the stack harness removes any `/dev/shm` one by the agent's `relay-socket` record (`stack.RemoveRecordedRelayDirs`), never by a pattern of names. A step started from the login node may have a `$TMPDIR` that differs from the batch script's (the probe of 9 Nov 2026 found them the same on Athena), so the path goes through a file: `<Allocation directory>/relay-socket` (`agentapi.RelaySocketFile`, mode 600), written to a temporary file in that directory and renamed. The Allocation directory is `<stagingDir>/alloc/<tag>` (`agentapi.AllocationDir`); the controller passes it as `--dir`. There is no pointer under the staging directory and no predictable path under `/tmp`.
    - The relay (`hostdial.Relay`) opens `relay-socket` with `O_NOFOLLOW` and takes it only if it is a regular file of its own user with no group or other bit, of at most 4 KiB, naming a clean absolute path of at most 107 bytes.
    - The exchange is three lines, each at most 256 bytes and 10 s: the agent greets with `agentapi.RelayGreeting`, `hpcburst-agent/1 <Allocation UID>`, after it has refused a peer of another user (`SO_PEERCRED`); the relay checks that the greeting names its `--allocation` and answers with `agentapi.RelayHello`, `relay/1 <channel> <E> <N>`; the agent answers `agentapi.RelayAccepted` (`ok`) or `agentapi.RelaySuperseded` (`superseded`), and after `ok` the socket carries the session.
    - A missing or unusable file, a socket that nobody answers, a greeting for another Allocation or no answer is `hostdial.ErrNotReady`, "agent not ready". `Job.Close` removes the file while it still names this socket, and the directory.
  - **Fencing.** The agent keeps, for each channel, the (E, N) of the session it accepted (`Job.handshake`). A hello that is not above it, a lower E or the same E with an N that is not higher, is answered `superseded` and its connection closed. A higher one replaces the older session, which is closed. E is read once when the relay owner starts: `OwnerOptions.Epoch` is `leaseEpoch`, the `leaseTransitions` of the `provider-<name>` `Lease` (a failed read is repeated every 2 s, and no relay starts meanwhile). N is the next value of one process-wide counter, so a later relay always has a higher (E, N), across owners and Providers. The owner is a leader-only runnable, which controller-runtime stops before it releases the `Lease`, so a copy that stops leading stops its relays by PID first; a new leader builds a new owner with a higher E.
  - **The preamble.** After `ok` the relay writes one line, `agentapi.RelayPreamble`, `hpcburst-relay/1 <Allocation UID>`, and then the session. `hostdial.Serve` requires that line first, within `hostdial.PreambleTimeout` (30 s) and at most 256 bytes. Any other first line is `hostdial.ErrUnexpectedOutput`, "unexpected output before the preamble", which names only the byte count, and nothing within 30 s is `hostdial.ErrNoPreamble`; both are retried. Nothing before the preamble is skipped.
  - **The session** is `fatedier/yamux` v0.2.0, with a 10 s keepalive and a 10 s write timeout on both ends (`hostdial` `sessionConfig`). `Serve` runs the host end over the ssh process's pipes. For each stream the job opens it dials only its channel's loopback port (`Host.RelayChannelPorts`) and opens no stream of its own. On the job side a connection that finds no session waits up to `hostdial.DefaultWait` (30 s), then is closed.
  - **Named failures.** A relay that ends writes a fixed line to standard error that names the Allocation's UID and no path (`hostdial.RelayMessage`): `hb-relay: agent not ready: ...` or `hb-relay: superseded: ...`, then a second line with the detail, which is never logged. `hostdial.ClassifyEnd` reads the standard error that `sshrun.Relay.Command` keeps (4 KiB, `sshrun.Stderr`) and returns an `hostdial.EndKind` with a fixed cause: `EndRetried` (`retried`: ssh dropped or killed, unexpected output or no preamble, "agent not ready"), `EndSuperseded` (`superseded`), `EndJobGone` (`the job's end`: `srun` says the job does not exist or is completing) and `EndFailed` (`failed`: `srun`'s step-limit refusal, "Step limit reached for this job", whose exact wording on a real cluster is not measured yet, HBEP-4 open question 16). For any other non-zero exit, `sshrun.Classify` names the kind of ssh failure.
  - **To look at the socket** from the login node: read `<Allocation directory>/relay-socket`, then `srun --overlap --jobid=<job> --ntasks=1 ls -la <its directory>`, which lists the socket and the directory's mode.
  - **The owner** (`hostdial.Owner`, one per Provider's manager) starts both relays of an Allocation that `Want` names and stops them by PID on `Drop`. It restarts a relay after a backoff of 1 s, doubling to 30 s, with jitter, the first start jittered too and the backoff reset once a relay has stayed up for 60 s. Before each start it reads the Provider's latest queue listing under the Allocation's tag (`hostdial.JobReader`, `Batch.ListByTag`: the listing the poll keeps, with no `squeue` of its own) and starts only for the recorded job, listed running with the tag as its name. A job listed pending or held, or not listed under the tag, is waited for, with no `srun` (a listing can miss a running job within the Provider's absence grace); one listed as ended or completing ends the relay for good, as `EndJobGone`, as does `srun`'s refusal that the job does not exist or is completing. Superseded and agent not ready are read from the relay's exit codes, 5 and 4, before its standard error, of which the ssh client keeps 4 KiB. It logs `a relay did not start` with the reason in `why`.
    - **Final ends** are `EndSuperseded`, `EndJobGone` and `EndFailed`; the relay is not started again until the owner is rebuilt (a controller restart) or `Want` names another job, agent, directory, UID, login node or credentials generation. `EndFailed` also covers more than `hostdial.DefaultRestartLimit` (120) restarts of one channel within `DefaultRestartWindow` (an hour), counting only restarts after a session that came up and dropped (`ServeStats.Sessions`); a relay that fails before its session comes up is never capped, and it calls `Target.OnFailed`, so the controller raises the Provider controller's `RelayFailed` event (`v1alpha1.EventReasonRelayFailed`) regarding the Allocation, with the message "the <channel> relay ended for good: <cause>". It goes through crossplane-runtime's recorder, so it is untyped in alpha (HBEP-8, open question 14). The same call records the failure for the Allocation (`relayState.recordFailure`, `internal/providerctl/relayfailed.go`: the first for its UID and job) and writes the Allocation's condition `v1alpha1.ConditionRelayEndedForGood` True, reason `v1alpha1.ReasonRelayFailed`, with the recorded failure's message (`persistRelayFailed`), before it raises the event, so a controller restart cannot lose the mark. Each attempt of the write reads the Allocation from the API server, refuses (`errMarkRefused`) when its UID or `status.atProvider.jobID` is not the relay's (`checkMark`), does nothing when the condition is True already, refuses an Allocation that is not Running, is completing or is being deleted (`checkRunning`), and patches the status with an optimistic lock, retried on a conflict (`retry.DefaultRetry`) within 30 s. It runs only while this copy leads: `relayState.leadContext` ends when the relay owner's run ends and when the relay fence's release hook calls `StopRelays`, before the relays stop. The callback records, writes and raises nothing without it, the write runs under it, retries included, and checks it again just before its patch. When the write fails, the next observation of the running Allocation sets the same condition from the record, under the same checks (`markRelayFailed`), and the managed reconciler writes it with the status. Nothing clears it. The record is dropped with the Allocation's relays. The lifecycle controller reads the condition in step 5 (`allocationFailed`) as it reads `SubmittedAsOther`: the Instance ends with `RelayEndedForGood` and the Allocation is released; `retention`'s `releaseEmpty` releases an empty one, and the frps plugin admits no login for it (issue #304). `superseded` and the job's end raise no event and set no condition. At the 30 s cap two relays make at most about 240 `srun` steps an hour, about 11,500 in 48 h, under the 40,000 `MaxStepCount` that both profiles record.
    - **The log** (`logs/controller.log`): `relay started` (`tag`, `channel`, `job`, `pid`, `epoch`, `seq`), `relay ended` (`tag`, `channel`, `job`, `up`, `exit`, `end`, `cause`), `a relay ended for good` (`tag`, `channel`, `end`, `cause`) and `a relay did not start` (`tag`, `channel`, `why`). `end` is `EndKind`'s string. No line carries the ssh or `srun` text.
    - **The process.** Each ssh runs in a process group of its own, started on one goroutine that locks its OS thread for good, with `Pdeathsig` `SIGKILL`, so relays die with the controller process (a parent-death signal fires when the creating thread exits, go.dev/issue/27505; the pattern of the fake Slurm's `startProc`, #274). The owner stops a relay by its PID: TERM to its group, KILL after 5 s. A target names its credentials' generation (`hostdial.Target.Gen`, a hash of the Provider's ssh settings), so rotated credentials stop the running relays and start them on the new ones; a replaced `sshrun.Relay` refuses to start or rewrite its file.
    - **A controller restart cuts the streams in flight,** counted as cuts and never replayed, and the relays return within the backoff (owner's decision, 9 Nov 2026, "Accept cuts for alpha", https://github.com/groundnuty/plgrid-llmlab-hpc-burst/pull/298#issuecomment-6749435073). A relay keeper, a process the launcher would supervise, is beta (HBEP-6, open question 13).
  - **The caps.**
    - **Allocations:** `lifecycle.HostDialedMaxAllocations` is 2. `hostDialedLimits` makes a host-dialed Provider's `maxSubmitPerUser` the smaller of its QOS limit and 2, so it is planned like any QOS limit: a third Allocation is not created and the deployment shows `SubmitLimitReached` (HBEP-4). The limit's source reads "host-dialed mode, HBEP-6", so the message says `maxSubmitPerUser 2 (host-dialed mode, HBEP-6)`; a QOS limit of 2 or less keeps its QOS name. The slot count, the no-overlap check and the status messages read the capped value.
    - **Relays per login node:** `hostdial.DefaultRelaysPerLogin`, 4, keyed by the login node as `sshrun.Relay.Login` names it: the host name as `ssh -G` resolves it through the relays' own `-F` file (the configured `HostName` when `ssh -G` fails), so an alias and a full name of one node are one host. An Allocation takes the slots of both its relays together (`Slots.Acquire`) before either starts and holds them while it is wanted, through restarts and backoffs, so none is left with half a pair. With the cap of 2 Allocations it is a backstop; a third Allocation on one login node waits, silently, with `Waiting` set in `Owner.Relays`.
    - **One host-dialed Provider per login host,** as `ssh -G` resolves its `HostName` through the Provider's own `-F` file. The host goes to the oldest such Provider by `creationTimestamp`, then by name (`hostdial.Hosts`: each Provider enrolls with its age when its manager starts, leading or not, and a younger one is not admitted while an older one has not said which host it uses), so a restart cannot hand it to another. The key is lower case. The Provider's controller refuses the others: it submits nothing and sets the Provider's `Ready` condition to False with reason `LoginHostInUse`, naming the login host and the Provider that holds it. The planner then treats it as unusable (`ProviderUnavailable`, HBEP-7), so no Allocation waits on it.
- **The agent's identity** is a random agent instance ID that the agent draws at its start (`agentapi.HeaderAgentInstanceID`), and the scheduler's restart count of the job in the registration (`RegisterRequest.RestartCount`, from `SLURM_RESTART_COUNT`). The kernel's boot ID is never used: a requeued job can land on the same node with no reboot. Registration is soft state: after a controller restart every agent registers again on its next poll, with the same ID, and no Instance fails and no generation rises.
- **The launch** always passes `--max-num-seqs`: the serving spec's value, else `v1alpha1.DefaultMaxNumSeqs` (256). `launch.maxNumSeqs` records it, and the front's cap, when `routing.instanceCap` is unset, is that times the Instance's workers (HBEP-5, HBEP-7). The controller renders every flag as one `--name=value` argument, and a CEL rule on the launch refuses a max-num-seqs argument in any other form or with another value than `launch.maxNumSeqs`.
- **The drain window** of an Instance is `v1alpha1.InstanceDrainWindow(profile, routing)`: `drainWindow`, or `routing.maxRequestDuration` plus `drainMargin` when that is shorter. The front and the lifecycle controller both call it, so both compute the same drain start (`v1alpha1.DrainStart`).
- **The image format.** Each partition's `imageFormat` (`sif` or `sandbox`) says what Apptainer runs on its compute nodes: `sif` on Helios GH200, `sandbox` on Athena A100 (spike S1, probe 2). It is not a deployment-ID input. The lifecycle controller sends `v1alpha1.ImageFormatOf(partition)` (`sif` when unstated) in `DesiredState.Settings.ImageFormat`, and the agent keeps the image at `agentapi.StagedImagePath(digest, format)`.
- **Agent builds** are a directory, `Host.AgentBuildsDir()`, of `agentapi.AgentBuildName(<cpuArch>)` files. The lifecycle controller sets `agentDigest` to the SHA-256 of the build for the partition's `cpuArch`. The provider finds the file by that digest and stages it at `agentapi.StagedAgentPath(digest)`.
  - **`hack/build-agents.sh DIR [CPUARCH...]`** (#158) cross-compiles `cmd/hb-agent` for `x86_64` and `aarch64`, or only the cpuArchs named, and places each as `DIR/hb-agent-<cpuArch>` (mode 755) with the DIR the controller reads, `<state>/agent-builds`. It prints each build's sha256, the agentDigest, and the `go version` that made it. Nothing else produces the aarch64 build Helios's GH200 needs.
  - **The build is static and reproducible, whatever the caller or the machine has set:** `CGO_ENABLED=0`, `-trimpath`, `-buildvcs=false`, Go's default architecture levels (`GOAMD64=v1`, `GOARM64=v8.0`), an empty `GOEXPERIMENT`, `GOFIPS140=off` and `GOWORK=off`. `GOENV=off` makes the go command ignore its saved configuration (`go env -w`), after `GOPATH`, `GOMODCACHE`, `GOCACHE` and `GOPROXY` were read once and passed explicitly, so a toolchain downloaded earlier is still found. `GOFLAGS` becomes `-mod=readonly` plus the caller's `-p=N`; every other entry (`-ldflags`, `-gcflags`, `-tags`, `-overlay` change the bytes) is dropped, and the script says so on stderr. The same sources therefore give the same bytes wherever the checkout is and whatever its git state, so a second run keeps the file in place (setting its mode to 755 if it was not) and the agentDigest does not move. `DIR` may be relative to the working directory. **The toolchain is pinned too:** the script sets `GOTOOLCHAIN` to go.mod's go line (`go1.26.0`, which CI installs; a patchless or release-candidate line, a comment and tabs are read as Go reads them), whatever the caller's Go or `GOTOOLCHAIN`. When that Go is not the one on `PATH`, the go command downloads it into the module cache (`GOMODCACHE`, once; its notice is on stderr, and only stdout is the version), and when it cannot the script exits 1 before it builds anything; it never builds with another Go. It prints `go version` next to each digest, and a test reads each output's embedded Go version and compares it with go.mod.
  - **One table maps the architecture names.** `hack/cpu-arch.sh`'s `CPU_ARCH_PAIRS` maps Go's and frp's `amd64` and `arm64` to the profiles' `x86_64` and `aarch64`, in both directions, for `hack/build-agents.sh`, `hack/fetch-frp.sh --agent-builds` and `hack/fetch-k3s.sh` alike. It is the bash copy of the first two columns of the launcher's `archTable` (`internal/launcher/arch.go`: Go's name, the cpuArch and the ELF machine type of a binary for it, the one place a Go architecture is added; `cpuArchOf`, `CPUArchs` and the agent build's ELF check read it); `TestScriptsMapArchitecturesAsCPUArchOfDoes` (`internal/launcher/frp_fetchscript_test.go`) compares the two and fails on a script that sources the table less or spells a map of its own.
  - **Tests** (`internal/testenv/build_agents_test.go`) build the real command offline. They read each output's ELF machine type (`EM_X86_64`, `EM_AARCH64`, written out in the test), its program headers (no `PT_INTERP`), and the build settings Go embeds; and they build from a copy of the sources at another path with no `.git`, with other `GOAMD64`/`GOARM64` in the caller's environment, and compare the sha256 of each output with the working tree's.
  - **`up` and `status` check the builds against the PlatformProfiles in the API server** (#158). For each cpuArch some partition of some profile has, they check that `hb-agent-<cpuArch>` is a readable ELF file for the machine its cpuArch names (`EM_X86_64` or `EM_AARCH64`, so a binary for the other architecture under the right name is reported; it is shown with its machine and its sha256, the agentDigest; nothing pins the digest, so it has no expected one), and that `frpc-<cpuArch>` has the sha256 `frp-pins.txt` pins for it. A cpuArch that is not one of the launcher's `archTable` (`launcher.CPUArchs()`, the same two names as `hack/cpu-arch.sh`) has no builds at all, and is reported with the kernel's name when it is Go's or frp's spelling. The source is the API server, not the manifests `up` applies, so a profile applied later with kubectl is checked at the next `status`; a server without the PlatformProfile CRD (a 404), or with no partition in any profile, has nothing to check and passes. Any other answer is an error and the check did not run, never "no profiles": a list that is not a `PlatformProfileList` of hpcburst's group and version (an HTTP 200 with a Status in its body decodes to an empty list), an item that is not a `PlatformProfile` with a name and a `spec.providerKind` of managed, batch or static, a batch profile with no partitions, or a partition without a name or a cpuArch. The check runs only on a host that runs controllers, since they stage the builds.
  - **`up`** checks last, after the API server and the controllers are up. On a missing or mismatched build it prints `ERROR:` lines that name the cpuArch, the digest found and the digest expected, and the fix (`hack/build-agents.sh <state>/agent-builds <cpuArch>`, or `hack/fetch-frp.sh --agent-builds <state>/agent-builds`; the paths are shell-quoted, so the command runs for a state directory with spaces and quotes, and `hpcburst status --state-dir ...` after it too), and exits **4**, with the host left running. The report is printed as usual (`--json` includes `agent_builds`), so the operator fixes the builds and runs `status`. If the profiles cannot be read, the check did not run and up also exits 4, saying so.
  - **`status`** reports the same per cpuArch (`agent builds` section and `agent_builds` in `--json`), and a missing or mismatched build is a reason the host is unhealthy (exit 1) until it is fixed. With `--no-api`, or when the host is unhealthy before the API is asked, it says that the builds were not checked and why, since the profiles come from the API server.
- **`agent.json`** is `agentapi.AgentConfig`, written by the provider from the launcher's front settings, the agent endpoint's port and certificate pin, and the paths it resolved.
  - In ssh mode its user is the user who runs the controller.
  - In host-dialed mode it names no endpoint and no ssh settings: `endpoint` is empty and the `ssh` member is absent, and `Validate` refuses a file that sets either. It carries `allocation`, the Allocation's UID, in this mode only.
  - The launcher creates the endpoint's certificate and key and reserves a loopback port for the endpoint in its own block; the controller's server binds it.
- **Time limits** are durations in whole minutes. The lifecycle controller rounds `min(maxTime, leaseLimit)` down to a minute, and the provider refuses any other value before a call. HBEP-4's QOS limits make it `v1alpha1.AllocationTimeLimit(maxTime, maxWall, leaseLimit)`, the smallest of the three, with the bound that set it. The controller switches to it in #151's lifecycle change.
- **QOS limits** (HBEP-4, HBEP-7; the contracts of #151, whose lifecycle behaviour lands in #151's lifecycle change). The profile lists every QOS that a Provider's `qos` or a partition's `qos` names, with its limits. The Slurm provider sends a Provider's `qos` as `--qos` and fails reading the profile when the profile does not list it.
  - `v1alpha1.EffectiveQOSLimits(profile, partition, providerQOS)` applies Slurm's order per limit: the partition QOS first unless the job QOS has `overPartQos`, and the first QOS that sets a limit gives it. With no Provider `qos`, only the partition QOS's typed limits apply.
  - `v1alpha1.MaxAllocationGPUs` is the smaller of `gpusPerNode` and `maxGpusPerUser`.
  - The Slurm plugin calls both for its refusals before any call, and the lifecycle controller is to call both, so the plan and the pre-call refusals agree.
- **A policy refusal** is a `*provider.PolicyRefusal` (Slurm's reason name and reason line), found with `errors.As`. For the five submit-count names (`provider.IsSubmitLimitReason`), the Provider's controller writes the submission record with `code: SubmitLimitReached`, in the same write as its Rejected state. The lifecycle controller matches that code, never the text (`@hpc-burst-science-agent`, 1 Nov 2026).
  - Readers check a record with `SubmissionRecord.Validate`.
  - The fake controller and the Slurm provider's controller write the code. The lifecycle controller's reading of it lands with #151's lifecycle change.
- **Check sampling** is `agentapi.CheckSampling(generationConfig, doSample, reasoning)`. Before it, `agentapi.CheckGenerationConfig` refuses a staged `generation_config.json` whose sampling values vLLM v0.32.0 would refuse, for every model, so verification fails with `VerificationFailed`. The agent is to send it on every verification, qualification and warm-up request. The lifecycle controller is to record it in the verification record, from the same reported inputs, because the record is written at verification time and never rewritten (HBEP-7, The allocation agent, Checks).
  - Both land with #151's agent change. Until then every check is greedy.
- **The verification record says whether the checkpoint has a `generation_config.json`** (#175). `agentapi.VerifyResult.GenerationConfigFile` is `absent` (the checkpoint directory has no entry of that name; vLLM then builds its defaults from `config.json`, which the checks do not read), `present` (an entry resolves to a regular file the agent can open, whatever it holds, so an empty file or one that is not JSON is present with no keys; `GenerationConfig` holds the keys it sets of those vLLM applies, none when it sets none or only nulls), `unreadable` (an entry is there that does not resolve to a readable regular file: a directory, a dangling symlink, a permission error, or an unreadable checkpoint directory), or empty (the agent had no staged checkpoint directory and looked at nothing). The science agent's ruling of 1 Nov 2026 is that `unreadable` never passes: it is to pair with #169's whole-file refusal (`VerificationFailed`) and never with greedy checks. This change only reports the value; the pairing arrives with #169, and a test pins it in whichever of #169 and #182 merges second. `internal/agent`'s `generationConfigFile` sets it from the staged directory, with `Lstat` first, so a dangling symlink is not taken for a missing file; the lifecycle controller copies it into the record (`generationConfigFile`, in the record's JSON in a ControllerRevision; it is not a CRD field, so no CEL rule applies).
- **Restart generations** live in Instance annotations, `v1alpha1.RestartGenerationAnnotation(part)`. Part is `instance` for the whole Instance, or `worker-<i>`. The controller records the restart in `status.restarts` (`v1alpha1.InstanceRestart`: part, generation, time, signal; entries within `restart.window`, at most 16) and emits its event first, then raises the generation by compare-and-swap. The attempts per rung are counted from `status.restarts`, so they survive a controller restart.
- **Provider readiness.** A batch Provider's controller reads the platform at least every `v1alpha1.ProviderPollInterval` (1 min): on a pass that observes no job it calls `provider.Batch.Poll`. `Ready` is True with reason `Polled` after a pass whose reads all succeeded; after a failed pass whose last success is older than `v1alpha1.ProviderReadyStaleness` (5 min), or with none, it is False with `ReadsFailing`. The lifecycle controller judges with `v1alpha1.ProviderReady(provider, now)`, which also checks the age, so a stopped Provider controller stops counting as ready.
- **Queue waits** are recorded once per job: when the recorded job is first seen with a start time and `status.atProvider.queueWaitRecorded` is false, the Provider's controller adds the wait to the Provider's status (`v1alpha1.AddQueueWait`, keyed by job ID), and only after that write succeeded sets `queueWaitRecorded`. A failed write is retried at the next observe. **The exception:** an Allocation that carries `v1alpha1.AnnotationQueuedSuccessor` (`hpcburst.groundnuty.github.io/queued-successor`, the queued-successor mark) adds no wait, but its `queueWaitRecorded` is set all the same, so once the job ends its observation is final and the job is not read again (HBEP-4, Provider status). The lifecycle controller writes the mark once, in the Allocation's create request, when the Allocation is for a no-overlap successor of a primary, or for a retry of one, whose own Allocation on the same Provider still holds its slot: the successor pends behind the per-user cap that primary holds, not in the scheduler's queue (HBEP-7, Handover, No-overlap mode; HBEP-11, Ownership). The condition reads the slot count's own test (`holdsSlot` in `internal/lifecycle/slots.go`), so a one-slot successor, created after the primary's job left the slot, is not marked. Both recorders (`internal/providerctl/observe.go`, `pkg/provider/fake/controller_wait.go`) skip a marked Allocation.
- **The idle anchor.** Retention's `idleLimit` and the profile's `maxIdle` count from the Allocation's `idle-since` annotation (`v1alpha1.IdleSince`), which only the lifecycle controller writes: the latest `status.endTime` of the Allocation's Instances when its last Instance ends, or the job's start when the job starts with no Instance placed; it is removed when an Instance is placed. It survives a controller restart and the deletion of the Instance.
- **Warm-up gates ready.** The lifecycle controller marks an Instance ready only after a report whose `WarmUp.Done` is true for the current verification generation: it judges settling from the rounds, sends a desired state without `WarmUp`, and the agent cancels in-flight warm-up requests and reports Done (`agentapi.Checks.WarmUp`).
- **Report size.** `workload.targetSessions` is at most 1024 (`v1alpha1.MaxTargetSessions`, `agentapi.MaxTargetSessions`), and the agent cuts a timing's error to `agentapi.MaxTimingErrorBytes` and other messages to `agentapi.MaxMessageBytes`, so the warm-up results of all five rounds take at most `agentapi.WarmUpBudgetBytes` (3 MiB) of the 4 MiB body limit. Both sides encode and decode bodies with `agentapi.EncodeBody` and `agentapi.DecodeBody`, which apply the limit. Bodies and the Authorization header are never logged; `Redacted()` gives a desired state or report without its secrets.
- **Health metrics can be unknown.** `agentapi.Health`'s gauges and counters (`RunningRequests`, `WaitingRequests`, `GeneratedTokens`, `KVCacheUsage`, and HBEP-8's `Preemptions`, `PrefixCacheQueriedTokens`, `PrefixCacheHitTokens`, `TimePerOutputTokenSecondsSum` and `TimePerOutputTokenCount`) are pointers, and `ResponsesByStatus` is a map: a value the agent did not read is absent, which decodes to nil and means unknown, never zero. `Health.MetricsReadAt` is the time of the last successful `/metrics` read, by the agent's clock. The lifecycle controller takes no gauge-based action (idle, KV pressure, the only-errors and no-progress signals) while the metrics are not fresh, that is while `MetricsReadAt` is nil or older than `agentapi.MetricsStaleProbeIntervals` (2) probe intervals. `Health.MetricsFresh(reportTime, receivedAt, now, probeInterval)` judges three ages, each at most two intervals: the read when the sample was taken (`Time` minus `MetricsReadAt`), the sample when its Report was made (`reportTime` minus `Time`), both on the agent's clock so skew does not enter, and the Report since the controller received it (`now` minus `receivedAt`, on the controller's clock). The last two close the gap of a cached sample that an agent keeps reporting. The controller also compares two samples' counters only when `MetricsReadAt` advanced. `ResponsesByStatus` has no `omitempty`: nil is unknown (`null` on the wire), `{}` is a read that found no responses. `@hpc-burst-science-agent`, 31 Oct 2026. The fakes' Health doubles read their metrics at every sample; `HealthMetricsUnreadable`, `HealthMetricsStale` and `HealthCached` model the three ways they are not. HBEP-8's five fields are read from vLLM v0.32.0's `vllm:num_preemptions_total`, `vllm:prefix_cache_queries_total`, `vllm:prefix_cache_hits_total` and the `_sum` and `_count` of `vllm:request_time_per_output_token_seconds`, in the same `/metrics` read, and follow the same rule: a line the engine does not export is nil, while a real vLLM with prefix caching off exports both prefix-cache counters at 0, a known zero. `MetricsFresh` covers them with the rest. `HealthEngineCounters` and `HealthWithoutPrefixCache` are the doubles for them.
- **Check outcomes carry a reason code.** A failed check's `agentapi.CheckOutcome` has `Reason`, a CamelCase code from the `agentapi.Reason*` constants (`pkg/agentapi/checks.go`: the corruption check's four from `agentapi.JudgeCorruption`, the answer failures, `Loop` and `ReasoningBudgetExhausted`), and `Message` stays human text. The lifecycle controller matches on `Reason` and never on `Message`. The behaviour check also reports `ContextTokens`, the prompt length it actually ran at, which the controller records. Without a reasoning parser that is `contextTokens.longest`; with one the agent shortens it to max-model-len minus the template overhead minus the typical output minus 4,096 (`agentapi.ReasoningHeadroomTokens`), never above `longest` and never below `typical` (`agentapi.BehaviourContextTokens`). `@hpc-burst-science-agent`, 31 Oct 2026.
- **Engine doubles.** The Go result doubles in `pkg/agentapi/fake` drive the fake agent only. #60's real agent needs its own socket-level, OpenAI-compatible engine double (HBEP-7: an engine double behind a real agent); it lives with #60's tests.
- **Verification records** are one per verification, `ver-<instance UID>-<generation>`, with the generation counting from 1 (`v1alpha1.NewVerificationRecord`). The Instance's status names the latest. A record that already exists is read, never rewritten.

## Checks

- `hack/check.sh` runs gofmt, vet, `go mod tidy -diff`, the generated-file check and the tests, then lists every skipped test. Run it under `nice` and the shared build lock. To run the frp tests in it instead of skipping them, install the binaries first: `hack/fetch-frp.sh "$FRP"` once, then `HPCBURST_FRP_DIR="$FRP" hack/check.sh` (add `HPCBURST_REQUIRE_FRP=1` to make a missing binary a failure, as CI does).
- `hack/go-test.sh` is the root module's test run, which `hack/check.sh` and CI's `go` job share. It runs every package with the tests of its groups left out by their exact names, then each group alone under a timeout of its own: `lease` (`TestLifecycleManagerReleasesItsLeaseOnEveryStop`, #282), and `livechecks-hostdialed` and `livechecks-dry`, `hack/livechecks`' dry runs through `hack/live-checks.sh`, which build and run the real test binaries and agent (PR #306). A group fails unless each of its tests passed and nothing in it skipped, subtests included, because `go test` exits 0 when `-run` matches nothing and a skipped subtest leaves its parent's `PASS`; the script also refuses a listed name that is not declared exactly once in the root module, since `-skip` applies to every package. So each package stays clear of `go test`'s 10-minute package timeout, which is not raised. `hack/go-test.sh own <group>` runs one group; CI runs each as a step of its own. A plain `go test ./...` still runs every test.
- `hack/mutate-cel.sh` neutralises each CEL admission rule in a copy of the CRDs and runs the test that covers it, which must fail. It takes about ten minutes, so it is not part of `hack/check.sh`; run it when a rule or its test changes. A rule with no entry in its table fails the script.
- The flag-name tests read the known flag names from HBEP-3's v1 table, so the admission rules' lists of known names are checked against the specification. A flag added to the table fails `TestEngineFlagsRefuseEveryPrefixOfAKnownFlag` until the list in the `EngineFlag` markers (`api/v1alpha1/modeldeployment_types.go`) gains it.
- Tests that start frp read `HPCBURST_FRP_DIR=<dir>` (an absolute path: a test runs in its package directory, so a relative one fails the test) through `testenv.FrpBinaries(t)`; a plain `go test ./...` takes it the same way (`hack/fetch-frp.sh <dir>`, then `HPCBURST_FRP_DIR=<dir> go test ./...`). `hack/fetch-frp.sh <dir>` installs the pinned `frps` and `frpc` there (the tarball's sha256 is checked before anything is extracted). Without `HPCBURST_FRP_DIR` those tests skip with a message; `HPCBURST_REQUIRE_FRP=1` fails them instead, and CI sets both in the `go`, `crd and envtest` and `launcher-k3s` jobs. A binary that is there but not executable, not runnable or not 0.71.1 fails in either mode.
- The `go` and `crd and envtest` jobs provide OpenSSH's sshd for the ssh-mode tunnel tests in `internal/agent` (`HPCBURST_SSHD`). This is the workflow's one use of sudo. It installs only `openssh-server`, and only when `/usr/sbin/sshd` is missing; the ubuntu-24.04 runner already has OpenSSH_9.6p1, so in practice the install does not run. It never starts the system service and stops it if it runs. The tests run sshd as the user, in inetd mode (`@hpc-burst-science-agent`, 31 Oct 2026).
- **CI caches the pinned binaries** (issue #290), so that an outage of GitHub's release downloads does not fail every job. Each job that fetches (`go`, `crd and envtest`, `launcher-k3s`, `rehearsal`, `rehearsal part 3`) restores the directories that `hack/fetch-frp.sh`, `hack/fetch-k3s.sh` and `hack/test-binaries.sh` install into, runs the same scripts, and saves the directories when the cache had no entry. The scripts check every file against its pin on every run, so a cache never replaces verification: a file that does not match is downloaded again (in `hack/test-binaries.sh` only a file in its own cache directory; one named by `HPCBURST_ENVTEST_ASSETS` or `HPCBURST_KUBE_CONTROLLER_MANAGER` stays an error). A key is exact (OS, architecture, a hash of the files that hold the pins, and the k3s versions), so changing a pin or a version misses and downloads once. GitHub lets a pull request read only its own branch's caches and `main`'s, so the entry that serves every pull request is the one a run on `main` saves; `workflow_dispatch` on `main` re-seeds it after GitHub evicts it (7 days unread). To test a script offline, point `FRP_RELEASE_BASE`, `K3S_RELEASE_BASE`, `K8S_RELEASE_BASE` or `ETCD_RELEASE_BASE` at a `file://` directory, and `FRP_PINS_FILE`, `K3S_PINS_FILE` or `TEST_BINARIES_PINS_FILE` at a pins file made for it (tests only).
- **CI installs Go from a pinned tarball, not with `actions/setup-go`** (issue #294). setup-go fetches the toolchain from GitHub's release assets in every job, checks no digest of it (its installer uses `crypto` only to name a cache directory), and caches no toolchain between runs. Every job runs the same five steps instead (a test compares the six copies): read go.mod's version with `hack/fetch-go.sh --version`; restore `$RUNNER_TEMP/go-download` from a cache; `hack/fetch-go.sh DOWNLOAD_DIR INSTALL_DIR`; save the directory when the cache had no entry; `hack/fetch-go.sh --check INSTALL_DIR`. The script checks the tarball against `hack/go-pins.txt` on every run, restored or not (a tarball that does not match is deleted and downloaded again from `https://go.dev/dl`, and a download that does not match fails the run), extracts it anew into `INSTALL_DIR/go` (an existing tree is never reused, so every file that runs comes from the verified bytes, not only the binary a pin names), and checks `go/bin/go` and `go/VERSION` against the release. The cache holds the tarball only, under one exact key (the Go version from go.mod, OS, architecture, and a hash of the script and its pins; no `restore-keys`), and, unlike the binaries' caches, is saved only by a push to `main` and by `workflow_dispatch`. The check step (id `gocheck`) shows that the go on PATH is the pinned one (the runner image has others) and that `go env GOROOT` is the installed tree, which the install step exports through `GITHUB_ENV` (a GOROOT inherited from elsewhere fails the check, since the go command would build with that tree's compiler and standard library). A step that runs even after an earlier failure (`!cancelled()`) must also require `steps.gocheck.outcome == 'success'`, or it would run on the runner image's own go when the install failed; a test enforces it for every job. Moving go.mod to another release needs its line in `hack/go-pins.txt` in the same change, or every job fails before it builds anything. The offline tests (`go test ./hack/gotoolchain`) use `GO_RELEASE_BASE` (a `file://` directory), `GO_PINS_FILE` and `GO_MOD_FILE`.
- The test host (`internal/testenv`) binds only loopback ports 29200 to 29219 and, in k3s mode, accepts only a kubeconfig whose server is loopback on 29200 to 29239. The control-plane binaries are always sha256-checked; `HPCBURST_TESTENV_UNPINNED=1` is the explicit override for a binary you built yourself.

## Live checks

Some tests run only against a real system and never in CI: the real LLMLab smoke test (`internal/front`), the Slurm conformance runs (`internal/providerctl/conformance`), the real-engine run (`cmd/hb-agent`) and the Hub golden test (`pkg/hubfiles`). HBEP-15 (Upgrading a pinned dependency) requires every live test that runs the changed code to run again after a merge. `hack/live-checks.sh` is the one entry point (issue #163).

- `hack/live-checks.sh --plan <base>..<head>` lists which live tests cover the range and runs nothing. It maps each changed file to the code a test runs, read from the two ends of the range (copies of their trees, never the current checkout): the packages the test's package imports (`go list -deps -test`, in the host build and, for the real-engine run, the linux/arm64 build), the files they embed wherever those sit (a deleted one counts, from the base), and the inputs named in the table (a glob, a directory or a file: the profile a conformance run reads, the Hub golden test's reference files, the real-engine job script). A change to `go.mod` or `go.sum` selects every test. A test file counts only for its own package. A discovery that fails, or lists nothing, fails the plan (exit 2); it never reads as "no live test covers this range". The last line, `run: <names>`, is the list to pass to `--run`.
- `hack/live-checks.sh --run <name>... [--yes]` runs only the named tests, each with its gate set from a settings file. `HPCBURST_LIVE_SETTINGS` names that mode-600 file; the script's header lists its keys (the output directory, the lock directory, the grant accounts, the credentials files). A cluster test prints its shape and the queue estimate (`sbatch --test-only`) and runs only with `--yes`.
- **What reaches the screen.** Statuses and counts, and fixed labels: never a key, a URL, a job ID, a host, an account, a private path or the name of a failed subtest. A tool's own diagnostics go to a log in the output directory, not to the screen. **The logs and records there are raw** (a test's log can hold anything the test printed): they are mode 600 in a mode-700 tree, and the no-secrets guarantee is for the screen only.
- **Skips are failures,** at any level: a live test that skips because its gate was not met, or a subtest that skips, reports FAIL.
- **Exit codes:** 0 passed; 1 failed, skipped for want of its gate, or left a job; 2 usage error, an unreadable range or discovery, or a table of the script that loads no rows; 3 refused, or `NOT RUN`: a job that never started within its bound, the one skip that is not a failure ([What a run ends as](alpha-runbook.md#what-a-run-ends-as)); 4 a cluster test not run for want of `--yes`.
- **The one-job slots** (QOS `now` on Helios, `plgrid-now` on Athena; owner's rule of 1 Nov 2026, issue #145). The script refuses to queue behind a job that already holds a slot, and runs one cluster test per host at a time (a run lock in `LIVE_LOCK_DIR`, for every cluster test, slot or not) with the test's own shortest time limit. The builds, and for the real-engine run the plan and the staging, come before the slot is taken, so the printed use covers only the time the slot was held: a UTC start, end and duration, to post on the issue the run served.
- **Cleanup** runs on every exit, signals included, and cancels only what this run owns. The real-engine run writes its job name to a file before it submits, and cancels its job by the ID it was given; a lost submit reply is reconciled by that name. A conformance run's test writes the tag of each Allocation to `job-tags.txt` in its record directory before anything can submit it (`internal/providerctl/conformance`), and the script cancels the jobs with those names. A job that only appeared in the same partition is never touched: the owner's controller or a manual run does not take the script's lock. A known job ID is cancelled even when `squeue` cannot be read; the failed verification is reported apart ("could not be read", never "left behind 0") and the exit trap tries once more. A run killed with SIGKILL cannot clean up; look at the queue.
- **The real-engine run** builds the arm64 agent and test binary and the plan on this host, stages them under `$SCRATCH/hpc-burst-live/<tag>` on the cluster, submits `spikes/s94/job.sh`, polls with short calls and fetches the log and the record into a directory of this run's own (a failed or empty fetch fails the run). Its budget has two clocks: the job may wait in the queue for 30 minutes, its one-job slot's bound (`LIVE_PENDING_MAX_SECONDS` overrides it), and from its first state other than PENDING it may run for its time limit plus 15 minutes. Either overrun cancels it: the first is `NOT RUN` only when the job's history, read with `sacct --json` once the cleanup has cancelled it, shows that it never started (a start, or a history that cannot be read, is a failure; #297; the reply is decoded by `python3`, which this host then needs, and a missing one fails the row before anything is submitted), and only a read that says PENDING can end that wait; the second is a failure, as are three unreadable reads in a row. The staged files stay on the cluster; deleting them needs the owner's go. The registry token that `job.sh` uses for its pull-limit check goes to curl on standard input, never in its arguments.
- **Builds** take the shared build lock when `LIVE_BUILD_LOCK` names one (`flock -o`, builds only, never a test run).
- **Adding a live test.** Add a row to the table in `hack/live-checks.sh` (and a shape row for a cluster test), and put a directive in the doc comment of the Test function: `//livecheck:<row>[,<row>]` for the rows that run it, or `//livecheck:none <reason>` for a test of a live file that is not a re-run target. `hack/livechecks` finds the live files by scanning the tree for a `t.Skip` that says it needs a real or live system next to an environment read, for a `_live_` file name, for the table's gate variables, and for a call to a gate helper wherever the helper is defined. It fails when a package that holds one has no row, when a Test function of a live file has no directive, when a directive names a row that does not exist, belongs to another package or whose `-run` pattern does not match the function, and when a row's pattern also runs a function that does not name the row.
- **The alpha rows** (#194; `docs/alpha-runbook.md` lists each run's settings, duration, slot use, posts and pass criteria): `alpha-athena-handover`, `alpha-helios-nooverlap`, `tunnel-hour-helios`, `tunnel-hour-athena`, `gpu-accounting-helios` and `gpu-accounting-athena`, with `tunnel-hour` and `gpu-accounting` as aliases for their two rows. The reach rows (#225), `reach-helios` and `reach-athena` (alias `reach`), confirm that a compute node reaches the gateway's forwarded port; their test is `TestReach` in the conformance package, the probe is `testdata/reach-probe.sh` there, and the stand-in sockets for its tests are `internal/providerctl/ctltest/reachstub.go`. The stack rows' tests are in `internal/alpha` (the criteria, the recorder that writes job tags ahead of every submission, the settings, and the stand-in steps of the dry run); `--plan` also takes the dependency closure of the stack's binaries for them (the plan-stack table in the script). The accounting rows' test is `TestGPUAccounting` in the conformance package. A row's own test runs in dry mode, through the script, in `hack/livechecks` (`HPCBURST_LIVECHECKS_ALPHA_TEST` and `HPCBURST_LIVECHECKS_CONF_TEST` name prebuilt test binaries; unset, the test builds them): a fake Slurm in run mode stands where the cluster would, the healthy run passes and every fault fails the row. `hack/mutate-alpha.sh` changes each criterion's condition and requires a test to fail. A stack row's deployment has the shortest lease (the lead plus a minute, `internal/alpha/rows.go`; the tunnel rows take 2 h 17 min by default, chosen by the GH200 start-to-ready measurement of 23 min 39 s on #94, and `LIVE_TUNNEL_LEASE_MINUTES` lets the owner choose another) and allows its cluster's Provider alone; `alpha-helios-nooverlap` and `tunnel-hour-helios` hold QOS `now`'s GPU for hours and refuse unless `LIVE_OWNER_GO_HELIOS_NOW` holds today's UTC date.
- The tests of the script itself run in the `go` job with the rest of the module (`go test ./hack/livechecks`). They start no live test and read no credential.
- **The rehearsal rows.** The one-host rehearsal's third part (#193) is the local row `rehearsal-part3`: no cluster and no `--yes`. It builds the stack's four binaries and the test binary under the build lock, then runs `TestRehearsalPart3` through `hack/rehearsal.sh` (`REHEARSAL_PREBUILT=1`), whose systemd scope stops everything the run started. `LIVE_BIN_DIR` must hold `k3s-1.36.5/k3s`, `frps` and `frpc`. The `rehearsal` row, a cluster run of the rehearsal, is still `pending`; #146's own two tests, `TestRehearsalDirect` and `TestRehearsalSSH`, and #298's `TestRehearsalHostDialed` run in CI's `rehearsal` job and in `hack/rehearsal.sh`'s default (`^TestRehearsal(Direct|SSH|HostDialed)$`), and #193's in `rehearsal-part3`. The rehearsal binds loopback ports 29500-29539 for #146's tests, 29680-29699 for #193's and 29780-29799 for #298's. `TestRehearsalHostDialed` takes the launcher's block 29780-29792 and the front's client on 29793, with no dial-home listener for the nodes, since nothing dials in. `TestRehearsalHostDialed` shows that a relay killed mid-stream cuts the stream and frpc logs in again, that a controller restart stops the relays by PID and the new leader starts both again, and that no relay is left once the job ends.

## Running the e2e suite on the launcher's k3s

`hack/check.sh` runs the e2e suite on the assembled host of `internal/testenv`. The same suite also runs on the user-level k3s that `hpcburst up` starts, which is the host HBEP-11 specifies; `TestRunsOnK3s` then passes instead of skipping. Run it before merging a change to the CRDs:

```
hack/fetch-k3s.sh <bin-dir>      # once: the pinned k3s binaries
go build -o <tmp>/hpcburst ./cmd/hpcburst
<tmp>/hpcburst up --state-dir <state> --port-base 29220 --bin-dir <bin-dir> --manifests config/crd
HPCBURST_TEST_HOST=k3s HPCBURST_KUBECONFIG=<state>/kubeconfig go test -count=1 ./api/v1alpha1/e2e/
<tmp>/hpcburst down --state-dir <state>
```

With `--port-base 29220` the launcher's block is 29220 to 29232, and the suite refuses a kubeconfig whose server is outside 29200 to 29239 (`internal/testenv`, `ExternalPortLast`). `up` installs the deletion guard of `config/admission/` on every start, whatever `--manifests` names (see "The launcher"), so on this host `TestCRDDeletionGuard` finds it installed and skips the steps that install and remove it, and `TestLauncherInstallsChecksAndRemovesTheGuard` skips. Keep `config/admission/` out of the manifests directory all the same: the guard is the launcher's to install.

## API field names

Every field of the CRDs is camelCase, as the Kubernetes API conventions ask (owner decision, PR #48): `holdRelease`, `lostGrace`, `imageDigest`, `gpuModel`, `timeZone`, `jobName.maxLength`, `cpusPerGpu`, `memPerGpu`, `gpusPerNode`. HBEP-3's hash object keeps its snake_case keys (`image_digest`, `gpu_model`, `cpu_arch`); `pkg/deploymentid` maps the API's fields onto them, and nothing in the API changes the hash. `TestEveryCRDFieldIsCamelCase` scans the committed manifests. HBEP text that writes a field in snake_case (`hold_release` in HBEP-11) means the camelCase field.

## Rules for every change

- **Dependencies (provenance):** a Go module enters through `go.mod` and `go.sum` only. The PR description lists each new direct dependency with its project, URL and version, and answers the questions in HBEP-15, "Dependencies". The HBEP that adopts it lists it under "Community software reused". A binary the framework downloads is pinned by sha256 in the pins file the code reads (see "Pinned versions"). Copied code goes under `third_party/forked/<project>/` with its upstream `LICENSE` and an `ORIGIN.md`.
- **Tests:** they come with the change. Expected values come from specifications or an independent implementation, never from the code under test.
- **Public content:** this repository is public. No host names, IP addresses other than loopback, job IDs, account or grant names, credentials or internal paths (HBEP-1).

## The launcher

`hpcburst` (`cmd/hpcburst`, code in `internal/launcher`) starts and supervises the single-user control-plane host of HBEP-11: the pinned k3s as the invoking user, with `server --rootless --disable-agent` and SQLite. It supports Linux only, because every health and stop decision is tied to `/proc`.

```
hpcburst up      --state-dir D --port-base 29220 [--version V] [--manifests DIR] [--front-mode direct|ssh --front-addr HOST[:PORT] [--front-key FILE] | --front-mode host-dialed] [--controller-bin PATH] [--front-config FILE [--front-bin PATH]]
hpcburst status  --state-dir D [--json] [--no-api]
hpcburst upgrade --state-dir D --to V
hpcburst restore --state-dir D --backup D/backups/<backup>
hpcburst down    --state-dir D
hpcburst guard remove --state-dir D
```

- **State:** everything the launcher owns is in the state directory (default `$XDG_STATE_HOME/hpcburst`, else `~/.local/state/hpcburst`): k3s's data directory, home and log, the record of the processes it started (`state.json`, with PID and start time), and `kubeconfig` (mode 600, written only once the host is ready).
- **Binaries:** `up` and `upgrade` look for `k3s-X.Y.Z/k3s` under `--bin-dir` (or `$HPCBURST_BIN_DIR`, else `~/.cache/hpcburst/k3s`), open it, and check the sha256 of what they opened against `internal/launcher/k3s-pins.txt`. k3s is then executed from that same descriptor (`/proc/self/fd/3`), so the bytes that run are the bytes that were checked. `hack/fetch-k3s.sh [DIR]` downloads and checks them. The pins file is the one place that says which versions are allowed, and `hack/fetch-k3s.sh` reads the same file, so there is no second copy. HBEP-15 keeps the checksums in this file; it adds no central list of versions.
- **Versions:** `store-version.json` in the state directory records the release that last wrote the store, and `down` keeps it. `up` without `--version` starts that release; `up` with another one is refused. A newer release goes through `upgrade` (the next minor, or a newer patch or k3s revision of the same minor), which backs the store up first. An older one only through `restore`, from a backup that `upgrade` took.
- **Backups and restore:** `upgrade` stops the host, copies `data/server/db` and the server token to `backups/<time>-<release>/` (mode 0600, synced), records the new release, and only then starts it. `restore` needs the host stopped. It moves the current store and token aside to `data/server/replaced-<time>/`, copies the backup back, and records the backup's release. Changes made after the backup are lost from the store.
- **Health:** `status` judges from the recorded processes, through a pidfd for each: PID, start time and boot ID must match. k3s must run a binary unpacked in its own data directory (k3s otherwise falls back silently to a system k3s's `/var/lib/rancher/k3s/data`). The process must hold exactly its loopback ports. Only then does it ask `/readyz`, the controller manager's `/healthz`, a small write to the store, and a garbage-collector probe (an owner and a dependent ConfigMap in namespace `hpcburst-launcher`; the dependent must be gone within a minute; `--no-gc-probe` skips it). Afterwards it checks the listeners and identities again. A listener that answers on a port but is not held by the recorded process never counts.
- **Processes:** the launcher signals only through a pidfd it verified (taken at launch from clone, or with `pidfd_open`), and reads exits from the pidfd. A process whose identity cannot be checked is never signalled, and `down` then exits 1 and keeps the record.
- **Audit:** the API server writes an audit log at the Metadata level to `logs/audit.log` in the state directory (no request or response bodies, so never a Secret's content), at most four files of 100 MB.
- **Events:** `up` starts k3s with `--kube-apiserver-arg=event-ttl=168h`, so the API server keeps an Event 7 days, where its own default is one hour (HBEP-8, Retention; issue #109). It records the value in `state.json` as `event_ttl`, in the first record of the start, from the same call that builds the argument. `status` reports it from that record, not from the running process or the API server (k3s rewrites its own command line after it starts, and the API server's `/flagz` debugging endpoint has no format guarantee, so neither is read): `event TTL: 168h` in the text, and `event_ttl` in `--json`. A record without it, from a host that an earlier release started, stands for the API server's default: `status` prints `event TTL: 1h (default; restart to apply 168h)`, sets `event_ttl` to `1h` and `event_ttl_default` to true in `--json`, and the host stays healthy. `down` and `up`, or `upgrade`, start k3s from arguments built afresh, so the next restart applies it and the new record holds `168h`. A restart restarts the clock of every Event, so an Event lives at least 7 days. The record says what the launcher passed, not what the API server does: `TestEventTTLIsHonouredByTheAPIServer` (`internal/launcher/eventttl_k3s_test.go`) starts k3s with a TTL of two minutes, through an option that only tests can reach, and shows the API server removing an Event after it.
- **CRD deletion guard:** `up` applies `config/admission/crd-deletion-guard.yaml` (embedded by `config/admission/embed.go`, so the launcher installs the repository's file) on every start, after `--manifests` and whatever it names, and a failure to apply it stops the start. It is a ValidatingAdmissionPolicy and a binding that refuse deleting a CRD of the framework's group (HBEP-11, Risks and Admission; issue #242). Removing it is the explicit step `hpcburst guard remove` (the binding first, then the policy; repeatable; the host must run), never a side effect of `down`, `upgrade`, `restore` or a restart. `up` installs it again. `status` asks the API server and reports the guard present (`CRD deletion guard: present` in the text, `crd_guard.present` in `--json`) only when the policy exists and a binding names it with Deny: the policy alone stops nothing, and the by-hand step the guide used to give deleted only the binding. Absent is printed as `ABSENT` with what is missing and does not make the host unhealthy, as an absent front does not; `--no-api` and an unhealthy host report nothing, because they did not ask. The tests that show it work delete a CRD: `cmd/hpcburst/guard_test.go` on a real k3s (refused after `up`, allowed after `guard remove`, status both ways), and `api/v1alpha1/e2e/guard_launcher_test.go` on the suite's control plane. A policy that exists but is never tried against a delete proves nothing.
- **Ports:** `--port-base B` names a block of 13 loopback ports, B to B+12, shared with the controller, the front and frps (`agentapi.Host`), and all of them must be free before `up` starts: B (apiserver), B+1 (https), B+2 (controller manager), B+3 (the agent endpoint, `agentapi.Host.AgentEndpointPort()`: the server of issue #60, which the controller binds; the launcher never binds it), B+4 (the front's `/healthz`, issue #64), B+5 (reserved, never bound), B+6 (the lifecycle controller's `/healthz`), B+7 (the front's dial-home listener in ssh and host-dialed modes, `127.0.0.1:<B+7>`, `Host.DialHomePort()`; the launcher never binds it), B+8 (the frps server plugin, which the controller binds), B+9 to B+11 (frps's bind, tcpmux and web ports, HBEP-6) and B+12 (the lifecycle controller's `/metrics`, `Host.ControllerMetricsPort()`, issue #111). A listener on any of them makes `up` refuse, naming the port. The default block is 29220 to 29232.
  - **In ssh mode a non-default base needs new restricted VM keys** (host-dialed mode has no key). Each platform's restricted key permits forwards to exactly `127.0.0.1:<B+3>` (the agent endpoint) and `127.0.0.1:<B+7>` (the dial-home listener), for the base it was made with (`@hpc-burst-science-agent`, 31 Oct 2026). A launcher started on another base needs keys made for that base, or its jobs' forwards are refused. `up` cannot warn yet: the step that makes the keys does not exist, so no record says which base they were made for (a TODO in `internal/launcher/ports.go`).
- **Controllers:** once k3s is ready and the manifests are applied, `up` creates the namespace `hpcburst-system` (`v1alpha1.ControllerNamespace`, where the controllers' Leases live), creates the host layout's `credentials` directory in the state directory with mode 0700 (`agentapi.Host.CredentialsDir()`) and, when it is absent, `agent-builds` with mode 0700 (`Host.AgentBuildsDir()`, where `hack/build-agents.sh` and `hack/fetch-frp.sh --agent-builds` place the agent builds and frpc; an existing one is left as it is), and starts a supervisor: a detached `hpcburst supervise --state-dir D --handoff-fd 3` process (own session, stdin `/dev/null`, output to `logs/supervisor.log`). It is a hidden subcommand, not listed in the usage. `up` records it in `state.json` as the process `supervisor`, after k3s, and waits until it reports every process started and still up half a second later, and, when it runs the front, until the front holds its health port and answers `/healthz` with 200 (the front binds its listeners only after its first lists, so a port taken meanwhile fails `up` instead of leaving a front that cannot start), all within 30 s; if the supervisor or a process exits meanwhile, `up` fails with the log's tail and stops everything it started.
  - **Handoff:** the supervisor outlives `up`, so one that `up` created but did not record could never be stopped by `down`. `up` therefore passes it the read end of a pipe (descriptor 3) and writes one byte to it only after `state.json` names the supervisor. The supervisor starts no process, and writes no `supervisor.json`, until it has read that byte; if the pipe closes first (`up` died, however it died) or nothing arrives within 30 s, it exits at once having started nothing. It closes the descriptor straight after, so no controller inherits it. `hpcburst supervise` without `--handoff-fd` is refused.
  - **The agent endpoint's certificate:** before it starts k3s (and again before the supervisor, and before `upgrade` stops the old host), `up` makes sure `agent-endpoint/tls.crt` and `tls.key` exist in the state directory (`Host.AgentCertFile()`, `Host.AgentKeyFile()`; directory mode 0700, key 0600). If neither exists it creates a self-signed ECDSA P-256 certificate for `127.0.0.1`, `localhost` and `agentapi.DialHomeServerName` (`dial-home.hpcburst.invalid`, the name frpc verifies, HBEP-6), valid for 100 years, with the key written first. A pair that exists is kept as it is, across `down`, `up` and `upgrade`, so the pin (`agentapi.PinOf`) the agents hold does not change; it must load as a pair, and the key must be a regular file owned by the user and readable by no one else. Otherwise `up` fails before it starts anything, naming the file and never printing key bytes. A kept certificate that is not valid for `agentapi.DialHomeServerName` (one made before the name was added) is issued again for the same key, in the same way as for a key alone, so the key file is not touched and the pin does not change: the new certificate's pin is compared with the kept one's before anything is written, and one that differs is refused, leaving the kept certificate as it was. A key without a certificate (a start killed between the two writes) gets a new certificate with the same pin; a certificate without a key is refused.
  - **What is supervised** is a list of entries (a name, an argument list and a health address). It holds `controller`: `hpcburst-controller --state-dir <state> --port-base <B> --health-addr 127.0.0.1:<B+6>`, plus `--front-mode M --front-addr A` when `up` recorded a front; in host-dialed mode `up` records the mode alone, so the command line carries `--front-mode host-dialed` and no `--front-addr`. The controller fills an `agentapi.Host` from the state directory and the port base, and takes `<state>/kubeconfig`, `Host.CredentialsDir()` and `Host.AgentBuildsDir()` from it; the launcher passes none of those paths. With `--front-config FILE` it also holds `front` (issue #64): `hpcburst-front --config FILE --state-dir <state> --port-base <B> --health-addr 127.0.0.1:<B+4>`, plus `--mode M` when `up` recorded a dial-home mode. The binary is `--front-bin PATH`, or `hpcburst-front` beside `hpcburst`; the front needs the controller binary, since it runs under the same supervisor. No key is on its command line: its configuration names the client keys file. The controller takes the Hugging Face Hub origin from `HF_ENDPOINT`: when set, it is the origin the lifecycle controller lists checkpoints from, and the Provider controller writes it into each Allocation's `agent.json` as `hubEndpoint`, from which `hb-agent` downloads them (a job does not inherit this host's environment; the agent falls back to its own `HF_ENDPOINT` only when `agent.json` names none); unset, it is `https://huggingface.co`. The supervisor passes `up`'s environment on, so `HF_ENDPOINT` in `up`'s environment reaches it.
  - **frps** (HBEP-6; HBEP-11, Single-user host) runs as one more entry, `frps`, whenever the controllers run. `up` resolves it from `--frps-bin PATH`, or `frp-0.71.1/frps` in `--bin-dir`, and checks it against `internal/launcher/frp-pins.txt`; a missing default starts no frps and `up` warns that Instances cannot open their tunnels, while a given path that is missing or does not match the pin fails before anything starts, as does `--frps-bin` without a controller binary. `up` then writes frps's web password (`Host.FrpsWebPasswordFile()`, kept when it exists) and its configuration (`<state>/frps/frps.toml`), both mode 600, and records the binary and version in `state.json` (`frps`). Before every start the supervisor copies the binary into a memory file (`memfd_create`), seals the copy against any write, growth or shrinking (`F_SEAL_WRITE`, `F_SEAL_GROW`, `F_SEAL_SHRINK`, `F_SEAL_SEAL`), checks the copy against the pin and passes that descriptor at fd 3, running `/proc/self/fd/3 -c <state>/frps/frps.toml --strict-config=true` with an environment of `PATH=/usr/bin:/bin` alone. So no change to the file on disk, by rename or by a write in place, can alter the bytes between the check and the exec. The kernel names such a process after the file it ran, so frps's command name is `3` (its `argv[0]` is the recorded binary's path, which `ps` shows): the launcher finds it by its recorded identity and its ports, never by name. A binary replaced or rewritten since `up` fails every start from then on (`start failed: ...` with the sha256 in `supervisor.json`), the entry backs off, and `status` reports frps as not running.
    - **Health:** frps's process tree must hold exactly base+9, base+10 and base+11 (bind, tcpmux, web server) as TCP listeners on `127.0.0.1`, matched by socket inode, and no other socket that can be reached from outside: no other TCP listener and no UDP socket without a remote address (KCP's or QUIC's would be one), on any address. No other process may listen on those three ports, at any address. frps must then answer `GET /healthz` on `127.0.0.1:<base+11>`, which its web server serves before the password check. `status` reports a missing, extra or misplaced socket of frps as a problem, and `up` waits for the listeners and the answer, as for the front.
  - **The binary** is `--controller-bin PATH`, or `hpcburst-controller` in the directory of the running `hpcburst`. A missing default is not an error: `up` starts the host, warns that no controllers run, and starts no supervisor. A given path that is missing, not a regular file or not executable fails before anything starts.
  - **Restarts:** the supervisor starts a process again whenever it exits, with any code, waiting 1 s, then 2, 4, 8, 16 and 30 s while it keeps exiting quickly; a process that ran for 60 s starts the sequence again. Each process's output goes to `logs/<name>.log`. Its environment is the supervisor's without `KUBECONFIG` and the in-cluster variables. A process is started with `Pdeathsig` SIGKILL, so a supervisor that is killed takes its processes with it.
  - **`controller/supervisor.json`** (mode 0600, replaced atomically at every start and exit) holds the supervisor's identity and, per process, its identity (PID, start time, boot ID), state, restart count and last exit.
  - **On SIGTERM** the supervisor sends SIGTERM to each process through its verified pidfd, SIGKILL after 10 s (the front: after `FrontTermGrace`, 30 s), waits, and exits 0. The front's 30 s are its longest normal stop, `FrontStopBudget` (26 s: 10 s for the requests in flight, 10 s more for the cut requests' handlers, 5 s for a cut stream's last event, 1 s to close the usage sink; HBEP-5, stop order), and a 4 s margin: a SIGKILL before the sink is closed would lose the cut requests' `front_shutdown` records.
- **Controller health:** `status` reports the supervisor and each supervised process, in the text and in `--json` (`supervisor`, `controllers`). Each process is checked as k3s is: a pidfd for the recorded PID, start time and boot ID must match, its parent must be the supervisor, and it must hold its health address (a listener bound to that address and port; the same port at another address does not count). Only then does `GET /healthz` on that address count, and the identity and the address are checked again after the answer. A dead or missing supervisor, or a process that is not running (including one waiting to restart), makes the host unhealthy (exit 1); a dead supervisor does not hide the results for k3s. A host started with no controller binary has no supervisor, and that is healthy.
  - **The front's usage state:** the front's `/healthz` body carries a `usage` member whose `state` is `ok` or `failing` (HBEP-8, Usage records). `status` reports it per process (`usage_state` in `--json`), and while it says `failing` the front's line ends with `degraded: usage writes failing` (`degraded` in `--json`). That is not a health problem: the front keeps serving, so the host stays `healthy`, no reason is added and `status` exits 0; only the front's line says degraded (`@hpc-burst-science-agent`, 31 Oct 2026; HBEP-11). A front whose body has no `usage` member, is cut at the 1 MiB read limit or states another value is reported as `usage state unknown` (`usage_state` `unknown`), again without changing the health.
  - **The controller's readiness:** the controller, and no other process, is also asked for its readiness on its health address, once its `/healthz` has answered 200 and before the identity and the address are checked again (HBEP-8, Observers; HBEP-11). It registers two readiness checks, `caches` (the informers of every kind it watches have synced; they start before it is elected) and `leading` (it holds the `Lease`; always passing under `--leader-elect=false`), and `/healthz` stays liveness. `status` reads each on its own path, by status code only, never by a body: `GET /readyz/caches` not 200 is `starting`; caches 200 and `GET /readyz/leading` not 200 is `not leading`; both 200 is ready. A 404 on either path means a controller from before the split, whose one check `serving` covered both: `status` then reads the aggregate `GET /readyz`, and a code other than 200 reads `starting, or not leading its Lease: /readyz does not say which`. A controller that is not ready makes the host unhealthy (exit 1) with a reason such as `controller: not ready: not leading: GET /readyz/leading on 127.0.0.1:29226 answered 500`. In `--json` the process has `readyz_ok` and `readyz_state` (`ready`, `starting`, `not leading`, or the fallback text; empty when the paths could not be read). The check names are an interface; the paths are controller-runtime v0.23.1's (`pkg/manager/internal.go:308-310`, `pkg/healthz/healthz.go:158-165`, `:175-180`). Right after `up` a real controller may need a few seconds to win its `Lease` and sync, and `status` calls it not ready until then.
  - **An absent front:** a host whose record holds no front configuration (`up` was given no `--front-config`) reports `front_absent` in `--json` and prints `front: absent` (with the recorded dial-home mode and address when there is one). That is a state, not a fault: the host stays healthy. It is judged from the launcher's record, not from the front's `Lease`, so a front that is configured and has not yet written its first `Lease` is not called absent; a configured front that is not running is not absent either, and stays unhealthy.
- **`down` and `upgrade`:** `down` stops the supervisor, which stops its processes, and waits for it before it stops k3s, through verified pidfds. `--grace` defaults to 40 s; when the supervisor runs the front, a grace below `SupervisorGraceWithFront` (35 s: the front's 30 s and 5 s for the supervisor) is refused before anything is stopped, with exit 2; a process whose identity cannot be checked still makes it fail with the record kept. `upgrade` stops the supervisor with the old host and starts it again, after the objects have been compared, with the new one, running the same controller, front and frps. It resolves no frps itself: a host recorded with the controllers but without frps comes back without it, and `upgrade` warns (on standard error, and in `warnings` with `--json`). The new host's first record already names them, so an upgrade interrupted while the new k3s starts leaves a record whose `status` says the supervisor is missing (`up` records them the same way); if that fails, the record still names the controllers, so `status` says none runs.
- **Exit codes:** 0 success, 1 failure (for `status`: unhealthy), 2 usage error, 3 (`status` only) stopped, 4 (`up` only) the host is up and left running, but an agent build or frpc build that a PlatformProfile partition needs is missing or does not match its pin, or the check could not read the profiles (see Agent builds).
- **Front:** `up` records the front mode and address. `--front-mode host-dialed` takes no `--front-addr` and no `--front-key`, and `up` refuses either; it records the mode alone, and `status` prints `front: host-dialed (no address: the host dials the jobs)`. When none is given it still starts, and warns that no jobs will be submitted until a front is configured: the lifecycle controller refuses to submit while no front is set (a later issue).

### Testing the launcher

`go test ./...` runs the unit tests. The tests that start a real k3s need the pinned binaries, and the tests that start frps or frpc (HBEP-6's tunnel) need the frp binaries. Both skip, loudly, without them. To run everything:

```
hack/fetch-k3s.sh "$DIR" 1.35.9 1.36.5
hack/fetch-frp.sh "$FRP"
HPCBURST_BIN_DIR="$DIR" HPCBURST_FRP_DIR="$FRP" hack/test-launcher.sh
```

The script sets `HPCBURST_REQUIRE_INTEGRATION=1`, which turns every skip of a required test into a failure (in `-short` mode too), and it exits non-zero if any test was skipped, which includes a frp test run without `HPCBURST_FRP_DIR`. The supervisor is tested with a fake controller, `internal/launcher/testdata/fakecontroller` (built by the tests with `go build`; it imports controller-runtime's `pkg/healthz` and `go-logr`, both already required). It accepts exactly the controller's flags, records its command line and environment, serves `/healthz` and, as the controller, `/readyz` through controller-runtime's own handler mounted as its manager mounts it (so 200, 500 and the 404 for an unknown check are its), and is told by control files when to exit, ignore SIGTERM, answer 503 on `/healthz`, fail the readiness check `caches` or `leading` (`caches-failing`, `leading-failing`), register only the older single check `serving` (`readyz-before-split`, `serving-failing`), or bind extra TCP and UDP sockets. The tests judge processes from `/proc` and `ss`, not from the launcher's own records. The tests use loopback ports 29220–29246 (two blocks of 13 from the bases 29220 and 29233, and 29246, just past the second, which the outside-block control of `TestUpRefusesWhenAPortIsTaken` holds; the frps rig binds 29252–29259) and state directories under `$TMPDIR` (about 0.6 GB at peak, removed after each test). The tests run one at a time, except the two real-k3s event TTL tests (`internal/launcher/eventttl_k3s_test.go`): they are parallel, one on each block, and run together after the serial tests of the package. Set `HPCBURST_TEST_ROOT_K3S=1` on a machine that runs a system k3s: the tests then fail if it is missing, and assert after each test that it still listens on 6443, 6444 and 10250. Before starting k3s the tests wait for a quiet machine; `HPCBURST_TEST_MIN_AVAIL_GIB` (default 8) sets how much available memory that needs. The store-full test mounts a size-limited FUSE volume as the invoking user, so it needs `/dev/fuse` and `fusermount3`.
