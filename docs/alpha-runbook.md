# Alpha runbook

The live runs that alpha's graduation criteria still need, each one command, ready the hour the owner's dial-home route exists (issue #194; the criteria are tracked on #145). Every run is a row of `hack/live-checks.sh`: it prints its queue estimate and runs only with `--yes`, takes the one-job slot only after the builds, cancels its own jobs by tag on every exit, and prints the slot use to post.

```
hack/live-checks.sh --list                    # every row, and the two aliases below
hack/live-checks.sh --plan <base>..<head>     # which rows cover what a range changed; runs nothing
hack/live-checks.sh --run <row>...            # shape and queue estimate, then "not run: pass --yes" (exit 4)
hack/live-checks.sh --run <row>... --yes      # the run
```

`tunnel-hour`, `gpu-accounting` and `reach` are aliases: each stands for its `-helios` and `-athena` rows, run one after the other. A skipped row counts as a failure, and so does a test that cannot start for lack of a setting.

## What a run ends as

The script's exit code and the word on the screen, for every row:

| Exit | Word | When |
|---|---|---|
| 0 | `PASS` | the row's test passed and the cleanup left nothing behind |
| 1 | `FAIL` | the property the row tests was absent; or a job started and failed, or a read at the bound could not tell whether it had started; or its test failed, skipped for want of its gate, timed out or was interrupted; or a run (a `NOT RUN` included) left a job behind |
| 2 | | a usage error, an unreadable range, or a table of the script that loads no rows |
| 3 | `NOT RUN` | **a job never started within its bound, on every row** (below); or the run was refused before it began: a setting is missing, the one-job slot is in use, the scheduler rejected the row's shape |
| 4 | | a cluster row without `--yes`: its shape and estimate were printed and nothing ran |

**A job that never started within its bound is `NOT RUN`, exit 3, on every row**, whichever bound ran out and whether the row has a one-job slot or not (the science agent's ruling of 8 Nov 2026, #272, which replaces #230's `FAIL` for a row with no slot). A `FAIL` means the property the row tests was absent, and a queue wait tests nothing: the run could not be done now, try again later. The bounds are the wait in the queue (`LIVE_PENDING_MAX_SECONDS`), a row's start wait, a tunnel row's `endTime` cap, a minute before its deployment's first end, and a two-job row's bound for its second job. In each case the test cancels what it submitted by its tags, checks that none is left, writes `not-run.txt` and skips; the script prints the line below, which says which bound ran out, runs the same cleanup, and exits 3. A cleanup that leaves a job behind makes the run a `FAIL` (exit 1), `NOT RUN` or not. Nothing is posted but the slot use.

**`NOT RUN` means the job affirmatively never started.** A read made at the bound must show it waiting. A job that started, one the read does not list, one never accepted, and a read that fails are each a `FAIL` that names what it found: missing evidence is neither "never started" nor a pass. `real-engine`'s own poll keeps to this: only a read that says `PENDING` ends its wait, and three unreadable reads in a row are a `FAIL`. Nor is that read the last word: a job can start between it and the cancel, so the rows with a test read the job's history once it is cancelled, and a job that had started by then, or a history that cannot be read, is a `FAIL` that says so. `real-engine` makes the same read (#297): once the cleanup has cancelled its job and found it gone from the queue, the script asks `sacct --json` for it. Only the form of the real GH200 reply for a job cancelled before it started is `NOT RUN`: a bare `4294967294` start (Slurm's NO_VAL) and the state `CANCELLED` ([#267](https://github.com/groundnuty/plgrid-llmlab-hpc-burst/issues/267)). A start time is a `FAIL` that names it. A read that fails, a reply with no record of the job, a form nobody has seen (a triple, a 64-bit marker, a start that is not before the end) and a job the cleanup left in the queue are each a `FAIL` that says what could not be read. Accounting can lag the queue, so the read is asked up to five times, `LIVE_SACCT_GAP` seconds (default 2) apart. That is the only wait this adds, after the wait in the queue and outside the run's own clock.

**A two-job row whose first job ran and whose second never started is `NOT RUN` too, unless the first job's part failed.** The handover's successor must start by the first's drain start; a no-overlap successor must start within the wait in the queue of the first's lease end. The run then judges what did happen (the deployment, the streams across the drain start, the worker-rung restart, the handover's attribution, and the cluster's record of the jobs): a failure there wins, and the row is a `FAIL` with its record and its text to post. The handover itself, and the gap, were never put to the test; the first job's streams open whether or not the replacement is ready. A second job the controller never made is a `FAIL`: that is a property of the row, not a queue wait. So is a watch that was reset, or a catch-up that cannot tell whether the watch has caught up with the API (#292): the first job's part is judged from the watch, so what cannot be read there is no `NOT RUN`. A first job that never started judges nothing from the watch, and ends on the scheduler's read, so a reset then is only logged. Beside the `NOT RUN` the script prints one more line, `ReplacementLate for its deployment: raised`, `not raised` or `unknown` (information, not a check): whether the controller raised that event for the run's deployment. It decides nothing, and a `FAIL` of this kind has it in its text to post. In no-overlap mode the gap is planned and the controller does not raise it, so `not raised` is what that row expects.

| Row | Its bound | The line when its job never starts |
|---|---|---|
| `conformance-helios` | start wait, 30 min | `a job did not start within 30 min of its acceptance and was cancelled by its tag` |
| `conformance-helios-gh200`, `conformance-athena`, `gpu-accounting-helios`, `reach-helios`, `reach-athena` | start wait, 10 min | `a job did not start within 10 min of its acceptance and was cancelled by its tag` |
| `real-engine`, `alpha-helios-nooverlap`, `tunnel-hour-helios` | wait in the queue, 30 min (their slot's) | `a job was still pending after 30 min in the queue and was cancelled by its tag` |
| `alpha-athena-handover`, `tunnel-hour-athena`, `gpu-accounting-athena` | wait in the queue, 2 h (no slot) | `a job was still pending after 120 min in the queue and was cancelled by its tag` |
| `tunnel-hour-helios`, `tunnel-hour-athena` | and the `endTime` cap, whichever comes first | `a job was still pending a minute before its deployment's first end and was cancelled by its tag` |
| `alpha-athena-handover` | and its second job, by the first's drain start | `the first job ran and the second never started by the first's drain start, and was cancelled by its tag` |
| `alpha-helios-nooverlap` | and its second job, the wait in the queue from the first's lease end | `the first job ran and the second never started within 30 min of the first's lease end, and was cancelled by its tag` |

An explicit `LIVE_PENDING_MAX_SECONDS` sets the wait in the queue of the rows that have one, shorter or longer (`1 min 30 s` for 90). Every line above is followed by `not a failure`. `hack/livechecks` reads the script's cluster table and fails, naming the row, for a row that has no case in its table of these lines (`TestEveryRowMapsAJobThatNeverStartedToNotRun`), so a row added later cannot end a never-started job in `FAIL`.

## Settings

The settings file is named by `HPCBURST_LIVE_SETTINGS`: `KEY=VALUE` lines, mode 600, owned by you (`hack/live-checks.sh`, header). Values never appear here, on the screen or in a post. Each missing setting is reported in one refusal (exit 3).

| Setting | Needed by | What it is |
|---|---|---|
| `LIVE_OUT_DIR` | every row | a private directory for logs and records |
| `LIVE_LOCK_DIR` | every row | the directory with the hosts' lock files |
| `LIVE_BUILD_LOCK` | optional | the shared build lock; builds take it, test runs never do |
| `ACCOUNT_ATHENA_A100` | Athena rows | the grant account for `plgrid-gpu-a100` |
| `ACCOUNT_HELIOS_GH200` | Helios rows | the grant account for `plgrid-gpu-gh200` |
| `LIVE_CONF_CREDENTIALS_ATHENA`, `LIVE_CONF_CREDENTIALS_HELIOS` | rows on that host | the Provider's ssh credentials file, mode 600 |
| `LIVE_DIALHOME_MODE` | the four stack rows | `direct` or `ssh` (HBEP-6, Dial-home modes) |
| `LIVE_DIALHOME_ADDR` | the four stack rows | `host:port` of the route, as the compute nodes see it |
| `LIVE_DIALHOME_KEY` | stack rows, `ssh` mode | the restricted dial-home key file, mode 600 |
| `LIVE_DIALHOME_LISTEN` | stack rows, `direct` mode | `host:port` of the front's dial-home listener on this host, where the owner's route arrives (the front's `dialHomeListen`, which has no default in direct mode) |
| `LIVE_BIN_DIR` | the four stack rows | the directory with `k3s-1.36.5/` and the pinned frp (`hack/fetch-k3s.sh`, `hack/fetch-frp.sh`) |
| `LIVE_TUNNEL_LEASE_MINUTES` | optional, `tunnel-hour-*` | the tunnel rows' lease in minutes, 106 to 240; default 137 (below). The owner's choice when giving the go: the shape, the hold note, the timeout and the test follow it |
| `LIVE_PROBE_HOST`, `LIVE_PROBE_PORT` | `reach-*` | the gateway's forwarded port as the compute nodes see it: a host name or address (letters, digits, dots, hyphens, underscores) and a port from 1 to 65535. **Private**: they go into the job's script on the cluster and nowhere else, never on the screen, in the test's log, in a record or in a post |
| `LIVE_PROBE_LABEL` | `reach-*` | the only name of that port in public output (`posts.md`): 1 to 40 letters, digits, dots, underscores or hyphens. It must not hold the host or the port, in any case, with or without the root dot, and with the dots, hyphens and underscores run together or changed (`GATEWAY.PRIVATE.EXAMPLE` holds `gateway.private.example`) |
| `LIVE_OWNER_GO_HELIOS_NOW` | `alpha-helios-nooverlap`, `tunnel-hour-helios` | today's UTC date (`YYYY-MM-DD`), set only after the owner has said yes to the hold; a missing or older date is refused (exit 3) |
| `LIVE_FRONT_HOST_LABEL` | every row that writes a text to post: the handover and no-overlap rows, `tunnel-hour-*`, `gpu-accounting-*` | where the front ran, in three parts: a **role** from a fixed list (`the development host`, `a Cyfronet-network host`, `a cloud host`; a code change adds one, the setting never does), a comma and a space, a **position** that is exactly `inside` or `outside` followed by `Cyfronet` or `Cyfronet's network` (required), and an optional **note** in parentheses. For example "the development host, outside Cyfronet (3.4 ms to the Helios login, behind a gateway)" or "a Cyfronet-network host, inside Cyfronet's network". The note holds words of letters and numbers with a unit (`3.4 ms`, `40 MB/s`, `5%`) and `, ; ' -`; a word with a digit in it (`gw-01`, `node7`), a dotted name or address (`gw.example`, `10.0.0.1`) and a colon are refused, so a host's name cannot pass for a note. At most 120 bytes in all, and case counts (`inside`, not `INSIDE`). It is the first thing after the verdict in `posts.md` (`- front ran on: <label>`), because the host that runs the front decides the path to the login nodes and so the timings. A row without a valid one is refused (exit 3) naming the setting and the part that is wrong, never its value, before anything is built, estimated or submitted. The reach, conformance and real-engine rows take none: they do not measure through the front. Heartbeats and timeouts are not retuned on this basis |

One environment variable, not a setting: `LIVE_PENDING_MAX_SECONDS` is how long a job may wait in the queue before the run cancels it. The default is 7200 (2 hours), except on a row in a one-job slot that has no start wait: `alpha-helios-nooverlap` and `tunnel-hour-helios`, the rows that hold QOS `now`'s GPU for hours, and `real-engine`: there it is 1800 (30 minutes), because a job of ours that pends for two hours stands in the owner's one-job slot (#222, and the science agent's rule of 2 Nov 2026: every row in a one-job slot, on either cluster, has a start wait of 10 minutes or less or a wait in the queue of 30 minutes or less, which `hack/livechecks` reads off the cluster table). An explicit value overrides either default, shorter or longer, and the script states it exactly (`59 s`, `1 min 30 s`, `10 min`). What a job still pending past it ends as is in "What a run ends as", above; `real-engine`'s job the script itself polls and cancels by its tag (#222). Athena's `plgrid-gpu-a100` queue was estimated at a start on 13 Nov for one GPU (#145, 1 Nov 2026): set it from the estimate that `--run` prints, which is the reason it is printed first. The script's timeout for a row is the row's run time plus this wait, once for each of its jobs, except a row with a start wait, whose bound is its first clock and is already in its timeout. Tests derive each row's least timeout from its bounds in the table and the waits in the code, those waits with a quarter more for what a scan can miss, and fail when a timeout can fire first.

## The one-job slot, the jobs a run holds, and the owner's go

Helios QOS `now` and Athena `plgrid-now` allow one job per user, and the owner shares them (#145, 1 Nov 2026): use them sparingly, batch checks, leave nothing held, and post each use. Before a row takes a slot the script reads it, refuses (exit 3) if it already holds a job, reads it again after the builds, and prints `slot use (<slot>): start <UTC> end <UTC> duration <hh:mm:ss>` when the run ends. That line goes in the post.

"One cluster job at a time" holds as one live run per host, plus the slot refusal before the start, plus the cleanup of every tag. It cannot mean one job, because two rows are about a successor beside a predecessor. The most jobs each row holds at once:

| Row | Most jobs at once | Where |
|---|---|---|
| `alpha-athena-handover` | 2: the predecessor and its replacement, together for the handover | `plgrid-gpu-a100`. **Not a one-job slot:** that partition has none, so the pair takes no one's slot. |
| `alpha-helios-nooverlap` | 2: the running predecessor and the pending replacement | QOS `now` on `plgrid-gpu-gh200`, the owner's shared slot |
| `tunnel-hour-helios` | 1 | QOS `now`, the shared slot |
| `tunnel-hour-athena` | 1 | `plgrid-gpu-a100`, no slot |
| `gpu-accounting-helios` | 1, for about 15 minutes at most (the 10-minute start wait and the job's few minutes) | QOS `now`, the shared slot |
| `gpu-accounting-athena` | 1 | `plgrid-gpu-a100`, no slot |
| `reach-helios` | 1, for about 13 minutes at most (the 10-minute start wait and a job of seconds, with a 2-minute limit) | QOS `now`, the shared slot |
| `reach-athena` | 1, for about 13 minutes at most | `plgrid-now`, the one-job partition, the shared slot |

On Helios the replacement of `alpha-helios-nooverlap` is created at its planned time and pends until the predecessor's job ends and frees the GPU (the partition's QOS allows 2,000 submitted jobs, QOS `now` one GPU: `hbep/0007-lifecycle-controller/README.md:463`, `:608`). So the pending replacement sits in the owner's shared slot only for the planned gap, from its planned submission to the predecessor's end, and the run never queues a third job. Under `ReleaseWhenIdle` with a 2-minute `idleLimit` the predecessor's job is released that long after its Instance ends, so it does not hold the GPU to its hard end (`:471`; the default `Keep` would).

**The owner's go.** `alpha-helios-nooverlap` and `tunnel-hour-helios` hold QOS `now`'s one GPU for hours. Each prints, before its estimate, "may pend up to 30 min in the queue (then it is cancelled by its tag and the run is NOT RUN), then holds QOS now's GPU for about 2 h 40 min; the owner's go is needed (the development rule on #145)" (2 h 20 min for the hour's row at the default lease; the note follows `LIVE_TUNNEL_LEASE_MINUTES`, and its 30 minutes follow `LIVE_PENDING_MAX_SECONDS`) and refuses unless `LIVE_OWNER_GO_HELIOS_NOW` holds today's UTC date. Set it only when the owner has said yes for this run; tomorrow's run needs a new go. The script reads the date again just before each protected row, and again after that row's builds, and refuses (exit 3) a row whose go has gone stale, also when an earlier row of the same command ran past UTC midnight. The owner's go covers both: the possible pend, which comes first, and the hold, which starts when the job does. The hold is the lease plus, for no-overlap, 45 minutes for the successor to start and become ready, rounded up to ten minutes. It is a few hours at most, not the 12 h `maxWall` of QOS `now`.

**The Helios Provider serves one deployment, and that deployment allows it alone.** QOS `now`'s one GPU per user makes a second deployment's primary on the Helios Provider pend behind the first, an unmarked pend that, while fewer than 20 waits are kept, could set the plan for a normal-mode deployment there (`hbep/0007-lifecycle-controller/README.md:468`, "Alpha's fence", from PR #205). So `alpha-helios-nooverlap`'s ModelDeployment names the Helios Provider and no other. The verdict fails a deployment that allows any other Provider, or none, and the dry run shows it with a deployment that also allows Athena. The other stack rows are held to their own cluster the same way, because a run that could place its Instance elsewhere measures nothing.

**The run keeps to those counts with the deployment's `endTime`** (issue #245; the science agent's rulings on PR #255). These rows bound their deployment's life on purpose, so that each stays within the job count above: a row that let the controller go on would plan replacements for ever. The continuous replacement chain is the one-host rehearsal's to show (`hack/rehearsal.sh`, part 3), not these rows'. With no queue wait observed, the lifecycle controller creates a primary's replacement at the primary's start; with a long one it creates a successor's own replacement in the very pass that first sees the successor run (HBEP-7, Handover). A deployment that ends at or before an Instance's drain start gives it no replacement (`internal/lifecycle/handover.go`). Every end is placed on the cluster's own clock, read on the login node (`date -u +%s`) through the run's own ssh, because the controller compares the end with the jobs' times, which the scheduler gives on that clock.
- **A tunnel row** creates its deployment ending at the earliest drain start its job can have: the cluster's clock read just before the creation, plus the job's time limit (the lease), less the 15-minute drain window. Once the job runs and its lease end is known, the end moves to a minute before the Instance's own drain start. Neither end is after a drain start, so no replacement is ever planned. The Instance drains a minute early, and the run records that as the drain start.
- **A two-job row** (`alpha-athena-handover`, `alpha-helios-nooverlap`) creates its deployment with the same kind of end, and a guard in the test moves it on with every look at the cluster, every 10 seconds: the cluster's clock, then the queue listing of the run's jobs. While no job of the run has started, and while only the predecessor has, the end is the latest look's clock plus 1 h 31 min (the 1 h 46 min lease less the drain window), which is no later than the drain start of any job that starts after that look. So the predecessor's start meets an end at or before its own drain start, which plans no successor yet; the first look after it raises the end past the predecessor's drain start, and only then can the successor be created. Once the successor runs, the end is its own drain start, to the second, for good. A third job that starts, a failed write of the end, three failed looks in a row, or a successor's drain start not after the predecessor's, stops the run at once (FAIL), and the run must end with the successor's drain start seen as the deployment's end. `internal/lifecycle` shows the guard against the controller with a first wait of 61 and of 90 minutes, on Helios's one-GPU QOS and on Athena's queue with a successor that starts after the drain start: no third Allocation is created, where an end set only at the successor's start lets one through.
- **The wait in the queue each row allows** (its first clock), and what a job still pending at its end makes of the run:

  | Row | The wait | At `LIVE_TUNNEL_LEASE_MINUTES=240` |
  |---|---|---|
  | `tunnel-hour-athena` | 2 h (`LIVE_PENDING_MAX_SECONDS`), but never past a minute before the first end: 2 h 1 min (2 h 17 min less the 15 min drain window, less a minute) | the cap is 3 h 44 min (4 h less 15 min, less a minute) |
  | `tunnel-hour-helios` | 30 min (its slot's), never past 2 h 1 min | 30 min; the cap 3 h 44 min |
  | `alpha-athena-handover` | 2 h (`LIVE_PENDING_MAX_SECONDS`); no cap from its end, which moves on while it waits | the row's lease is 1 h 46 min, not the setting |
  | `alpha-helios-nooverlap` | 30 min (its slot's); no cap from its end | as at the default |

  What a job still pending at the wait or at the cap ends as is in "What a run ends as", above. At the default a tunnel row's own wait comes first on Athena (2 h before 2 h 1 min), so the line says the wait in the queue; a wait asked past 2 h 1 min reaches the cap first, and the line says that bound instead. The script's cleanup, and the test's own, find the run's jobs by the run's tag prefix (below) and check that none is left.
- **The Athena rows run when #145's daily estimate is under their cap:** `tunnel-hour-athena` under 2 h 1 min at the default lease, or under 3 h 44 min at `LIVE_TUNNEL_LEASE_MINUTES=240` with `LIVE_PENDING_MAX_SECONDS` set to the estimate; `alpha-athena-handover` under its `LIVE_PENDING_MAX_SECONDS`, and in practice well under the 1 h 31 min from the predecessor's start to its drain start, since the successor waits in the same queue and must be ready before that drain start for the handover to happen.

Cleanup is by the run's own jobs, and by them alone. The script draws a run ID (10 random hex digits) for each stack row and passes it to the test, which names the row's Provider and deployment `alpha-<ID>`; the controller names every Allocation after its Provider, so every job of the run is named `hb-alpha-<ID>-...`. The test also writes each Allocation's tag to `job-tags.txt` when its watch first sees it. On every exit, a signal included, the test's Close and then the script cancel every job of the run's prefix or of a tag written down, and only those, until the queue shows none of them alive: a job is alive while the scheduler holds, queues or runs it, and while it is COMPLETING after its end. A tag the watch delivered late, or that could not be written, leaves no job behind.

## The shortest lease

Every stack row's deployment sets a short `leaseLimit` and a short `routing.maxRequestDuration`, so that a handover or a gap fits in hours, not in the 48 h of the partitions. The lease cannot be shorter than the lead an Instance needs, or the Provider is skipped with `PartitionTooShort` and no Allocation is made. The lead is the drain window plus `handoverMargin` plus `health.startTimeout` (`internal/lifecycle/timelimit.go:22`), and an Allocation hosts an Instance only when its time limit is longer than the lead, in whole minutes (`timelimit.go:42`). The drain window is `routing.maxRequestDuration` plus the profile's `drainMargin` when that is shorter than its `drainWindow` (`api/v1alpha1/writers.go:87`).

With a `routing.maxRequestDuration` of 5 minutes and the shipped profiles' values (`drainMargin` 10 minutes, `handoverMargin` 30 minutes, `health.startTimeout` 1 hour) the lead is 1 h 45 min, the figure `profiles/athena.yaml:39` gives, and the shortest lease **1 h 46 min**, which the two handover rows use. Each stream they hold across a drain start must finish within the 5 minutes.

**The tunnel hour is one healthy session, not one stream.** The front cuts a request at the deployment's deadline (HBEP-5), and a deployment can only shorten the front's, so no stream can last an hour behind a 5-minute deadline. The science agent's ruling of 2 Nov 2026 reads `hbep/0006-instance-reachability/README.md:354` and `:375` as an hour of one tunnel staying healthy under real use, so the 5-minute deadline stays and the hour is what the tunnel carries across many requests.

**The tunnel rows' lease is chosen by measurement.** The hour of traffic (61 minutes) must end before the drain start, 15 minutes before the lease ends, so the Instance must be ready within `lease - 76 minutes` of its job's start (`LatestReady`): 30 minutes under the shortest lease, 1 h 46 min, and 61 minutes under 2 h 17 min (a start of up to `health.startTimeout`, the hour, the drain window and a minute). The rule: take GH200's measured start-to-ready with the cold SIF build included; under 20 minutes, keep 1 h 46 min, else 2 h 17 min. The measurement is the second real-engine run on Helios GH200 ([issue #94, comment 6557821833](https://github.com/groundnuty/plgrid-llmlab-hpc-burst/issues/94#issuecomment-6557821833)): a cold build with an empty image cache and a slow Hub; the job started at 11:42:26Z and its first Instance had qualified and warmed up at 12:06:05Z, **23 min 39 s** later. That is over 20 minutes, so the default is **2 h 17 min**, and the Helios row holds the slot for about 2 h 20 min. A failed hour costs that hold and a rerun, which is worse than the margin. The owner may choose the other value, or any from 106 to 240 minutes, with `LIVE_TUNNEL_LEASE_MINUTES` when giving the go; the hold note, the shape and the test follow it, and a start slower than the lease allows fails the row with "the hour ended after the Instance's drain start".

## The runs

Durations are plans, from the lease each row sets (`internal/alpha/rows.go`); the first run replaces them with a measurement. The queue wait comes on top of every one.

### `gpu-accounting-athena`, `gpu-accounting-helios`

```
hack/live-checks.sh --run gpu-accounting --yes
```

- **Settings:** the account, the credentials file, `LIVE_OUT_DIR`, `LIVE_LOCK_DIR`, `LIVE_FRONT_HOST_LABEL`. No dial-home route.
- **Duration and slot:** one GPU job of 5 minutes' limit per cluster, holding its GPU for about 20 seconds; the run is about 10 minutes once the job starts. Helios uses QOS `now`: at most 15 minutes of the slot (below); Athena's `plgrid-gpu-a100` has no slot.
- **Two guards on Helios** (the science agent's rule of 2 Nov 2026, the same two as `conformance-helios-gh200`, which run the shared functions of `hack/live-checks.sh`):
  1. **The slot precondition.** The row starts only when `squeue --me` shows no job in QOS `now`, running or pending, the owner's or ours; otherwise it exits 3 with "skipped: the now slot is in use" before anything is built, estimated, submitted or cancelled (`check_slot`).
  2. **The start-wait bound.** The job must start within 10 minutes of its acceptance (`HPCBURST_CONF_START_WAIT`, the 14th column of the row's shape).     **On a live row, in alpha** (the science agent's ruling (4) on PR #255: no product change, so no sender-side timing on the live path; front-side timing is post-alpha, #273), criteria 4 and 5 read:
    - The upload's interval and rate are **not measured in alpha**, and the text to post says so ("not measured in alpha (no sender-side timing on the live path)"). The download is measured as in 4. A dry run keeps the full check: there a missing upload rate or interval fails.
    - **Each large body shows it arrived whole.** The large requests are chat prompts of words ("hello") that ask for one token (`max_tokens` 1), under the deployment's context, so the engine serves each whole, a prefill of the whole prompt, and its response's `usage.prompt_tokens` counts every token of the prompt it read. Only a completed response is read: every choice finished, and the usage complete and adding up. A refusal is no count: vLLM v0.32.0 serves a prompt under the context however many tokens it asks for (it clamps `max_tokens`), and over the context it says "at least N input tokens" (the parent's reading of its source, after the delta round of PR #255). Before the hour, three such prompts of 1,000, 2,000 and 4,000 words give the engine's count as a line in the words (tokens a word, and the chat template's): the first two fix it, and the third must lie on it exactly. The large prompt holds as many words as 0.4 MB takes, but fewer tokens than the context, leaving room for its one token: at the live 32,768 tokens and a token a word, 32,763 words, 0.2 MB. A fourth prompt, of half its words (16,382 there), must lie on the line too. A count that is not whole tokens a word, or that bends anywhere up to half the large prompt (a token merged or split every so many words), fails the row, as does a context that cannot hold 0.1 MB under it. **What the count shows:** frp is a byte tunnel, so a body cut short on the way is no longer JSON, and the engine answers it with an error; the row fails on any large body not answered with a completed response with its usage. Equal counts are the second check: the body arrived whole when its usage counts exactly its own count, from the line, so the engine tokenized the whole well-formed body. A path that rewrites content (a proxy that edits well-formed JSON) is out of scope for this check, because frp carries bytes and does not parse payloads. Two senders send it for the 30 s of the download's measurement, each half a second after its last reply, once all 16 streams run, and one must have been in flight, from its first byte sent to its response read on the client's clock, while 16 streams at 20 tokens/s were open. The large requests do not count toward the run back to back: they follow one another a fraction of a second apart.
    - **Head-of-line** (reported, not judged): the longest gap between two tokens of any stream while a large body was in flight, by the client's windows, against the longest elsewhere in the hour. Each large body's window is split where the client wrote the body's last byte to its connection: its **send window** (first byte to last byte, the body on its way) and its **prefill window** (last byte to the response, the engine prefilling the body's whole prompt, about 16,000 to 32,000 tokens live, before its one token). Each gap is classed: a send if it overlaps any body's send window (the two senders interleave, so a gap often overlaps another body's prefill as well), a prefill if it overlaps only prefill windows, and neither otherwise; the text to post gives the longest in flight, the longest of each of the first two, and the longest elsewhere. A gap over 1 s is FLAGGED as a stall, and each FLAG names its class ("in a send window", "in a prefill window", "in neither window"), so that a reader can tell a tunnel stall from engine work: at the 20 tokens a second the streams must hold a token is due every 50 ms, an engine's scheduling hiccup is tens of milliseconds, a second in a send window points at the tunnel holding the token direction behind a body, and a second in a prefill window at the engine's prefill, which can lengthen the gaps by itself.

## Before the first real run

1. `hack/live-checks.sh --list` and `--plan origin/main..HEAD` name the rows; `--run <row>` (no `--yes`) prints the shape and the estimate, or the settings it lacks.
2. Run `gpu-accounting` first: short, no route needed, and fully wired. `reach` is as short and needs the owner's word that the forwarded port is up.
3. Set `LIVE_PENDING_MAX_SECONDS` from the estimate before a queued run.
4. Post each result where the row says, with its slot use. The text of `posts.md` is private until you copy it; it holds counts, durations and fixed labels, never a host, account or job ID.
5. Every row that runs the stack posts `watch resets over the run`, a measured count. A reset fails the test as "not known", on any kind, and the failure says whether any read's window crossed it. If a live row ever fails on a reset that no read crossed, the rule is refined before that row is re-run.

## What the dry runs show, and what they cannot

The package tests and `hack/livechecks` run every row's own compiled test, through the script, over a fake Slurm in run mode with stand-in steps. The healthy run passes; each of 105 faults (a cut stream, no stream in flight, a second restart, a successor that starts beside its predecessor, a lane an hour short, a deployment that also allows Athena, the default lease, a lease at the lead, no `ReleaseWhenIdle`, a node with two GPUs against a record of one, no request body of 0.1 MB, large requests sent far from the streams, a missing upload or download rate, and so on) fails its row with exit 1, while a node whose `nvidia-smi` lists eight GPUs to a job given one still passes, and `hack/mutate-alpha.sh` changes each criterion's condition and requires a test to fail. The dry fault `pend-past-bound` shows the pending bound: the owner's job holds the fake QOS's one GPU until a release file appears (no fixed window), the run's job pends past the first clock and is cancelled by its tag, and every stack row ends `NOT RUN` with exit 3 (the owner's job untouched on the two Helios rows), the Athena rows included, as does `gpu-accounting-athena` in its own dry fault `queue-held`. The dry fault `second-never-started` runs a first job to its end beside a second held in the queue, and both two-job rows end `NOT RUN`; with a failure of the first job's part added (`second-never-started-cut`, `second-never-started-late-cut`, `second-never-started-no-restart`), or a catch-up that cannot tell (`second-never-started-not-known`), they fail instead. The `-late` and `-unknown` variants show that what the run read of `ReplacementLate` changes neither end. The dry run keeps the bound the script gave it, and the stand-in logs the manual clock one second before the bound (the job still pending) and one second after it (cancelled), which the tests check against bounds written out in them. A dry binary refuses live settings, and the script never passes the dry switch on.

They cannot show that the real controllers, front and tunnel behave: the stand-in steps report what the real scenario will report, and the criteria judge it.
