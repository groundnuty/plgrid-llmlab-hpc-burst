# Alpha runbook

The live runs that alpha's graduation criteria still need, each one command (issue #194; the criteria are tracked on #145). Alpha graduates on Athena alone (the owner's decision of 11 Nov 2026, recorded on #145 and approved on PR #373): the Helios rows are beta's, kept runnable by their own names and in no alias ([Alpha rows and beta rows](#alpha-rows-and-beta-rows)). Alpha's host runs the stack rows in `host-dialed` mode, which needs no dial-home route from the compute nodes ([Host-dialed mode](#host-dialed-mode)); `direct` and `ssh` modes need the owner's route. Every run is a row of `hack/live-checks.sh`: it prints its queue estimate and runs only with `--yes`, takes the one-job slot only after the builds, cancels its own jobs by tag on every exit, and prints the slot use to post.

```
hack/live-checks.sh --list                    # every row, and the four aliases below
hack/live-checks.sh --plan <base>..<head>     # which rows cover what a range changed; runs nothing
hack/live-checks.sh --run <row>...            # shape and queue estimate, then "not run: pass --yes" (exit 4)
hack/live-checks.sh --run <row>... --yes      # the run
```

`tunnel-hour`, `gpu-accounting`, `reach` and `reach-host-dialed` are aliases: each stands for its Athena row, the row alpha runs (`gpu-accounting` for `gpu-accounting-athena-now`, the same test on `plgrid-now`, since the A100 queue is days out; issue #145). The Helios row is beta's and runs by its own name, so a Helios row that is skipped or lacks its settings cannot fail alpha's run (issue #386). A skipped row counts as a failure, and so does a test that cannot start for lack of a setting.

## What a run ends as

The script's exit code and the word on the screen, for every row:

| Exit | Word | When |
|---|---|---|
| 0 | `PASS` | the row's test passed and the cleanup left nothing behind |
| 1 | `FAIL` | the property the row tests was absent; or a job started and failed, or a read at the bound could not tell whether it had started; or its test failed, skipped for want of its gate, timed out or was interrupted; or a run (a `NOT RUN` included) left a job behind |
| 2 | | a usage error, an unreadable range, or a table of the script that loads no rows |
| 3 | `NOT RUN`, `INVALID` | **a job never started within its bound, on every row** (below); or the run was refused before it began: a setting is missing, the one-job slot is in use, the scheduler rejected the row's shape; or, `INVALID` on `beta-athena-now-bulk` alone, its run had no saturation witness (below) |
| 4 | | a cluster row without `--yes`: its shape and estimate were printed and nothing ran |

**A job that never started within its bound is `NOT RUN`, exit 3, on every row**, whichever bound ran out and whether the row has a one-job slot or not (the science agent's ruling of 8 Nov 2026, #272, which replaces #230's `FAIL` for a row with no slot). A `FAIL` means the property the row tests was absent, and a queue wait tests nothing: the run could not be done now, try again later. The bounds are the wait in the queue (`LIVE_PENDING_MAX_SECONDS`), a row's start wait, a tunnel row's `endTime` cap, a minute before its deployment's first end, and a two-job row's bound for its second job. In each case the test cancels what it submitted by its tags, checks that none is left, writes `not-run.txt` and skips; the script prints the line below, which says which bound ran out, runs the same cleanup, and exits 3. A cleanup that leaves a job behind makes the run a `FAIL` (exit 1), `NOT RUN` or not. Nothing is posted but the slot use.

**`NOT RUN` means the job affirmatively never started.** A read made at the bound must show it waiting. A job that started, one the read does not list, one never accepted, and a read that fails are each a `FAIL` that names what it found: missing evidence is neither "never started" nor a pass. `real-engine`'s own poll keeps to this: only a read that says `PENDING` ends its wait, and three unreadable reads in a row are a `FAIL`. Nor is that read the last word: a job can start between it and the cancel, so the rows with a test read the job's history once it is cancelled, and a job that had started by then, or a history that cannot be read, is a `FAIL` that says so. `real-engine` makes the same read (#297): once the cleanup has cancelled its job and found it gone from the queue, the script asks `sacct --json` for it. Only the form of the real GH200 reply for a job cancelled before it started is `NOT RUN`: a bare `4294967294` start (Slurm's NO_VAL), the state `CANCELLED` ([#267](https://github.com/groundnuty/plgrid-llmlab-hpc-burst/issues/267)), exactly one record, for that job, that is neither an array nor a heterogeneous job and lists no steps, and a restart count that is present and 0 (a job that ran, was requeued and shows only its cancelled last execution has the same start and state). The reply is decoded as JSON by `python3`, which the host that runs `real-engine` needs; the run fails before it submits anything if it is missing. A start time is a `FAIL` that names it. A read that fails, a reply that is not one JSON document, a reply with no record of the job or with another record beside it, an array or heterogeneous record, a restart count that is missing or not 0, a form nobody has seen (a triple, a 64-bit marker, a start that is not before the end), a job the cleanup left in the queue and a queue the cleanup could not read are each a `FAIL` that says what could not be read or seen. Accounting can lag the queue, so the read is asked up to five times, `LIVE_SACCT_GAP` seconds (default 2) apart (about 8 s of sleeps); a lag past that is a `FAIL` that names the state it saw, not a `NOT RUN`. That is the only wait this adds, after the wait in the queue and outside the run's own clock.

**A two-job row whose first job ran and whose second never started is `NOT RUN` too, unless the first job's part failed.** The handover's successor must start by the first's drain start; a no-overlap successor must start within the wait in the queue of the first's lease end. The run then judges what did happen (the deployment, the streams across the drain start, the worker-rung restart, the handover's attribution, and the cluster's record of the jobs): a failure there wins, and the row is a `FAIL` with its record and its text to post. The handover itself, and the gap, were never put to the test; the first job's streams open whether or not the replacement is ready. A second job the controller never made is a `FAIL`: that is a property of the row, not a queue wait. So is a watch that was reset, or a catch-up that cannot tell whether the watch has caught up with the API (#292): the first job's part is judged from the watch, so what cannot be read there is no `NOT RUN`. A first job that never started judges nothing from the watch, and ends on the scheduler's read, so a reset then is only logged. Beside the `NOT RUN` the script prints one more line, `ReplacementLate for its deployment: raised`, `not raised` or `unknown` (information, not a check): whether the controller raised that event for the run's deployment. It decides nothing, and a `FAIL` of this kind has it in its text to post. In no-overlap mode the gap is planned and the controller does not raise it, so `not raised` is what that row expects.

**A row whose streams cannot be sized to tell a cut from an end is `NOT RUN` too** (#447; the science agent's ruling (a), 12 Nov 2026). `alpha-athena-handover`, `alpha-helios-nooverlap` and `alpha-athena-now-nooverlap` open a stream one lead before the drain start and hold it two leads, sized at the engine's rate measured on a first stream. The lead is a third of `routing.maxRequestDuration`, or less when the deployment's `max-model-len` cannot hold a stream of two leads at that rate: `min(maxRequestDuration / 3, (max-model-len - 512) / rate / 2)`, rounded down to a whole second (`FitLead`, `internal/alpha/handoverlead.go`). At 199 tokens a second on a context of 32768 that is 81 s, where a third of 5 minutes, 100 s, made a stream of 39,761 tokens that does not fit (row B's first live run, 12 Nov 2026). A lead under 30 s, whichever of the two terms sets it (what the context fits, or a deadline whose third is short: the 30 s floor applies to the final lead; the science agent's ruling (a) on #451, 12 Nov 2026), ends the row `NOT RUN`, exit 3, before any stream opens (before the worker restart, on the rows that have one): a stream that only just straddles the drain start cannot tell a cut from an end, so the row is never run weaker. The marker and the script's line name the rate and the context. The stream's checks stay as they were: in flight at the drain start, ended after it, none cut, from its own timestamps. The tunnel hour's requests are not sized by a lead and are unchanged.

**The router row on a node whose glibc is too old is `NOT RUN` too** (#521). `beta-athena-now-router` reads the compute node's glibc, on the node and from the agent's own log of a refused router start, and a version under the 2.30 Envoy needs ends the run `NOT RUN`, exit 3, naming the version and nothing else of the node, with no text to post, since the run sent no request; 2.30 itself is fine.

**The keeper row whose stream cannot span a controller restart is `NOT RUN` too** (#521). `beta-athena-now-keeper` sizes its stream to the deployment's `max-model-len` at the engine's measured rate, and one shorter than the window of 100 s (10 s to the kill, 60 s for the keeper's outcome, 30 s of margin; the science agent's ruling (b) on #543) ends the run `NOT RUN`, exit 3, naming the rate and the context and nothing else of the run, with no text to post: no controller was killed. **A stream that does not outlast the keeper's outcome by the 30 s margin is `NOT RUN` too,** never a pass: an outcome inside the verdict's 2 minutes but past the window, so the run cannot show a stream crossing the handover. The controller was killed, so this one posts, saying `NOT RUN` with the times from when the stream was opened (its request's start, before its first token); a failure of any other check wins.

**The bulk row's run with no saturation witness is `INVALID`, exit 3** (#521; the science agent's ruling on #521). `beta-athena-now-bulk` reads the gaps of token streams beside a 64 MiB transfer, and they measure something only when the transfer loaded the path while the streams ran: the control's bytes counted with their time and rate, and all eight streams running across the whole transfer. A run without that witness, and with no failure, is judged, recorded (verdict `invalid`) and posted (headed `INVALID`, with why), and the script prints `INVALID` apart from `PASS`, `FAIL` and `NOT RUN`: not a failure, not a pass, run it again. **`INVALID` is not a `NOT RUN`, though both exit 3:** a `NOT RUN`'s job never started, or its row was never put to the test, so it spent nothing of the slot and posts nothing of a run; an `INVALID` run's job started, ran and spent the slot's hold, the test ran, and it posts what it read, but the reading measures nothing it can be judged by. The post, the marker and the script's line each say so in words. A failure of any other check wins. Its marker is `not-run.txt` with words of its own, which the script holds to that row.

**A tunnel row whose long stream does not fit the context is `NOT RUN` too** (#451; the science agent's rulings (b) and (ii), 12 Nov 2026). `tunnel-hour-helios` and `tunnel-hour-athena` size the one completed long stream of check 2 to the deployment's `max-model-len` at the engine's rate, measured on a first stream before the hour: as long as `(max-model-len - 512) / rate` allows, rounded down to a whole second, and at most 4 min 30 s (halfway from the 4-minute `NearDeadline` to the deadline, which the stream had before). The 4 minutes it replaces are 53,730 tokens at the A100's 199 tokens/s, over the 32,256 a context of 32768 leaves; the model's own limit is 32,768, so a longer context would need YaRN and another deployment ID. A fit under 135 s ends the row `NOT RUN`, exit 3, before any request of the hour, with no text to post; the marker and the script's line name the rate and the context. 135 s is the floor because the stream is judged at 8/9 of what it was sized for and at least 2 minutes: 8/9 of 135 s is exactly 2 minutes, so no stream under 2 minutes is ever a pass (a fit of 120 to 134 s, which a floor of 2 minutes admitted, is `NOT RUN`). The other checks, which carry the hour, are unchanged: one tunnel session through it, back-to-back requests, 16 streams at once, no cut.

## Settings

The settings file is named by `HPCBURST_LIVE_SETTINGS`: `KEY=VALUE` lines, mode 600, owned by you (`hack/live-checks.sh`, header). Values never appear here, on the screen or in a post. Each missing setting is reported in one refusal (exit 3).

| Setting | Needed by | What it is |
|---|---|---|
| `LIVE_OUT_DIR` | every row | a private directory for logs and records |
| `LIVE_LOCK_DIR` | every row | the directory with the hosts' lock files |
| `LIVE_BUILD_LOCK` | optional | the shared build lock; builds take it, test runs never do |
| `ACCOUNT_ATHENA_A100` | Athena rows | the grant account for `plgrid-gpu-a100` |
| `ACCOUNT_HELIOS_GH200` | Helios rows (beta's) | the grant account for `plgrid-gpu-gh200` |
| `LIVE_CONF_CREDENTIALS_ATHENA`, `LIVE_CONF_CREDENTIALS_HELIOS` | rows on that host | the Provider's ssh credentials file, mode 600 |
| `LIVE_DIALHOME_MODE` | the four stack rows | `direct`, `ssh` or `host-dialed` (HBEP-6, Dial-home modes). Alpha's host runs `host-dialed` ([below](#host-dialed-mode)) |
| `LIVE_DIALHOME_ADDR` | the four stack rows, `direct` and `ssh` modes | `host:port` of the route, as the compute nodes see it. **Not set in `host-dialed` mode**: the mode has no address, since the host dials the jobs, and a row with one set is refused, like a missing setting (exit 3) |
| `LIVE_DIALHOME_KEY` | stack rows, `ssh` mode | the restricted dial-home key file, mode 600 |
| `LIVE_DIALHOME_LISTEN` | stack rows, `direct` mode | `host:port` of the front's dial-home listener on this host, where the owner's route arrives (the front's `dialHomeListen`, which has no default in direct mode) |

One environment variable, not a setting: `LIVE_PENDING_MAX_SECONDS` is how long a job may wait in the queue before the run cancels it. The default is 7200 (2 hours), except on a row in a one-job slot that has no start wait: `alpha-helios-nooverlap` and `tunnel-hour-helios`, the rows that hold QOS `now`'s GPU for hours, and `real-engine`: there it is 1800 (30 minutes), because a job of ours that pends for two hours stands in the owner's one-job slot (#222, and the science agent's rule of 2 Nov 2026: every row in a one-job slot, on either cluster, has a start wait of 10 minutes or less or a wait in the queue of 30 minutes or less, which `hack/livechecks` reads off the cluster table). An explicit value overrides either default, shorter or longer, and the script states it exactly (`59 s`, `1 min 30 s`, `10 min`). What a job still pending past it ends as is in "What a run ends as", above; `real-engine`'s job the script itself polls and cancels by its tag (#222). Athena's `plgrid-gpu-a100` queue was estimated at a start on 13 Nov for one GPU (#145, 1 Nov 2026): set it from the estimate that `--run` prints, which is the reason it is printed first. The script's timeout for a row is the row's run time plus this wait, once for each of its jobs, except a row with a start wait, whose bound is its first clock and is already in its timeout. Tests derive each row's least timeout from its bounds in the table and the waits in the code, those waits with a quarter more for what a scan can miss, and fail when a timeout can fire first.

### Host-dialed mode

Alpha's host runs the stack rows in `host-dialed` mode, because compute nodes cannot reach it and the gateway's forward is not awaited. The owner's ruling of 9 Nov 2026 was "we have to solve this, you should wait for nothing. just dial whatever you want from this host" (HBEP-6, Dial-home modes; HBEP-11, open question 8, amended the same day). The host dials each job through the Provider's login node, and the job's two connections run back over what it opened.

- **Settings:** `LIVE_DIALHOME_MODE=host-dialed`, and no `LIVE_DIALHOME_ADDR` (a set one is refused). The mode needs no key and no `LIVE_DIALHOME_LISTEN`. The row starts the stack with `hpcburst up --front-mode host-dialed`, which takes no `--front-addr` and no `--front-key`. The front's dial-home listener stays on loopback at the port base plus 7.
- **What the run needs from the network:** the Provider's ssh credentials, as every cluster row does, and nothing else: no gateway port forward, no restricted key, no route for the compute nodes. A reverse forward on a login node binds its loopback only, and ssh into a compute node needs a Kerberos ticket, which is why the relays below carry the connections (HBEP-6, probe of 9 Nov 2026).
- **The relays.** The stack's controller keeps two per running job, one for the agent's control traffic and one for the token tunnel. Each is an `ssh` to the login node, on a connection of its own, that runs `srun -u --overlap --jobid=<job> --ntasks=1 <staged hb-agent> relay <channel> --dir <Allocation directory> --allocation <UID> --epoch <E> --seq <N>`, with `control` or `serving` as the channel. The relays are `ssh` children of `hpcburst-controller` and die with it. The step is the agent binary itself, and it is part of the run's job, not a job of its own. On the login node a relay is an ssh session and an `srun` client that compute nothing (HBEP-4, open question 14, amended 9 Nov 2026).
- **The rendezvous.** The agent makes one Unix socket, for both channels, in a directory with a random name, `hb-relay-<random>` (mode 700), under the job's `$TMPDIR`, which the site removes with the job, so a killed agent's directory goes with it; under `/dev/shm` only when the `$TMPDIR` path would pass a socket's 107 bytes, which the agent logs. The random name means no other user can create it first. It writes the socket's path into `<Allocation directory>/relay-socket` (mode 600), by a temporary file and a rename. The step reads that file, checks that the agent's greeting, `hpcburst-agent/1 <Allocation UID>`, names its Allocation, and sends `relay/1 <channel> <E> <N>`; the agent answers `ok` or `superseded` and refuses another user's peer (`SO_PEERCRED`). After `ok` the step writes `hpcburst-relay/1 <Allocation UID>`, which the host side requires first, within 30 s; any other first output is refused as `unexpected output before the preamble` and retried. One multiplexed session (`fatedier/yamux`) then runs over the step's input and output.
- **The fence.** E is the `provider-<name>` `Lease`'s `leaseTransitions` when the controller took the lead, and N a count of relay starts. The agent keeps the highest (E, N) on each channel and refuses a lower one as `superseded`, which the controller never starts again. A copy that stops leading stops its relays by PID before it releases the `Lease`, so a hand-over between two copies does not make their relays take turns cutting each other.
- **The cap:** a host-dialed Provider has at most 2 Allocations, pending or running, the handover pair. The lifecycle controller applies that as a submit limit, `SubmitLimitReached`, whose message names "host-dialed mode, HBEP-6", and the Provider's controller counts again from a fresh read just before it submits, refusing a third with `SubmitLimitReached`, for the moment two leaders overlap. `alpha-athena-handover`'s two jobs together take all 4 relay slots of the login node, and the row holds no third. An Allocation's pair of slots is reserved whole and held through its relays' restarts and backoffs, so a relay that drops never hands its slot to another job. A replacement that is still pending has no relays until its job runs. Only one host-dialed Provider runs per login host, as `ssh -G` resolves its host name: the Provider's controller refuses a second, whose `Ready` condition goes False with reason `LoginHostInUse`, and the planner then skips it as `ProviderUnavailable`.
- **See them during a run.** `hpcburst status` on the run's state directory gives the controller's PID, and `pgrep -a -P <pid>` lists its children: two per running job, ending in `relay control` and `relay serving`. `logs/controller.log` in that directory has a line when a relay starts, one when it ends (with `end`, which is `retried`, `superseded`, `the job's end` or `failed`, and `cause`), one when it ends for good and one when a start is refused. To look at the socket from the login node, read `<Allocation directory>/relay-socket`, then run `srun --overlap --jobid=<job> --ntasks=1 ls -la <its directory>`, which lists the socket and the directory's mode. [Operations, Host-dialed relays](operations.md#host-dialed-relays) has the rest.
- **What a drop costs a row.** A relay that drops cuts the streams on it, counted as cuts and never replayed, and frpc logs in again once the relay is back. A restart of the controller does the same to every relay, because they die with its process: the owner accepted that for alpha (9 Nov 2026, "Accept cuts for alpha", https://github.com/groundnuty/plgrid-llmlab-hpc-burst/pull/298#issuecomment-6749435073), and the new leader starts the relays of every running job within the backoff. A relay keeper that would keep them across a restart is beta. A row that judges "none was cut" fails on a cut stream, and `tunnel-hour-*`'s first check (one tunnel session for the hour) fails on the changed `lastStartTime`. A controller restart mid-run therefore fails `tunnel-hour-*` in this mode, and any other row with a stream in flight, where in `direct` and `ssh` modes it would cut nothing.
- **When a relay does not run:**
  - `a relay did not start` in the log. The controller starts a relay only for the job the Allocation recorded, listed running under its tag in the Provider's latest queue listing (the one its poll keeps, with no `squeue` of its own). `job <id> is <phase>, not running yet` and `job <id> is not listed under tag <tag>` are retried after the backoff, starting no `srun` (a listing can miss a running job for a while). `job <id> is completing` and `job <id> is <phase>, not running` end that relay for good as the job's end, with no event; around the job's start or end that needs nothing.
  - No relays for a running job while two other jobs' relays run on the same login node: the job waits for a pair of slots, with no log line. The cap of 2 Allocations leaves this as a backstop.
  - A `relay started` and `relay ended` pair with a short `up`, repeating after the backoff (1 s, doubling to 30 s, with jitter, reset after 60 s up), `end` `retried` and its `cause` naming why: `agent not ready` (the step found no socket that answers, because the agent has not published one yet), `unexpected output before the preamble` (the login shell prints to standard output for a non-interactive ssh), `no preamble` (nothing came within 30 s), or the kind of an ssh failure. `agent not ready` is ordinary for the first seconds of a job; if it goes on once the agent runs, the agent died, and the job's `job.err` tells.
  - `superseded` after a hand-over is expected and final: the agent keeps the newer copy's relay, and nothing needs doing.
  - An event with the reason `RelayFailed`, regarding the Allocation, naming the channel and the cause, means a relay ended for good for another reason than `superseded` or its job's end: `srun` refused the step because the job's step limit is reached, or one channel's sessions came up and dropped more than 120 times within an hour (failures before a session comes up, such as `agent not ready` or a login node down, never count). The controller starts no relay of that channel again while the job runs, unless it restarts, and at the same moment it writes the Allocation's condition `RelayEndedForGood` True, which a controller restart does not lose (if that write fails, its next observation of the Allocation sets it). The lifecycle controller's next pass then ends the Instance with `RelayEndedForGood` and a `failing` event and releases the Allocation, whose finalizer cancels the job, and the planner makes a replacement (issue #304). So the GPU is not held; a row that judges no Instance failed fails, and the cause in the event's message says whether the next job will meet it too.
- **Cleanup:** the relays stop by PID with the Allocation, and each `srun` step ends with its job at the latest (HBEP-6, Paths), so cancelling the run's jobs by tag, as the cleanup does, also ends their steps.

## The one-job slot, the jobs a run holds, and the owner's go

Helios QOS `now` and Athena `plgrid-now` allow one job per user, and the owner shares them (#145, 1 Nov 2026): use them sparingly, batch checks, leave nothing held, and post each use. Before a row takes a slot the script reads it, refuses (exit 3) if it already holds a job, reads it again after the builds, and prints `slot use (<slot>): start <UTC> end <UTC> duration <hh:mm:ss>` when the run ends. That line goes in the post.

The owner's go covers both: the possible pend, which comes first, and the hold, which starts when the job does. It is a few hours at most, not the 12 h `maxWall` of QOS `now`. `alpha-athena-now-serve` holds the `plgrid-now` slot for up to the hour and needs the same kind of go, `LIVE_OWNER_GO_ATHENA_NOW`: it prints "may wait up to 10 min to start (then it is cancelled by its tag and the run is NOT RUN), then holds the plgrid-now slot for about 1 h 00 min; the owner's go is needed (the development rule on #145)" and refuses without today's date. `gpu-accounting-athena-now` holds that slot for about 16 minutes, rounded up to 20, and needs the same go: it prints "may wait up to 10 min to start (then it is cancelled by its tag and the run is NOT RUN), then holds the plgrid-now slot for about 0 h 20 min; the owner's go is needed (the development rule on #145)" and refuses without today's date. The verdict fails a deployment that allows any other Provider, or none, and the dry run shows it with a deployment that also allows Athena. The other stack rows are held to their own cluster the same way, because a run that could place its Instance elsewhere measures nothing.

**The run keeps to those counts with the deployment's `endTime`** (issue #245; the science agent's rulings on PR #255). These rows bound their deployment's life on purpose, so that each stays within the job count above: a row that let the controller go on would plan replacements for ever. The continuous replacement chain is the one-host rehearsal's to show (`hack/rehearsal.sh`, part 3), not these rows'. With no queue wait observed, the lifecycle controller creates a primary's replacement at the primary's start; with a long one it creates a successor's own replacement in the very pass that first sees the successor run (HBEP-7, Handover). A deployment that ends at or before an Instance's drain start gives it no replacement (`internal/lifecycle/handover.go`). Every end is placed on the cluster's own clock, read on the login node (`date -u +%s`) through the run's own ssh, because the controller compares the end with the jobs' times, which the scheduler gives on that clock.
- **A tunnel row** creates its deployment ending at the earliest drain start its job can have: the cluster's clock read just before the creation, plus the job's time limit (the lease), less the 15-minute drain window. Once the job runs and its lease end is known, the end moves to a minute before the Instance's own drain start. Neither end is after a drain start, so no replacement is ever planned. The Instance drains a minute early, and the run records that as the drain start.
- **A two-job row** (`alpha-athena-handover`, `alpha-helios-nooverlap`) creates its deployment with the same kind of end, and a guard in the test moves it on with every look at the cluster, every 10 seconds: the cluster's clock, then the queue listing of the run's jobs. While no job of the run has started, and while only the predecessor has, the end is the latest look's clock plus 1 h 31 min (the 1 h 46 min lease less the drain window), which is no later than the drain start of any job that starts after that look. So the predecessor's start meets an end at or before its own drain start, which plans no successor yet; the first look after it raises the end past the predecessor's drain start, and only then can the successor be created. Once the successor runs, the end is its own drain start, reckoned as its start plus the time limit less the drain window: that is its lease's drain start, or up to the job's configuration time earlier, at most 5 min, since Slurm moves a job's lease end later by the time its configuration took and the guard stops the run on a lease end more than 5 min later (#534). It stays there for good. A third job that starts, a failed write of the end, three failed looks in a row, or a successor's drain start not after the predecessor's, stops the run at once (FAIL), and the run must end with the successor's drain start seen as the deployment's end. `internal/lifecycle` shows the guard against the controller with a first wait of 61 and of 90 minutes, on Helios's one-GPU QOS and on Athena's queue with a successor that starts after the drain start: no third Allocation is created, where an end set only at the successor's start lets one through.
- **The wait in the queue each row allows** (its first clock), and what a job still pending at its end makes of the run:

  |---|---|---|

  | `alpha-athena-handover` | 2 h (`LIVE_PENDING_MAX_SECONDS`); no cap from its end, which moves on while it waits | the row's lease is 1 h 46 min, not the setting |

The script's cleanup, and the test's own, find the run's jobs by the run's tag prefix (below) and check that none is left.
- **The Athena rows run when #145's daily estimate is under their cap:** `tunnel-hour-athena` under 2 h 1 min at the default lease, or under 3 h 44 min at `LIVE_TUNNEL_LEASE_MINUTES=240` with `LIVE_PENDING_MAX_SECONDS` set to the estimate; `alpha-athena-handover` under its `LIVE_PENDING_MAX_SECONDS`, and in practice well under the 1 h 31 min from the predecessor's start to its drain start, since the successor waits in the same queue and must be ready before that drain start for the handover to happen.

Cleanup is by the run's own jobs, and by them alone. The script draws a run ID (10 random hex digits) for each stack row and passes it to the test, which names the row's Provider and deployment `alpha-<ID>`; the controller names every Allocation after its Provider, so every job of the run is named `hb-alpha-<ID>-...`. The test also writes each Allocation's tag to `job-tags.txt` when its watch first sees it. On every exit, a signal included, the test's Close and then the script cancel every job of the run's prefix or of a tag written down, and only those, until the queue shows none of them alive: a job is alive while the scheduler holds, queues or runs it, and while it is COMPLETING after its end. A tag the watch delivered late, or that could not be written, leaves no job behind.

## The shortest lease

Every stack row's deployment sets a short `leaseLimit` and a short `routing.maxRequestDuration`, so that a handover or a gap fits in hours, not in the 48 h of the partitions. The lease cannot be shorter than the lead an Instance needs, or the Provider is skipped with `PartitionTooShort` and no Allocation is made. The lead is the drain window plus `handoverMargin` plus `health.startTimeout` (`internal/lifecycle/timelimit.go:22`), and an Allocation hosts an Instance only when its time limit is longer than the lead, in whole minutes (`timelimit.go:42`). The drain window is `routing.maxRequestDuration` plus the profile's `drainMargin` when that is shorter than its `drainWindow` (`api/v1alpha1/writers.go:87`).

With a `routing.maxRequestDuration` of 5 minutes and the shipped profiles' values (`drainMargin` 10 minutes, `handoverMargin` 30 minutes, `health.startTimeout` 1 hour) the lead is 1 h 45 min, the figure `profiles/athena.yaml:39` gives, and the shortest lease **1 h 46 min**, which the two handover rows use. Each stream they hold across a drain start must finish within the 5 minutes.

**The tunnel hour is one healthy session, not one stream.** The front cuts a request at the deployment's deadline (HBEP-5), and a deployment can only shorten the front's, so no stream can last an hour behind a 5-minute deadline. The science agent's ruling of 2 Nov 2026 reads `hbep/0006-instance-reachability/README.md:601` and `:625` as an hour of one tunnel staying healthy under real use, so the 5-minute deadline stays and the hour is what the tunnel carries across many requests.

**The tunnel rows' lease is chosen by measurement.** The hour of traffic (61 minutes) must end before the drain start, 15 minutes before the lease ends, so the Instance must be ready within `lease - 76 minutes` of its job's start (`LatestReady`): 30 minutes under the shortest lease, 1 h 46 min, and 61 minutes under 2 h 17 min (a start of up to `health.startTimeout`, the hour, the drain window and a minute). The rule: take GH200's measured start-to-ready with the cold SIF build included; under 20 minutes, keep 1 h 46 min, else 2 h 17 min. The measurement is the second real-engine run on Helios GH200 ([issue #94, comment 6557821833](https://github.com/groundnuty/plgrid-llmlab-hpc-burst/issues/94#issuecomment-6557821833)): a cold build with an empty image cache and a slow Hub; the job started at 11:42:26Z and its first Instance had qualified and warmed up at 12:06:05Z, **23 min 39 s** later. That is over 20 minutes, so the default is **2 h 17 min**, and the Helios row holds the slot for about 2 h 20 min. A failed hour costs that hold and a rerun, which is worse than the margin. The owner may choose the other value, or any from 106 to 240 minutes, with `LIVE_TUNNEL_LEASE_MINUTES` when giving the go; the hold note, the shape and the test follow it, and a start slower than the lease allows fails the row with "the hour ended after the Instance's drain start".

## The worker-rung fault's process tree

The stack rows' worker-rung fault lists the processes of the run's job on its node and kills the engine: the process the agent launched through Apptainer (`internal/alpha/workerfault.go`, `PickEngine`; issue #445). The listing itself holds paths, logins and job IDs, so it is never logged. Instead the step writes a redacted shape of the job's process tree (`internal/alpha/engineshape.go`, `Shape`): a line of counts, then a line per process of the job's tree with its depth, a kind for its program, how it is of the job, its cgroup's form and which of the pick's three conditions it meets (`job`, `apptainer`, `command`). It holds no PID, path, login, host or job ID.

**The engine is the one process of the job that meets all three conditions.** It is **of the job** (its environment or cgroup names the job, or it descends from a process that does); it is **under Apptainer** (its parent is Apptainer's, or a shell under one, each of the job) **or its parent is hidden from this user** (#488; the science agent's ruling on #488, 12 Nov 2026): the parent's PID is not in the listing, which holds this user's processes only, AND the listing could not read its `/proc` entry, which is what Apptainer's setuid starter, running as another user, looks like under `hidepid`; and it **runs the launch's command**. A parent that can be read must still be Apptainer's: one the node could read but the listing does not hold is refused as before. The hidden parent counts at the engine's own parent, never above a shell. Exactly one such process is killed (through its pidfd); zero or several kill nothing and print the shape.
- **Where it is:** in the run's private test log when the engine was found, and in the row's FAILED output when the count was not one. It is for the operator and the agents to read, never for a post: the posts (`posts.md`) do not carry it.
- **Reading a failure:** the engine is the line that meets `job+command`. Look at what it lacks, and at the lines above it:
  - no `apptainer`, under a process of kind `other`: an Apptainer name the pick does not know;
  - no `apptainer`, with `parent:unlisted` at depth 0: its parent is not this user's to list, and the node could read it, so it must be Apptainer's and is not; `parent:hidden` at depth 0 is the other case (its parent is not listed and could not be read: Apptainer's setuid starter, which the pick takes as Apptainer's, `meets:job+apptainer+command`), so a `parent:hidden` line that lacks `apptainer` or `command` says which of the other conditions it fails;
  - no line meets `command`, but a `python` or `vllm` line sits under the `runtime-parent`: the command line's form differs (its `argv:` form says how);
  - the counts line says 0 in the job's tree: no process's environment or cgroup tied it to the job.

It is judged at **the larger of 8/9 of what it was sized for and 2 minutes**: 4 minutes of 4 min 30 s at the cap, as before; about 2 min 24 s of the A100's 2 min 42 s (199 tokens a second on a context of 32768); never under 2 minutes, whatever the plan. It is judged on the long requests alone (the chains the row sizes this way, by their role), never on the hour's 16 burst streams, however long those last: a burst stream that crosses the bar is no evidence that the long stream completes (the science agent's ruling (a) on #451, https://github.com/groundnuty/plgrid-llmlab-hpc-burst/issues/451#issuecomment-6824492878). The share is there because the measured rate includes the time to the first token, so a bar at the full plan would fail routinely. A fit under 135 s, which is what makes a bar of 2 minutes, is `NOT RUN`, exit 3, before the hour starts, and says the rate and the context (`FitLong`, `internal/alpha/longstream.go`); 16 streams open at once at 20 tokens/s each or more; an idle stretch of 2 minutes or more with no request open (heartbeats only).
    3. **No cut:** no response with a `cutBy`, no `stream_cut`, every request complete and within the deployment's 5-minute deadline (a longer one fails: the front would have cut it); the requests span an hour and end before the Instance's drain start, which must be observed.

    **On a live row, in alpha** (the science agent's ruling (4) on PR #255: no product change, so no sender-side timing on the live path; front-side timing is post-alpha, #273), criteria 4 and 5 read:
    - The upload's interval and rate are **not measured in alpha**, and the text to post says so ("not measured in alpha (no sender-side timing on the live path)"). The download is measured as in 4. A dry run keeps the full check: there a missing upload rate or interval fails.
    - **Each large body shows it arrived whole.** The large requests are chat prompts of words ("hello") that ask for one token (`max_tokens` 1), under the deployment's context, so the engine serves each whole, a prefill of the whole prompt, and its response's `usage.prompt_tokens` counts every token of the prompt it read. Only a completed response is read: every choice finished, and the usage complete and adding up. A refusal is no count: vLLM v0.32.0 serves a prompt under the context however many tokens it asks for (it clamps `max_tokens`), and over the context it says "at least N input tokens" (the parent's reading of its source, after the delta round of PR #255). Before the hour, three such prompts of 1,000, 2,000 and 4,000 words give the engine's count as a line in the words (tokens a word, and the chat template's): the first two fix it, and the third must lie on it exactly. The large prompt holds as many words as 0.4 MB takes, but fewer tokens than the context, leaving room for its one token: at the live 32,768 tokens and a token a word, 32,763 words, 0.2 MB. A fourth prompt, of half its words (16,382 there), must lie on the line too. A count that is not whole tokens a word, or that bends anywhere up to half the large prompt (a token merged or split every so many words), fails the row, as does a context that cannot hold 0.1 MB under it. **What the count shows:** frp is a byte tunnel, so a body cut short on the way is no longer JSON, and the engine answers it with an error; the row fails on any large body not answered with a completed response with its usage. Equal counts are the second check: the body arrived whole when its usage counts exactly its own count, from the line, so the engine tokenized the whole well-formed body. A path that rewrites content (a proxy that edits well-formed JSON) is out of scope for this check, because frp carries bytes and does not parse payloads. Two senders send it for the 30 s of the download's measurement, each half a second after its last reply, once all 16 streams run, and one must have been in flight, from its first byte sent to its response read on the client's clock, while 16 streams at 20 tokens/s were open. The large requests do not count toward the run back to back: they follow one another a fraction of a second apart.
    - **Head-of-line** (reported, not judged): the longest gap between two tokens of any stream while a large body was in flight, by the client's windows, against the longest elsewhere in the hour. Each large body's window is split where the client wrote the body's last byte to its connection: its **send window** (first byte to last byte, the body on its way) and its **prefill window** (last byte to the response, the engine prefilling the body's whole prompt, about 16,000 to 32,000 tokens live, before its one token). Each gap is classed: a send if it overlaps any body's send window (the two senders interleave, so a gap often overlaps another body's prefill as well), a prefill if it overlaps only prefill windows, and neither otherwise; the text to post gives the longest in flight, the longest of each of the first two, and the longest elsewhere. A gap over 1 s is FLAGGED as a stall, and each FLAG names its class ("in a send window", "in a prefill window", "in neither window"), so that a reader can tell a tunnel stall from engine work: at the 20 tokens a second the streams must hold a token is due every 50 ms, an engine's scheduling hiccup is tens of milliseconds, a second in a send window points at the tunnel holding the token direction behind a body, and a second in a prefill window at the engine's prefill, which can lengthen the gaps by itself.
    Also: the deployment is as above; the cluster's own record names exactly one job (by job ID: a held duplicate under the tag, or a second tunnel job, fails) on the row's partition, with the lease as its time limit, and both its start and end time, an hour or more apart: a missing time fails.

## Before the first real run

1. `hack/live-checks.sh --list` and `--plan origin/main..HEAD` name the rows; `--run <row>` (no `--yes`) prints the shape and the estimate, or the settings it lacks.
2. Run `gpu-accounting` first: short, no route needed, and fully wired. It runs on `plgrid-now` now, so it needs the owner's go (`LIVE_OWNER_GO_ATHENA_NOW`) and the slot free. `reach` is as short and needs the owner's word that the forwarded port is up; the stack rows in `host-dialed` mode do not need that port.
3. Set `LIVE_PENDING_MAX_SECONDS` from the estimate before a queued run.
4. Post each result where the row says, with its slot use. The text of `posts.md` is private until you copy it; it holds counts, durations and fixed labels, never a host, account or job ID.
5. Every row that runs the stack posts `watch resets over the run`, a measured count. A reset fails the test as "not known", on any kind, and the failure says whether any read's window crossed it. If a live row ever fails on a reset that no read crossed, the rule is refined before that row is re-run. A reset that only catch-ups crossed counts as one that no data read crossed (`@hpc-burst-science-agent`, 9 Nov 2026): a catch-up crosses any reset it finds, which is the coarse rule's own conservatism, and a verdict rests on the data reads. The failure tells the two apart, since a catch-up reads there as "the catch-up for ...", so a row that fails where only catch-ups crossed gets the same refinement before it is re-run.
6. On the first Athena run in host-dialed mode, confirm that the scheduler sets `TMPDIR` in the job and in an `--overlap` step (`reach-host-dialed-athena`'s rendezvous line says both): it is the relays' rendezvous precondition (HBEP-4, open question 16), measured on Athena on 9 Nov 2026, and Athena's profile sets no `tmpDir` of its own (the science agent's ruling, 9 Nov 2026: no profile change, since pinning one would also move the engine's temporary files). A miss shows within seconds: the agent exits with `ErrNoSocketDir`, `no directory for the relay socket under TMPDIR`, on its output in the job's `job.err`.

## What the dry runs show, and what they cannot

The package tests and `hack/livechecks` run every row's own compiled test, through the script, over a fake Slurm in run mode with stand-in steps. The healthy run passes; each of its faults (a cut stream, no stream in flight, a second restart, a successor that starts beside its predecessor, a lane an hour short, a deployment that also allows Athena, the default lease, a lease at the lead, no `ReleaseWhenIdle`, a node with two GPUs against a record of one, no request body of 0.1 MB, large requests sent far from the streams, a missing upload or download rate, and so on) fails its row with exit 1, while a node whose `nvidia-smi` lists eight GPUs to a job given one still passes, and `hack/mutate-alpha.sh` changes each criterion's condition and requires a test to fail. The dry fault `pend-past-bound` shows the pending bound: the owner's job holds the fake QOS's one GPU until a release file appears (no fixed window), the run's job pends past the first clock and is cancelled by its tag, and every stack row ends `NOT RUN` with exit 3 (the owner's job untouched on the two Helios rows), the Athena rows included, as does `gpu-accounting-athena` in its own dry fault `queue-held`. `gpu-accounting-athena-now` ends `NOT RUN` in its dry fault `slot-held`: the owner's job holds the partition's one-job slot, the run's job pends past the 10-minute start wait and is cancelled by its tag, and the owner's job is left alone. The dry fault `second-never-started` runs a first job to its end beside a second held in the queue, and both two-job rows end `NOT RUN`; with a failure of the first job's part added (`second-never-started-cut`, `second-never-started-late-cut`, `second-never-started-no-restart`), or a catch-up that cannot tell (`second-never-started-not-known`), they fail instead. The `-late` and `-unknown` variants show that what the run read of `ReplacementLate` changes neither end. The dry run keeps the bound the script gave it, and the stand-in logs the manual clock one second before the bound (the job still pending) and one second after it (cancelled), which the tests check against bounds written out in them. A dry binary refuses live settings, and the script never passes the dry switch on.

They cannot show that the real controllers, front and tunnel behave: the stand-in steps report what the real scenario will report, and the criteria judge it.
