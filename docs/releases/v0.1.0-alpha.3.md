# v0.1.0-alpha.3

The third alpha of plgrid-llmlab-hpc-burst. Since [v0.1.0-alpha.2](v0.1.0-alpha.2.md), it adds sticky routes for Workloads, a beta feature used only when a Workload asks for it. Like the earlier alphas, it's tagged before alpha graduates (HBEP-15, Releases). The criteria still open, the HBEPs' statuses (none is at a stage yet), the stated limits and the pins are alpha.2's, with the additions below.

Start with [the quickstart](../quickstart.md). From the archive, unpack it, check `SHA256SUMS`, and follow the steps with the archive's `bin/`, `agent-builds/`, `config/crd/`, `profiles/` and `examples/`. No clone is needed.

## New in this release

**Sticky routes** (HBEP-5, Workloads, Sticky routes; #791, #795). A Workload with `sessionAffinity: Route` pins each conversation, on its first request, to one target, one of our ModelDeployments at its deployment ID or LLMLab, and never moves it:
- such a Workload's requests must carry a session header, one the front's `sessionHeaders` names (`x-session-id` by default), or get 400 `session_header_required`;
- the pin is journalled to the front's usage directory before the request is sent, so it survives a front restart if that directory is kept;
- later requests go only to the pinned target. When it's full, they wait in the Workload's queue and are served if it frees before `queueTimeout`, else they get 503 with `Retry-After`;
- a pin expires `pinTTL` after its conversation's last request ends, at the TTL in force when it was made (12 h by default);
- `maxPins` bounds a Workload's live pins (100,000 by default). Past it, a new conversation gets 503 `pins_full` at once, and existing pins are kept;
- a Workload's `model` and `sessionAffinity` can't be changed once it exists.

**Also:** Sano's profile and docs record that direct mode has served (#801); this changes comments and fact text only, with no field value.

## Stated limits, added to alpha.2's

- **Sticky routes:**
  - `managedSessions` counts requests in flight on LLMLab, not conversations. More conversations than that can be pinned to LLMLab, and their later turns wait when it's reached.
  - LLMLab's own answers, a 429 or 503 included, pass through to a pinned conversation, which is never rerouted.
  - Once a rollout of a pinned ModelDeployment to a new deployment ID starts, its pinned conversations get 503 `pinned_target_gone` until their pins expire. Don't roll one out while its conversations are live. A briefly empty list of current IDs means wait, not gone.
  - Recreating a Workload clears its pins, so a conversation's next request is a first request again.
  - LLMLab reports no revision, so a change of model behind its managed ID isn't seen.
  - A conversation idle for longer than `pinTTL` starts again as a new one. After a front restart, a pin journalled as in flight gets a full `pinTTL` from the restart.
  - If the pin journal can't be read at start, or a write needed before a request is sent fails, that request gets 503 `pins_unavailable`, never a move. A failed write after a request ends is logged.
- **Upgrading a live stack** to this release restarts the front, which cuts streams in flight. The agent's code is unchanged since alpha.2, but its binary carries the release's version, so its `agentDigest` differs: new Allocations get the new build, and running ones keep theirs.
