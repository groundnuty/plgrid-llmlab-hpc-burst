# v0.1.0-alpha.3

The third alpha of plgrid-llmlab-hpc-burst. Since [v0.1.0-alpha.2](v0.1.0-alpha.2.md), it adds sticky routes for Workloads, a beta feature used only when a Workload asks for it. Like the earlier alphas, it's tagged before alpha graduates (HBEP-15, Releases). The criteria still open, the stated limits and the pins are alpha.2's, with the additions below.

Start with [the quickstart](../quickstart.md). From the archive, unpack it, check `SHA256SUMS`, and follow the steps with the archive's `bin/`, `agent-builds/`, `config/crd/`, `profiles/` and `examples/`. No clone is needed.

## New in this release

**Sticky routes** (HBEP-5, Workloads, Sticky routes; #791, #795). A Workload with `sessionAffinity: Route` pins each conversation, on its first request, to one target, one of our ModelDeployments at its deployment ID or LLMLab, and never moves it:
- such a Workload's requests must carry the session header (`x-session-id`);
- the pin is journalled to the front's usage directory before the request is sent, so it survives a front restart if that directory is kept;
- later requests go only to the pinned target. When it's full, they wait in the Workload's queue, then get 503 with `Retry-After`;
- pins expire `pinTTL` after a conversation's last request (12 h by default), and `maxPins` bounds them (100,000 by default);
- a Workload's `model` and `sessionAffinity` can't be changed once it exists.

**Also:** Sano's profile and docs record that direct mode has served (#801); this changes comments and fact text only, with no field value.

## Stated limits, added to alpha.2's

- **Sticky routes:**
  - `managedSessions` counts requests in flight on LLMLab, not conversations. More conversations than that can be pinned to LLMLab, and their later turns wait when it's reached.
  - LLMLab's own answers, a 429 or 503 included, pass through to a pinned conversation, which is never rerouted.
  - A rollout of a pinned ModelDeployment to a new deployment ID ends its pins once the rollout starts (503 `pinned_target_gone`), so don't roll one out while its conversations are live.
  - A conversation idle for longer than `pinTTL` starts again as a new one.
  - If the pin journal can't be read or written, the Workload's requests get 503 `pins_unavailable`, never a move.
- **Upgrading a live stack** to this release restarts the front, which cuts streams in flight. The agents are unchanged since alpha.2.
